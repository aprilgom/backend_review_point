# FC0344 · 현재 render 메서드로 View를 처리하는 방식과 스프링의 View 처리 방식에 어떤 차이가 있는지 묻는다.

[소속 분야: 렌더링·데이터 로딩](../18-rendering.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0345](FC0345.md) · [다음 FC: FC0347 →](FC0347.md)

- [ ] 현재 render 메서드로 View를 처리하는 방식과 스프링의 View 처리 방식에 어떤 차이가 있는지 묻는다. (설계 질문)
  - 조건: 3단계와 관련된 학습 질문이다. 작성자는 ViewResolver를 통한 View 선택과 데이터 반환 시 ModelAndView 부재 처리 등을 설명했지만, 이 설명의 기술적 정확성을 리뷰어가 확인한 후속 발언은 없다.

- [ ] 리다이렉트하는 경우에도 먼저 request에 모델 속성을 설정할 필요가 있는지 물었다. (설계 질문)
  - 조건: 리뷰어는 해당 부분을 충분히 학습하지 못한 상태에서 질문한다고 밝혔다. 작성자는 리다이렉트에서 request 객체를 재사용하지 않는다는 이유로 속성 설정을 forward 시점으로 옮기겠다고 답했다. 실제 변경 여부는 확인되지 않는다.

- [ ] 세션 속성을 Model로 복사하는 이유와 해당 데이터가 뷰 렌더링에 사용되는 구체적인 경우를 질문했다. (설계 질문)
  - 조건: 작성자는 세션의 User 등을 사용해 JSP와 JSTL을 직접 파싱하고 응답을 작성해야 한다고 생각해 추가한 코드라고 설명했다. 이후 RequestDispatcher를 사용하기로 했고 기존 코드도 이미 이를 사용하고 있었음을 알게 되어 복사 코드를 삭제할 계획이라고 답했다. 리뷰 참여자는 이 설명 중 잘못 이해했던 부분을 추가로 물었으며, 세션 복사 자체를 확정된 결함으로 보고한 것은 아니다. 삭제 완료 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
View view = viewResolver.resolve(result.viewName());
view.render(result.model(), request, response);
```

**적용 설명:** 자체 MVC의 논리 뷰 이름 해석과 렌더링을 분리한 개념 코드다. Spring과 비교할 때 선택·모델 전달·출력 책임을 대응시킨다.
