# FC0346 · 요청 모델 전달과 서버 내부 이동

[소속 분야: 렌더링·데이터 로딩](../18-rendering.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0345 →](FC0345.md)

## 검토 질문

- [ ] 서버 템플릿에 전달할 데이터를 요청에 담는 이유와 forward·redirect의 차이를 이해하는가?

**직접 작성한 예시**

```java
request.setAttribute("tasks", taskReplies);
request.getRequestDispatcher("/WEB-INF/views/tasks.jsp").forward(request, response);
```

**적용 설명:** Jakarta Servlet 사용 예다. 같은 요청의 모델을 서버 템플릿에 전달하며 브라우저 리다이렉트와 다르다.

## 구체적인 검토 사례

- [ ] 뷰 렌더링에서 응답이 아닌 요청에 속성을 설정하는 이유와 RequestDispatcher 및 forward의 역할을 알아보자고 제안한다. (설계 질문)
  - 조건: 리뷰 참여자는 자신도 이유를 아직 모른다고 명시하며 3단계에서 살펴볼 학습 주제로 제시했다. 작성자는 다음 처리 주체에 필요한 속성을 전달하기 위한 것일 수 있다고 추측했고, 리뷰 참여자도 비슷하게 예상했다며 다음 단계에서 공부하겠다고 답했다. 양측의 추측을 확인된 동작 설명이나 현재 구현의 결함으로 보지 않는다.

- [ ] 모든 액션에서 뷰를 새로 렌더링하는 방식이 의도된 것인지 질문했다. (설계 질문)
  - 조건: 작성자는 버튼에 따라 표시할 정보가 달라 별도의 hbs 뷰를 렌더링하도록 의도했다고 설명했다. 리뷰 참여자는 향후 프런트엔드 개발자와 협업하며 데이터만 주고받는 서버를 만들 때 다른 방식을 경험할 것이라고 덧붙였으며, 현재 방식을 결함으로 확정하거나 변경을 요구하지 않았다.

- [ ] 어노테이션으로 매핑된 핸들러를 실행한 뒤에도 뷰가 렌더링되도록 GET·POST /register의 처리 흐름과 렌더링 위치를 확인하도록 요청했다. (문제 보고)
  - 조건: 처음에는 렌더링을 어디서 수행할지 묻는 질문이었다. 작성자는 다른 코멘트에 정리했다고만 답했으며 그 내용은 이 단위에 없다. 다만 후속 댓글에서 리뷰 참여자는 SimpleHandlerAdapter와 달리 AnnotationHandlerAdapter에는 렌더링 로직이 없어 뷰가 렌더링되지 않았다고 설명하고, 렌더링을 HandlerAdapter 외부로 위임하여 해결되었다고 평가했다.
