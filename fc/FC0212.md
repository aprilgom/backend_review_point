# FC0212 · Reservation이 status로 예약과 예약 대기를 표현하는 것을 어색하게 느낀 이유를 묻고, 취소 예약까지 고려해 모델 분리 기준을 검토하도록 제안한다.

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0211](FC0211.md) · [다음 FC: FC0210 →](FC0210.md)

- [ ] Reservation이 status로 예약과 예약 대기를 표현하는 것을 어색하게 느낀 이유를 묻고, 취소 예약까지 고려해 모델 분리 기준을 검토하도록 제안한다. (토론)
  - 조건: 리뷰어는 현재의 통합 모델이 충분히 합리적이라고 보면서 다른 모델로 분리하는 방식도 이유가 있다면 가능하다고 설명했다. 작성자는 상태 필드 자체보다 예약이라는 이름이 예약 대기까지 포함하는 점이 어색했다고 답했고, 취소 예약 보관 요구사항을 적용하며 별도 모델 여부를 고민하겠다고 했다.

- [ ] 예약과 예약 대기를 상태로 함께 표현하는 대신 별도 도메인으로 분리하는 방향을 어떻게 보는지 논의한다. (토론)
  - 조건: 작성자는 현재 요구사항에서는 두 개념이 같은 슬롯에 대한 사용자 신청의 상태 차이이며, 승격과 취소 규칙도 슬롯 기준이므로 함께 관리하는 편이 응집도가 높다고 설명했다. 대기 자체에 독립적인 생명주기와 규칙이 생기면 분리를 고려할 수 있다는 조건도 제시했다. 리뷰 참여자는 이 근거가 적절하다고 인정하면서 변경을 요구하는 것은 아니라고 명시했고, 슬롯 기준으로 예약은 1:1이고 대기는 1:N이라는 관계 차이에서 다시 생각해 보도록 질문했다. 이 후속 질문에 대한 작성자의 답변은 없다.

- [ ] 예약과 대기를 Reservation의 상태로 표현하는 설계 외에, 별도 개념으로 분리한다면 어떤 방식이 가능한지 논의한다. (토론)
  - 조건: 리뷰어는 Reservation에서 처리하거나 상태로 표현하는 방식도 가능하다고 인정하면서, 분리할 경우의 설계 방법을 질문했다. 분리를 필수 변경으로 요구한 것은 아니다. 작성자는 다른 댓글에 정리했다고 링크만 제시했으므로, 구체적인 분리 방안과 후속 결론은 제공된 대화에서 확인할 수 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
void cancel() {
    if (state == CANCELLED) throw new AlreadyCancelled();
    state = CANCELLED;
}
```

**적용 설명:** 상태 모델을 선택했다면 허용 전이와 취소 정책을 함께 정의한다. 취소의 멱등성 요구에 따라 결과 계약은 달라진다.
