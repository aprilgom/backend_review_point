# FC0028 · 응답 객체의 변환 책임

## 검토 질문

- [ ] 도메인 필드를 호출부마다 꺼내 조립하는 대신 응답 객체의 생성 경계에 변환 규칙을 모을 수 있는가?

**직접 작성한 예시**

```java
static CartLineReply from(CartLine line) {
    return new CartLineReply(line.productName(), line.quantity());
}
```

**적용 설명:** 응답 타입이 도메인을 읽게 해 변환 코드를 모은다. 도메인에서 응답 타입을 참조하는 역방향 의존은 피한다.

## 구체적인 검토 사례

- [ ] CartItem의 필드를 각각 꺼내 응답 DTO를 만들기보다 CartItem 자체를 받는 생성 메서드를 추가하자는 제안이다. (개선 제안)
  - 조건: CartItemResponse.of 호출에 대한 제안이다. 작성자는 수정했다고 답했으며 구체적인 구현은 제시되지 않았다.

- [ ] 수량과 체크 상태를 따로 변경하는 이유를 묻고, 개별 변경이 필요 없다면 changeCartItem(quantity, checked) 같은 하나의 연산으로 합치자고 제안했다. (조건부 제안)
  - 조건: 리뷰 참여자는 서비스에서 사용자 유스케이스가 드러나야 하는데 상태 변경 호출이 나뉘면 혼란을 줄 수 있다는 이유를 제시했다. 개별적으로 변경하는 경우가 없다는 조건의 제안이며, 작성자는 분리한 특별한 이유는 없고 제안한 방식으로 수정해도 좋겠다고 답했다. 실제 수정 완료는 확인되지 않는다.

- [ ] 도메인에서 상품을 제거한 뒤 별도 deleteCartItem을 호출하는 대신 cartRepository.save(cart)로 변경된 장바구니를 저장할 수 있는지 제안한다. (개선 제안)
  - 조건: 작성자는 동작을 명확히 드러내기 위해 save와 delete를 분리했다고 설명했다. 이후 save를 현재 장바구니 상태의 저장으로 해석할 수 있다고 받아들이며 리팩터링 의사를 밝혔지만, 변경 결과는 확인되지 않는다.
