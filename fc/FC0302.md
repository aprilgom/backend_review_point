# FC0302 · 조회와 변경의 부작용 표현

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0331](FC0331.md) · [다음 FC: FC0335 →](FC0335.md)

## 검토 질문

- [ ] 조회처럼 보이는 메서드가 외부 상태를 변경한다면 분리하거나 이름에서 부작용을 드러내는가?

**직접 작성한 예시**

```java
Station next = findNextStation(current);
result.add(next);
```

**적용 설명:** 조회와 외부 컬렉션 변경을 나누어 부작용을 보이게 한다. 합치면 appendNextStation처럼 동작을 드러낸다.

## 구체적인 검토 사례

- [ ] findNextStation이 조회뿐 아니라 전달받은 result에 요소를 추가하므로, 실제 동작을 더 잘 드러내는 이름이 있는지 질문했다. (설계 질문)
  - 조건: 작성자는 두 기능이 함께 있어 명령-쿼리 원칙에 위배된다고 판단하여 메서드를 분리했다고 보고했다. 명령-쿼리 분리의 필요성은 작성자가 제시한 판단이며, 리뷰 참여자의 직접적인 요청은 동작에 적절한 메서드 이름을 검토하는 것이었다.

- [ ] getHandlerMappings가 객체 생성과 초기화까지 수행하므로 create를 사용하는 이름도 어울리지 않을지 의견을 묻는다. (토론)
  - 조건: 초기화 시 한 번만 호출되는 구조임을 인정하면서 제시한 개인적인 명명 의견이며, 현재 이름을 확정적인 결함으로 지적한 것은 아니다. 작성자는 동의하고 반영했다고 답했다.

- [ ] user와 member의 의미 차이를 묻고, 두 용어가 혼용되어 혼동을 줄 수 있다고 지적했다. (토론)
  - 조건: 작성자는 member를 user와 admin으로 구분했다고 설명하고, 두 권한 모두 사용하는 UserInfo를 MemberInfo로 바꿨다고 보고했다. 리뷰어는 여전히 혼동과 혼용 가능성을 언급했고, 작성자는 이후 user를 없애고 regular와 admin으로 구분했다고 보고했다. 실제 변경 내용과 혼동 해소 여부는 별도로 확인되지 않았다.
