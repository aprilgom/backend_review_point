# FC0101 · 대기 생성 요청이 거의 동시에 들어오는 상황을 검토하고 트랜잭션 격리 수준을 확인해보자는 제안이다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0104](FC0104.md) · [다음 FC: FC0106 →](FC0106.md)

- [ ] 대기 생성 요청이 거의 동시에 들어오는 상황을 검토하고 트랜잭션 격리 수준을 확인해보자는 제안이다. (개선 제안)
  - 조건: 작성자는 트랜잭션만으로 동시성 문제를 완전히 보완하지는 못한다고 보았고, 문제 상황을 정확히 이해하지 못해 추가 동시성 대응은 고려하지 않았다고 밝혔다. 리뷰 참여자는 후속으로 격리 수준 학습을 권했으며, 구체적인 경합 결과나 해결 여부는 확인되지 않는다.

- [ ] 기존 예약을 조회한 뒤 없으면 생성하는 흐름에서 두 요청이 거의 동시에 들어올 경우 어떻게 동작하는지 트랜잭션 격리 수준과 함께 검토하도록 질문한다. (설계 질문)
  - 조건: 리뷰 참여자가 중복 생성의 재현 결과를 보고한 것은 아니다. 작성자는 H2의 기본 격리 수준을 Read Committed로 설명하며 두 요청이 모두 예약 부재로 판단할 수 있다고 답했고, 테마·시간·날짜 조합의 unique 제약과 DB 예외 처리를 보완책으로 제시했다. 해당 설명의 기술적 검증이나 보완책의 실제 적용 여부는 확인되지 않는다.

- [ ] 락이 필요한 근본 원인과 가능한 대안을 살펴보고, 다른 방법 대신 현재 락 방식을 선택한 이유를 설명하도록 요청했다. (설계 질문)
  - 조건: 작성자는 동일 슬롯의 예약 생성·취소·대기 승급 간 판단을 순차화하려는 목적이라고 설명했다. 유니크 제약만 사용하면 충돌 후 대기 전환 처리가 필요하고, 낙관적 락도 재시도 설계가 필요하므로 슬롯 행의 SELECT FOR UPDATE를 선택했다고 밝혔다. 배타락 선택과 슬롯 ID 순서에 따른 잠금으로 데드락을 방지하려 했다는 설명도 작성자의 학습·설계 근거이며, 리뷰 참여자의 검증이나 동작 확인은 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
BEGIN;
SELECT id FROM queue_slot WHERE id = :slot_id FOR UPDATE;
INSERT INTO waiting(slot_id, member_id) VALUES (:slot_id, :member_id);
COMMIT;
```

**적용 설명:** 슬롯 행을 잠그는 DB 트랜잭션 예시다. 관련 작업이 같은 잠금 규약을 사용하고 고유 제약도 갖춰야 한다.
