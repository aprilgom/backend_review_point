# FC0158 · 구현체가 하나인 Repository에 인터페이스가 필요한지, 분리의 이점을 현재 누리거나 앞으로 누릴 가능성을 납득할 근거가 있는지 검토하도록 했다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0178](FC0178.md) · [다음 FC: FC0176 →](FC0176.md)

- [ ] 구현체가 하나인 Repository에 인터페이스가 필요한지, 분리의 이점을 현재 누리거나 앞으로 누릴 가능성을 납득할 근거가 있는지 검토하도록 했다. (토론)
  - 조건: 작성자는 향후 확장성과 메서드 목록의 파악 용이성을 근거로 들고 코드 증가와의 선택은 취향 차이인지 물었다. 리뷰어는 이점 자체를 부정하지 않고 실제 효용과 미래 가능성을 따져 설명할 수 있어야 한다고 답했다. 작성자는 현재 규모와 확장 가능성에서는 이점이 부족하다고 판단하여 인터페이스를 삭제하겠다고 했다. 구현체가 하나면 인터페이스를 쓰면 안 된다는 보편 규칙을 제시한 대화는 아니다.

- [ ] Repository 인터페이스 분리의 장단점과 테스트용 구현체를 만들기 위해 인터페이스가 반드시 필요한지 묻는 논의다. (토론)
  - 조건: 작성자는 데이터베이스와 독립된 테스트 및 원인 파악의 용이성을 장점으로, 인터페이스와 구현체를 함께 수정하는 작업량을 단점으로 들고 향후 변경을 고려해 분리를 선택했다고 설명했다. 리뷰 참여자는 상속으로도 테스트용 구현체를 만들 수 있지 않느냐고 재질문했다. 인터페이스 제거 요구나 어느 방식이 옳다는 결론은 없다.

- [ ] DB 접근 구현체를 쉽게 교체할 수 있도록 Repository를 인터페이스로 추상화하는 방안을 고려했는지 논의했다. (토론)
  - 조건: 작성자는 현재 규모에서 인터페이스 분리가 파일 수와 구조 복잡성을 늘릴 수 있어 적용하지 않았다고 설명했다. 리뷰 참여자는 이에 동의하며 당장 필수는 아니라고 완화했다. 추상화의 교체 가능성이라는 관심사 자체를 철회한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
interface Documents {
    Optional<Document> find(DocumentId id);
    void save(Document document);
}
```

**적용 설명:** 도메인 언어로 저장 계약을 제한하는 예다. 같은 메서드 전달만 추가하는지, 실제 의존 경계를 만드는지 확인한다.
