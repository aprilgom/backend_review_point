# FC0457 · 필수 입력과 primitive 기본값

[소속 분야: 타입·타입 테스트](../24-type-safety.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0455](FC0455.md) · [다음 FC: FC0462 →](FC0462.md)

## 검토 질문

- [ ] 기본형을 사용할 때 누락이 기본값으로 바뀌는 바인딩 동작이 입력 계약과 맞는가?

**직접 작성한 예시**

```java
record RequiredQuantity(int quantity) {}
record OptionalQuantity(Integer quantity) {}
```

**적용 설명:** primitive는 null을 표현하지 않는다. 바인더의 누락 처리·0 기본값이 입력 계약과 맞는지 확인한다.

## 구체적인 검토 사례

- [ ] DTO와 PathVariable에서 기본형 타입을 사용하는 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 타입 선택을 미처 신경 쓰지 못했다고 답하면서도, PathVariable에는 값이 반드시 들어오므로 누락 시 기본값이 설정되는 문제가 적용되지 않는 것 아니냐고 반문했다. 현재 ID 타입과 같아 문제없을 수 있다고 보면서 일관성을 위해 기본형을 피하는 편이 좋겠다고 덧붙였다. 해당 반론에 대한 후속 답변은 없다.

- [ ] Class<Junit3Test> 대신 Class<?>를 사용해 구체적인 타입 정보를 생략한 이유를 질문했다. (토론)
  - 조건: 작성자는 편의성과 스트림 사용 시의 타입 캡처를 이유로 들었다. 리뷰 참여자는 타입 캡처에 관해 찾아본 설명을 공유하고, 해당 테스트에서는 특정 타입 메서드 호출 제약이 문제가 되지 않아 와일드카드 사용에 문제가 없어 보인다고 판단했다. 작성자가 마지막에 언급한 성능 저하 등의 단점은 작성자의 견해이며 리뷰 참여자의 요구나 검증된 사실로 취급하지 않는다.

- [ ] ModelAndView의 view 필드를 View 대신 Object 타입으로 관리하게 된 이유를 묻는다. (설계 질문)
  - 조건: 작성자는 핸들러에서 View 인스턴스를 직접 생성하는 번거로움을 줄이고 문자열 viewName을 전달할 수 있도록 하려는 선택이라고 설명했다. 내부 값에 따라 View를 생성하고 렌더링하려는 의도이며, 리뷰어가 이 선택을 결함으로 확정하거나 타입 변경을 요구한 것은 아니다.
