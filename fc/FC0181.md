# FC0181 · 탐색 범위의 외부 구성

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0184](FC0184.md) · [다음 FC: FC0175 →](FC0175.md)

## 검토 질문

- [ ] 스캔 대상 패키지나 등록 범위를 하드코딩하지 않고 실행 맥락에서 공급하며 허용 범위도 제한하는가?

**직접 작성한 예시**

```java
String basePackage = entryPointClass.getPackageName();
List<Class<?>> handlers = scanner.findHandlers(basePackage);
```

**적용 설명:** 실행 진입점을 탐색 기준으로 주입한다. 모듈·하위 패키지 포함 범위와 보안상 허용 범위를 정한다.

## 구체적인 검토 사례

- [ ] 스캔 대상 패키지를 바꿀 때 DispatcherServlet 코드를 수정하지 않도록 상수 대신 애플리케이션 실행 패키지를 기준으로 동적으로 정하는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 스프링 부트의 @SpringBootApplication 위치를 스캔 기준으로 삼는 방식에 빗대어 의견을 제시했다. 작성자는 반영했다고 보고했지만 실제 기준 패키지 결정 구현은 제시되지 않았다.

- [ ] ControllerScanner의 탐색 패키지를 samples로 고정하지 말고 외부에서 지정할 수 있게 하자고 제안했다. (개선 제안)
  - 조건: 어노테이션 기반 Controller가 app 모듈에 만들어질 수 있다는 예상에 근거한 제안이다. 작성자는 패키지를 외부에서 주입받도록 변경했다고 보고했다.

- [ ] MVC 패키지의 DispatcherServlet이 특정 애플리케이션 컨트롤러 패키지에 의존하는 구성을 다른 방식으로 바꿀 수 있는지 논의했다. (토론)
  - 조건: 작성자는 지정한 패키지만 명시적으로 스캔하는 방식을 선호하며, 변경 가능성이 낮아 결합의 위험보다 예상치 못한 패키지를 스캔할 위험을 더 우려한다고 설명했다. 리뷰 참여자는 DispatcherServlet을 개발자가 직접 관여하지 않는 프레임워크 영역으로 보았기 때문에 제기한 의견이라고 배경을 밝혔다. 양측의 프레임워크 설정 경계에 대한 관점 차이가 드러나며, 변경 합의나 명백한 철회는 없다.
