# FC0134 · 연관 도메인을 객체로 참조해야 하는지, ID 참조만으로 충분한지 설계할 때 검토해보라고 제안했다.

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0132](FC0132.md) · [다음 FC: FC0135 →](FC0135.md)

- [ ] 연관 도메인을 객체로 참조해야 하는지, ID 참조만으로 충분한지 설계할 때 검토해보라고 제안했다. (토론)
  - 조건: 리뷰 참여자는 필수 반영 사항이 아니며 Reservation에만 한정된 논의도 아니라고 명시했다. 작성자는 전체 객체 데이터가 필요하지 않을 때의 ID 참조 가능성은 이해하지만 의존관계를 끊는 이점은 아직 체감하지 못한다고 답했다. 리뷰 참여자는 생명주기가 다른 엔티티 간 참조를 ID로 분리하는 경우를 예로 들고 향후 개발·운영에서 떠올려보라고 했다. 현재 코드를 ID 참조로 변경하라는 확정 요구는 아니다.

- [ ] CartItem이 Product와 Member를 ID가 아닌 객체로 보유하는 이유와, 객체 참조가 더 순수한 도메인이라는 판단 근거를 논의했다. (토론)
  - 조건: 작성자는 다른 객체의 DB ID를 알면 도메인의 순수성이 깨진다고 보아 객체를 보유하게 했으며, 매핑 편의와 순수성의 트레이드오프라고 설명했다. 리뷰어는 ProductId 대신 Product를 알면 순수한 도메인인지 되물었다. ID 보유가 곧 도메인 순수성 훼손이라는 주장이 기술적 사실로 확정된 것은 아니다.

- [ ] CartItem에서 Product와 Member의 필드를 펼쳐 보관한 이유를 묻고, 객체 참조를 유지하거나 외부 객체 의존을 피하려는 경우 식별자만 보관하는 방식을 제안했다. (토론)
  - 조건: 리뷰어는 내부에서 필드를 펼칠 필요가 없어 보인다고 했으며, 특히 Product를 직접 참조하지 않으려는 목적일 때 ID 참조를 대안으로 제시했다. 마지막에는 변경 없이 진행해도 된다고 완화했으므로 필수 수정 요구나 철회로 보지 않는다. 후속 링크의 상세 내용과 완화 발언의 정확한 적용 범위는 이 단위만으로 확정하기 어렵다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record Purchase(CustomerId customerId, List<Line> lines) {}
```

**적용 설명:** 다른 집합의 식별자만 보유하는 모델 예시다. 즉시 동작 협력이 필요한 객체라면 직접 참조가 더 자연스러울 수 있다.
