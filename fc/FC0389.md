# FC0389 · 비밀번호와 개인정보를 DB에 평문으로 저장하는 것이 문제이므로 서버에서 저장 전 암호화하는 방식을 고려해야 한다는 의견이다.

[소속 분야: 인증·보안·비밀값](../20-security.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0388](FC0388.md) · [다음 FC: FC0391 →](FC0391.md)

- [ ] 비밀번호와 개인정보를 DB에 평문으로 저장하는 것이 문제이므로 서버에서 저장 전 암호화하는 방식을 고려해야 한다는 의견이다. (의견)
  - 조건: 리뷰어는 계정·보안 경험이 없어 설명이 정확하지 않을 수 있다고 명시했다. 실제 DB에 평문으로 저장되고 있다는 확정적 결함 보고가 아니라, 평문 전송과 저장 위험을 구분하는 설계 의견이다.

- [ ] 비밀번호를 더 안전하게 다루기 위해 저장 전 암호화와 로그인 시 비교 방식을 학습하고 적용해보도록 제안했다. (조건부 제안)
  - 조건: 리뷰 참여자는 전달받은 비밀번호를 암호화해 DB에 저장하고 로그인 입력도 암호화하여 비교하는 흐름을 설명했다. 이는 원문의 제안이며 구체적인 알고리즘이나 보안 타당성은 확인되지 않았다. 요구사항 구현을 먼저 마치고 시간이 남으면 시도하라는 조건이 있었고, 작성자도 우선 JPA 관련 기능에 집중한 뒤 고려하겠다고 답했다.

- [ ] JWT의 memberId 노출이 일으킬 수 있는 구체적 취약점, 필드 자체와 ID 생성 방식 중 원인, 방어 방법과 대응 비용의 타당성을 검토하고 크루들과 논의해 정리하도록 요청했다. (설계 질문)
  - 조건: 리뷰 참여자는 memberId 노출을 확정된 취약점으로 단정하지 않고 위협과 비용을 구체화하는 질문을 제시했다. 작성자는 세션·토큰의 절충과 JWE 비용을 논의했다고 보고하고, memberId는 페이로드에 두되 노출만으로 위험한 정보가 추가되면 JWE를 사용하겠다는 개인적 결론을 밝혔다. 이는 작성자의 결론이며 리뷰 참여자가 그 보안 타당성을 확인한 발언은 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
String encoded = passwordHasher.hash(rawPassword);
accounts.create(loginName, encoded);
boolean matches = passwordHasher.verify(attempt, encoded);
```

**적용 설명:** passwordHasher는 검증된 비밀번호 전용 해시 구현을 뜻한다. 비밀번호에 가역 암호화나 단순 빠른 해시를 직접 구현하지 않는다. 개인정보 보관은 별도 정책이다.
