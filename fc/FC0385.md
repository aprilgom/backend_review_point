# FC0385 · 자원 수명 관리 책임의 집중

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0384](FC0384.md) · [다음 FC: FC0386 →](FC0386.md)

## 검토 질문

- [ ] 쿼리 실행 도구와 연결 관리 도구 중 누가 트랜잭션 참여·소유권·해제를 결정하는지 명확한가?

**직접 작성한 예시**

```java
ConnectionLease lease = connections.acquire();
try { return executeQuery(lease.connection()); }
finally { connections.release(lease); }
```

**적용 설명:** 커넥션 소유권·트랜잭션 참여를 관리하는 자체 계약 예다. 쿼리 실행 도구가 임의로 소유권을 추측하지 않게 한다.

## 구체적인 검토 사례

**혼합·경계:** 직접 구현한 JDBC 도구의 책임 배치와 트랜잭션 자원 관리.

- [ ] 트랜잭션 사용 여부에 따른 커넥션 상태 확인과 처리를 JdbcTemplate이 아닌 DataSourceUtils에 둔 이유를 묻는다. (설계 질문)
  - 조건: 리뷰어는 책임 배치의 이유를 질문했으며 결함이나 변경 요구로 단정하지 않았다. 작성자는 JdbcTemplate을 커넥션 획득과 SQL 실행에 집중시키고, DataSourceUtils가 트랜잭션 동기화 판단과 커넥션 관리를 맡도록 분리했다고 설명했다. 또한 JdbcTemplate을 사용하지 않는 경우에도 DataSourceUtils를 재사용할 수 있다는 장점을 제시했다.

- [ ] DAO에서 SQL 생성을 분리한 이유를 묻고, DAO는 실행할 내용을 정하고 JdbcTemplate은 실행 방법을 담당하도록 책임을 나누는 관점을 제시했다. (토론)
  - 조건: 작성자는 엔티티 재사용성과 필드 변경에 따른 외부 수정 방지를 위해 JdbcTemplate이 SQL도 생성하도록 했다고 설명했다. 리뷰 참여자는 DAO에서 SQL을 만드는 것을 개인적으로 선호하며, 조인이나 서브쿼리가 필요해지면 JdbcTemplate 사용법과 내부 동작 이해 부담이 커질 수 있다고 설명했다. 작성자는 이 관점에 동의하고 2단계 리팩터링 계획을 밝혔으나, 실제 변경 여부는 확인되지 않는다.

- [ ] JdbcTemplateDao 구현 클래스가 Template과 DAO의 역할을 동시에 수행하게 되는지 검토하자고 질문했다. (설계 질문)
  - 조건: 역할 혼재를 확정하기보다 질문으로 제기했다. 작성자는 인터페이스를 나누고 MySqlJdbcTemplateDao가 Dao를 구현하도록 수정했다고 보고했지만, 그 변경이 책임 분리를 충족하는지는 대화에서 확인되지 않는다.
