# FC0359 · HttpResponse가 응답 값을 표현하는 것 외에 요청에 맞는 Controller를 찾고 실행하는 책임까지 가져야 하는지 검토한다.

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0356](FC0356.md) · [다음 FC: FC0364 →](FC0364.md)

- [ ] HttpResponse가 응답 값을 표현하는 것 외에 요청에 맞는 Controller를 찾고 실행하는 책임까지 가져야 하는지 검토한다. (토론)
  - 조건: 리뷰 참여자는 HttpResponse의 Controller 의존성과 ControllerMapping 호출 위치를 질문했다. 작성자는 Http11Processor로 책임을 옮기는 방안을 제시하면서도 서버 패키지가 애플리케이션의 ControllerMapping에 의존하는 문제를 추가로 질문했다. 리뷰 참여자는 자신의 구현에서는 Response를 값 보관과 문자열 출력에 한정하고 RequestInfo와 HandlerAdapter로 Controller를 찾는다고 설명했다. 이 대화에서 특정 구조의 적용이나 의존성 문제의 해결은 확인되지 않는다.

- [ ] 브라우저 요청을 나타내는 HttpRequest에서 서버가 관리하는 HttpSession을 직접 가져오는 책임 배치가 자연스러운지 논의했다. (토론)
  - 조건: 리뷰어는 예시 파일도 같은 구조임을 인정하며 코드 수정은 필요 없다고 명시했다. 작성자는 Sessions에 request나 requestHeader를 넘기는 방식이 더 자연스럽다는 의견을 냈다. 리뷰어는 요청을 받은 뒤 별도로 세션에 데이터를 넣었으며 그 주체를 Controller-Service 등 프레임워크로 생각했다고 설명했지만, 다음 MVC 미션에서 더 고민할 사안으로 남겼다.

- [ ] HttpHeader가 요청 헤더와 응답 헤더라는 두 가지 책임을 함께 맡고 있는 것으로 보인다는 의견을 제시한다. (관찰)
  - 조건: 참여자가 인식한 책임 구조에 대한 관찰이다. 요청·응답 헤더를 반드시 별도 클래스로 분리하라는 구체적인 요구까지 제시한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Handler handler = routes.find(request);
HttpReply reply = handler.handle(request);
writer.write(reply);
```

**적용 설명:** 응답 값 객체가 라우팅과 실행까지 맡지 않도록 역할을 나눈다.
