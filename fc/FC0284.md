# FC0284 · 페이지 조회 방식의 비용

## 검토 질문

- [ ] 깊은 OFFSET의 비용과 키셋 방식의 제약을 이해하고 이동·정렬·동시 변경 요구에 맞게 선택했는가?

**직접 작성한 예시**

```sql
SELECT id, title FROM post
WHERE id > :last_id ORDER BY id LIMIT 50;
```

**적용 설명:** 깊은 OFFSET을 피하는 키셋 페이지 예다. 임의 페이지 이동·복합 정렬·동시 변경의 의미는 다르다.

## 구체적인 검토 사례

- [ ] OFFSET 페이지네이션의 동작 방식과 부하 측면의 문제 가능성을 더 검토하도록 질문했다. (설계 질문)
  - 조건: 작성자는 OFFSET이 커지면 앞선 데이터를 탐색·정렬한 뒤 버리는 비용이 발생할 수 있다고 설명했다. 커서 기반 방식은 작성자가 제시한 대안이며, 데이터 증가나 무한 스크롤 요구가 생기면 고려하겠다고 했을 뿐 현재 교체 요구나 성능 측정 결과는 없다.

- [ ] 외부 API 응답을 로깅할 때 응답 크기를 제한하는 방안을 검토해보자. (개선 제안)
  - 조건: 작성자는 외부 API 통신이므로 로깅이 필요하다는 의견을 냈고, 사람 참여자도 요청·응답 기록의 디버깅 가치를 인정하면서 응답 크기 제한을 고민해보자고 제안했다. 작성자는 앞으로 염두에 두겠다고 답했으며 실제 제한 구현 여부는 확인되지 않는다. 봇만 언급한 구체적인 처리 방식과 성능 주장은 추출하지 않았다.

- [ ] 모델 크기가 1로 확정된 경우 스트림을 생성하지 않고 값을 직접 꺼내는 방안을 제안한다. (개선 제안)
  - 조건: 단일 요소임이 보장되는 경로에 한정된 제안이다. 리뷰 참여자는 스트림 생성 비용을 이유로 들었으나 성능 측정 결과는 제시하지 않았다.
