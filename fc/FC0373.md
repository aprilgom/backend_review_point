# FC0373 · 복잡한 조회 로직 때문에 fakeRepository 구현이 어렵다면 Repository의 책임이 많은지 살펴보고 관련 로직을 Service로 옮기는 방안을 제안했다.

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0358](FC0358.md) · [다음 FC: FC0383 →](FC0383.md)

- [ ] 복잡한 조회 로직 때문에 fakeRepository 구현이 어렵다면 Repository의 책임이 많은지 살펴보고 관련 로직을 Service로 옮기는 방안을 제안했다. (토론)
  - 조건: 참여자는 E2E가 아닌 서비스 계층 중심 테스트에서 fakeRepository 사용을 긍정적으로 보았다. 작성자는 쿼리에서 필터링하면 불필요한 데이터 로딩을 피하고 서비스 메서드도 작게 유지할 수 있다고 반론했다. 참여자는 복잡한 쿼리보다 서비스 로직이 읽기 쉽다는 개인적 견해를 밝혔으며, 작성자가 제시한 DB와 애플리케이션 간 역할 분담 기준을 계속 고민해보도록 권했다. 단일한 책임 분리 기준에 합의한 것은 아니다.

- [ ] 조회 결과가 없을 때 예외를 던지는 처리를 repository의 책임으로 두는 것이 적절한지 의문을 제기했다. (설계 질문)
  - 조건: 리뷰 참여자는 repository의 default 메서드에서 조회와 예외 발생을 묶는 방식의 유용성은 인정했다. 책임 배치에 대한 질문이며, 잘못된 설계로 확정하거나 변경을 명시적으로 요구하지는 않았다.

- [ ] 단순 위임만 하는 Service와 Repository가 각각 어떤 책임을 가져야 하는지 검토하되, 없는 책임을 억지로 추가할 필요는 없다고 논의했다. (토론)
  - 조건: 리뷰 참여자는 필요한 책임이 다른 곳으로 빠져 있지는 않은지 점검하자고 했다. 작성자는 Repository를 DB 접근 담당, Service를 비즈니스 흐름 제어와 데이터 접근 분리 담당으로 설명했고, 리뷰 참여자는 그 역할 이해를 긍정했다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
List<Order> candidates = orders.findPending();
List<Order> eligible = candidates.stream().filter(policy::canShip).toList();
```

**적용 설명:** 조회와 업무 판단을 나누는 대안이다. 데이터량이 크면 전부 메모리에 올리기보다 DB 조건·전용 조회 계약도 검토한다.
