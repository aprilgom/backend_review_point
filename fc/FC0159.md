# FC0159 · SQL에 사용할 값을 PreparedStatementSetter를 통해 전달받는 방식도 구현해 볼 것을 제안한다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0168](FC0168.md) · [다음 FC: FC0161 →](FC0161.md)

- [ ] SQL에 사용할 값을 PreparedStatementSetter를 통해 전달받는 방식도 구현해 볼 것을 제안한다. (개선 제안)
  - 조건: 리팩터링 힌트를 참고하라는 제안이다. 작성자는 해당 클래스를 새로 만들고 이를 주입받는 메서드 오버로딩을 추가하겠다고 답했으며, 완료 보고는 아니다.

- [ ] 인터페이스 기반 MVC와 애노테이션 기반 MVC를 공존시키는 데 어댑터를 사용할지는 작성자가 선택하되, 도전하고 싶다면 적용 후 리뷰를 요청하자. (조건부 제안)
  - 조건: 두 MVC 방식의 공존은 요구사항이라고 설명했지만, 이를 만족시키기 위한 어댑터 도입 자체는 필수가 아니라 작성자의 선택이라고 명시했다. 구현 완료 여부는 이 단위에서 확인되지 않는다.

- [ ] 공통 Handler 인터페이스가 직접 ModelAndView를 반환하도록 할 수도 있는데, 스프링이 어댑터 패턴을 사용하는 이유가 무엇인지 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 대안 코드로 설계 이유를 질문했으며 어댑터 패턴 제거를 요구하지 않았다. 작성자는 특정 인터페이스를 지원하지 않는 외부 라이브러리·서비스 통합과 기존 Controller 호환성을 장점으로 설명했다. 이 설명은 작성자의 답변이며 기술적 정답으로 별도 검증된 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
StatementBinder values = ps -> {
    ps.setString(1, title);
    ps.setLong(2, ownerId);
};
```

**적용 설명:** SQLException을 허용하는 자체 함수형 계약으로 SQL 값 바인딩을 전달한다. 문자열 연결로 SQL을 만들지 않는다.
