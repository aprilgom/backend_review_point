# FC0213 · HTTP의 method, uri, version은 헤더가 아닌 Request Line에 속하므로 HttpRequestHeader와 다른 객체에서 표현하는 방안을 제안했다.

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0210](FC0210.md) · [다음 FC: FC0214 →](FC0214.md)

- [ ] HTTP의 method, uri, version은 헤더가 아닌 Request Line에 속하므로 HttpRequestHeader와 다른 객체에서 표현하는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰어는 HTTP 메시지 구조를 참고할 것을 권했으며 핵심 근거는 댓글 본문에 있다. 작성자는 Request Line 클래스를 생성해 해당 필드를 옮겼다고 보고했다. 함께 언급한 생성 로직의 정적 팩토리 메서드 이동은 작성자의 추가 리팩터링 보고이지 별도의 리뷰 요구는 아니다.

- [ ] HttpRequest가 Headers 전체 대신 Cookies만 추출해 보관한 이유와 최소 요구사항 구현을 위한 선택인지 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 HttpRequest가 Headers를 속성으로 갖는 것도 자연스럽다고 보았으나 결함으로 단정하지 않았다. 작성자는 Headers의 사용처가 없어 저장하지 않았다고 설명하고, Headers를 보관한 뒤 쿠키를 조회하는 방식도 가능했겠다고 답했다. 실제 구조 변경 여부는 확인되지 않았다.

- [ ] 요청 라인을 문자열로 다루는 대신 HTTP 메서드, URL, 프로토콜을 보관하는 RequestLine 객체로 표현하자는 제안이다. (개선 제안)
  - 조건: 작성자는 요청 라인 객체를 만들었다고 보고했다. 객체의 구체적인 구현이나 적절성까지 확인된 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record RequestLine(String method, String target, String version) {}
record RequestHead(RequestLine line, Map<String, List<String>> headers) {}
```

**적용 설명:** 요청 첫 줄과 헤더 필드를 다른 구조로 표현한다. 반복 헤더와 파싱 검증은 별도 구현한다.
