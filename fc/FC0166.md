# FC0166 · DataSource를 받아 내부에서 JdbcTemplate을 생성하는 UserDao 생성자를 제거하고 JdbcTemplate을 직접 주입받도록 한 이유를 논의했다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0164](FC0164.md) · [다음 FC: FC0162 →](FC0162.md)

**혼합·경계:** JdbcTemplate 주입 사례지만 핵심은 객체 생성 책임·의존성 주입.

- [ ] DataSource를 받아 내부에서 JdbcTemplate을 생성하는 UserDao 생성자를 제거하고 JdbcTemplate을 직접 주입받도록 한 이유를 논의했다. (토론)
  - 조건: 처음에는 생성자를 제거한 이유를 묻는 질문이었다. 작성자가 DataSource 변경에 따라 JdbcTemplate 구현도 달라질 것으로 예상했다고 답하자, 리뷰 참여자는 DataSource가 인터페이스인데 어떤 부분이 구현에 영향을 주는지 재질문했다. 작성자는 DB별 SQL 문법 변경과 JdbcTemplate 구현 변경을 혼동했다고 자신의 설명을 정정하고, 빈으로 제공되는 JdbcTemplate을 재사용할 수 있다는 추가 이유를 제시했다. 이는 작성자 설명의 정정이며 리뷰 관심사 자체의 철회는 아니다.

- [ ] UserDao가 DataSource를 주입받아 JdbcTemplate을 생성하는 대신 JdbcTemplate만 주입받도록 제안한다. (개선 제안)
  - 조건: 현재 코드에서는 UserDao가 DataSource를 주입받을 이유가 없어 보인다는 조건의 제안이다. 작성자는 제거를 잊었다며 수정하겠다고 답했으나, 실제 변경 결과는 이 대화에서 확인되지 않는다.

- [ ] UserDao에 JdbcTemplate 주입 생성자뿐 아니라 DataSource를 받아 내부에서 JdbcTemplate을 생성하는 생성자도 남긴 이유를 논의했다. (토론)
  - 조건: 작성자는 기존 코드가 두 생성자를 모두 사용하며 호출자가 JdbcTemplate을 직접 다루지 않을 때 생성 책임을 UserDao에 맡길 수 있다고 설명했다. 리뷰 참여자는 자신은 JdbcTemplate 생성자만 남겼지만 작성자의 설명에도 설득되었다고 답했다. 생성자 제거를 확정적으로 요구하거나 최초 질문 자체를 철회한 대화는 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
UserDao(SqlRunner runner) { this.runner = runner; }
// 생성 책임은 조립 코드로 이동
UserDao dao = new UserDao(new SqlRunner(dataSource));
```

**적용 설명:** SqlRunner는 자체 JDBC 도우미다. DAO의 의존성과 생성 책임을 분리하는 원리를 보여준다.
