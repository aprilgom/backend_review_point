# FC0127 · INNER JOIN을 선택한 이유와 LEFT JOIN과의 결과 차이, 시간 정보가 누락된 예약의 조회 결과를 질문했다.

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0126](FC0126.md) · [다음 FC: FC0128 →](FC0128.md)

- [ ] INNER JOIN을 선택한 이유와 LEFT JOIN과의 결과 차이, 시간 정보가 누락된 예약의 조회 결과를 질문했다. (설계 질문)
  - 조건: 작성자는 시간 정보가 없는 예약을 유효하지 않은 것으로 보아 INNER JOIN으로 제외하려 했다고 설명했다. LEFT JOIN으로 time_value가 null이면 현재 코드에서 NPE가 발생할 것이라는 설명과 도메인 방어를 추가하겠다는 계획도 작성자의 답변이다. 해당 예외나 별도 도메인 검증 지적이 이 단위에서 직접 확인된 것은 아니다.

- [ ] LEFT JOIN 대신 INNER JOIN을 사용한 이유를 물었다. (설계 질문)
  - 조건: 작성자는 대상 데이터를 좁히기 위해 INNER JOIN을 선택했다고 설명하면서 LEFT OUTER JOIN을 합집합, INNER JOIN을 교집합으로 표현했다. 리뷰 참여자는 설명을 들었다는 반응을 남겼지만, 해당 설명의 기술적 정확성이나 조인 선택의 타당성이 검증된 것은 아니다.

- [ ] INNER JOIN을 선택한 이유와 단순 JOIN 표기를 사용하지 않은 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 Reservation 구성에 필요한 ReservationTime 정보를 한 번의 DB 접근으로 얻기 위해 조인했다고 설명했다. 리뷰어가 JOIN도 사용할 수 있는지 재질문하자, 작성자는 기본 JOIN과 INNER JOIN이 같다고 확인했다며 간결한 JOIN 표기로 변경하겠다고 밝혔다. 리뷰어가 INNER JOIN의 기능적 결함을 확정한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
SELECT b.id, s.starts_at
FROM booking b LEFT JOIN slot s ON s.id = b.slot_id;
```

**적용 설명:** 슬롯이 없는 행도 남기는 계약이다. INNER JOIN과 NULL 처리 결과를 실제 데이터로 비교한다.
