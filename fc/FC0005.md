# FC0005 · 저장소를 한 번 더 추상화하는 근거

## 검토 질문

- [ ] 이미 추상화된 저장소를 추가 인터페이스로 감쌀 때 의존성 격리·모델 변환·교체 가능성 중 어떤 이점이 생기는가?

**직접 작성한 예시**

```java
interface CustomerStore { Optional<Customer> find(CustomerId id); }
final class SqlCustomerStore implements CustomerStore {
    // DB 의존 코드는 이 어댑터에 둔다.
}
```

**적용 설명:** 저장 기술 교체·도메인 분리를 위한 경계가 실제로 필요할 때의 모양이다. 기존 인터페이스를 그대로 복제할 뿐이면 추가 추상화 이점이 작다.

## 구체적인 검토 사례

**혼합·경계:** 저장소 추상화의 필요성이 중심이며 Spring Data 사례가 섞임.

- [ ] 이미 인터페이스인 JpaMemberRepository를 다시 추상화하여 얻는 이점이 무엇인지 질문했다. (설계 질문)
  - 조건: 작성자는 FakeMemberRepository가 JpaRepository의 모든 메서드를 구현하지 않고 실제 필요한 메서드만 구현하도록 범위를 좁히기 위한 설계라고 설명했다. 추가 추상화가 불필요하다는 결함 판정이나 이를 제거하라는 요구는 아니다.

- [ ] NotFoundController만 AbstractController를 상속하지 않고 Controller를 직접 구현한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 NotFoundController를 먼저 만들었고 상속 여부가 동작에 영향을 주지 않아 특별한 이유 없이 그렇게 두었다고 설명했다. 이후 통일성을 위해 상속하도록 바꾸었다고 보고했으며, 이는 작성자의 변경 보고이다.

- [ ] 별도의 FakeTimeRepository가 있는데 테스트 내부 클래스로도 같은 구현을 둔 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 내부 클래스를 분리하는 과정에서 기존 구현을 지우는 것을 잊은 것 같다고 설명하고 제거하겠다고 답했다. 실제 제거 여부는 확인되지 않는다.
