# FC0383 · 재사용 프레임워크와 앱 초기화의 배치

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0373](FC0373.md) · [다음 FC: FC0379 →](FC0379.md)

## 검토 질문

- [ ] 공통 요청 처리·초기화 코드와 애플리케이션별 조립 코드를 적절한 모듈에 배치했는가?

**직접 작성한 예시**

```text
framework/mvc/Dispatcher.java
framework/mvc/DispatcherInitializer.java
app/Bootstrap.java
```

**적용 설명:** 재사용 가능한 배치와 앱별 조립을 분리한 구조다. 이름 이동만으로 역방향 의존이 사라지지는 않는다.

## 구체적인 검토 사례

- [ ] DispatcherServlet과 DispatcherServletInitializer를 app 패키지에 둔 이유를 묻고 mvc 패키지로의 이동을 검토하자고 제안했다. (토론)
  - 조건: 작성자는 DispatcherServletInitializer가 app 패키지에 의존해 분리하지 못했다고 설명했다. 리뷰 참여자도 Initializer는 app에 남기고 DispatcherServlet만 옮겼다고 밝혔으며, 두 클래스 모두의 이동을 강제하기보다 배치를 고민해 보았는지 확인하려는 취지라고 설명했다. 최초 관심사를 철회한 것은 아니다.

- [ ] 이번 구현에서 DispatcherServlet이 수행하는 역할을 설명해 달라고 질문했다. (설계 질문)
  - 조건: 작성자는 요청을 핸들러에 전달하고 실행 결과를 뷰로 렌더링하는 전체 제어 흐름을 관리하는 프론트 컨트롤러라고 설명했다. 이는 작성자의 책임 배분 근거이며, 리뷰 참여자가 변경을 요구하거나 결함을 확정한 것은 아니다.

- [ ] HandlerMapping과 HandlerAdapter를 추가하는 로직을 DispatcherServlet.init() 대신 DispatcherServletInitializer에 둔 이유를 묻는다. (설계 질문)
  - 조건: 리뷰 참여자는 자신도 잘 몰라 묻는 질문임을 명시했으며, init()으로 옮기라고 요구하거나 현재 배치를 결함으로 단정하지 않았다. 작성자는 외부에서 추가하는 편이 좋겠다는 막연한 판단이었다고 설명하고, init()에서 실행하는 방안도 더 고민하겠다고 답했다.
