# FC0316 · 패키지 깊이와 탐색 비용

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0342](FC0342.md) · [다음 FC: FC0336 →](FC0336.md)

## 검토 질문

- [ ] 패키지·모듈 구조의 추가 단계가 역할과 경계를 설명하는지 단순히 탐색 비용만 늘리는지 검토했는가?

**직접 작성한 예시**

```text
domain/
  order/Order.java
  order/OrderId.java
application/
  PlaceOrder.java
```

**적용 설명:** 역할과 탐색 비용을 기준으로 단순화한 구조 예다. 패키지를 줄이는 것 자체보다 의존 방향이 중요하다.

## 구체적인 검토 사례

- [ ] 멀티 모듈 구조가 복잡하게 느껴지는 이유가 도메인 모듈 아래에 추가된 한 단계의 깊이 때문인지 살펴본다. (토론)
  - 조건: 리뷰 참여자는 작성자가 복잡해졌다고 표현한 점을 언급하면서, 자신은 3단계보다 원하는 도메인 객체에 접근하기 편했다고 반대 경험을 제시했다. 구조 변경을 요구하거나 복잡성 문제를 확정한 것은 아니다.

- [ ] 애플리케이션 타입을 CS·WE로 축약하면 작은 저장공간 이득보다 유지보수 비용과 타입 혼동 위험이 커질 수 있다고 지적했다. (토론)
  - 조건: 리뷰 참여자는 애플리케이션에서 사용하는 타입과 다른 축약값에 개인적으로 반대한다고 밝혔다. 작성자는 처음에는 게임마다 타입 문자열을 저장한다고 생각해 비용을 줄이려 했으나, 별도 타입 테이블을 외래키로 참조하는 현재 구조에서는 이득이 작다며 원래 표현을 사용하는 쪽에 동의했다. 실제 변경 여부는 확인되지 않는다.

- [ ] 공통 VO 모듈의 이름으로 common은 어색하지 않으며, 대안으로 core도 괜찮다는 의견을 제시했다. (토론)
  - 조건: 작성자가 common이라는 이름의 적절성을 묻자 참여자가 보편적으로 쓰이는 이름이라고 답했다. 이름 변경을 요구한 것은 아니다.
