# FC0434 · 테스트 수행 전마다 동일한 테이블을 새로 생성하기보다 테스트 전용 truncate SQL로 데이터를 초기화하는 방식을 제안했다.

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0430](FC0430.md) · [다음 FC: FC0432 →](FC0432.md)

- [ ] 테스트 수행 전마다 동일한 테이블을 새로 생성하기보다 테스트 전용 truncate SQL로 데이터를 초기화하는 방식을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 현재 schema.sql이 테이블 생성만 한다는 점을 근거로 /test/resources 하위에 각 테이블의 truncate 문을 담은 파일을 따로 작성하도록 추천했다. 이는 작성자가 설명한 스키마 재실행과 기존 테이블 충돌 문제에 이어 나온 제안이며, 적용 결과는 제공되지 않았다.

- [ ] @Sql을 테스트 실행 후가 아니라 실행 전에 적용해 데이터를 초기화한 이유를 질문했다. (토론)
  - 조건: 리뷰어는 변경 요구가 아님을 명시했다. 작성자는 테스트 시작 시 DB 초기 상태를 보장하기 위해서라고 설명하고, BEFORE_TEST_METHOD가 기본값임을 확인해 명시 구문을 삭제했다고 보고했다. 리뷰어도 다른 테스트의 사후 초기화 누락으로 실패한 경험 때문에 사전 초기화를 선호하지만 개발자마다 판단이 달라 정답은 아니라고 덧붙였다.

- [ ] 테스트 데이터 초기화에 @Sql 대신 별도의 truncate 빈을 만든 이유를 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 @Sql 관련 자료를 함께 제시했다. 작성자는 엔티티가 수정되거나 추가될 때 SQL도 함께 변경해야 하는 수고를 줄이려는 선택이었다고 설명했다. 별도 빈의 사용을 결함으로 확정하거나 @Sql로 교체하라고 요구한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
-- 격리된 테스트 DB 전용
TRUNCATE TABLE test_event;
```

**적용 설명:** DDL 재생성 대신 데이터 초기화하는 예다. DB별 트랜잭션·외래 키·시퀀스·병렬 테스트 영향을 확인한다.
