# FC0124 · 간단한 존재 여부 조회는 직접 쿼리를 작성하는 대신 existsByEmailAndPassword 형태의 메서드를 사용하는 대안도 검토하자는 제안이다.

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0118](FC0118.md) · [다음 FC: FC0123 →](FC0123.md)

- [ ] 간단한 존재 여부 조회는 직접 쿼리를 작성하는 대신 existsByEmailAndPassword 형태의 메서드를 사용하는 대안도 검토하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 이를 '네임드 쿼리'라고 부르며 자체 쿼리 튜닝과 직접 작성한 쿼리의 문법·띄어쓰기 실수 감소를 장점으로 설명했다. 다만 불필요한 조인이나 성능 저하가 생길 수도 있어 상황에 맞게 선택해야 하며, 현재는 두 방식 모두 괜찮다고 명시했다. 자동 최적화 주장을 검증된 사실로 취급하지 않는다.

- [ ] findById의 조회 결과를 사용하지 않는 것으로 보이므로 exists 조회를 사용하는 것을 제안한다. (개선 제안)
  - 조건: 조회 객체를 실제로 사용하지 않는다는 전제의 제안이다. 작성자는 수정하겠다고 답했으며 실제 변경 결과는 제시되지 않았다.

- [ ] 노선 중복 검증에서 findBy 대신 exists 쿼리로 존재 여부를 확인하는 방법을 제안한다. (개선 제안)
  - 조건: 기존의 꼼꼼한 중복 검증을 긍정하면서 제시한 대안이며, 변경 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
boolean exists = accounts.existsByEmail(normalizedEmail);
```

**적용 설명:** 존재 확인용 저장소 계약 예시다. 비밀번호를 평문 조건에 넣는 인증 방식은 예시로 사용하지 않으며 인증은 해시 검증으로 별도 처리한다.
