# FC0167 · 저장 인터페이스의 노출 범위

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0157](FC0157.md) · [다음 FC: FC0160 →](FC0160.md)

## 검토 질문

- [ ] 프레임워크의 넓은 저장 API와 최소 계약 중 실제 필요한 기능만 노출하는 방식을 선택했는가?

**직접 작성한 예시**

```java
interface BookingQueries extends org.springframework.data.repository.Repository<Booking, Long> {
    Optional<Booking> findById(Long id);
}
```

**적용 설명:** Spring Data의 최소 노출 계약 예다. 이 혼합 FC는 포함 대상이며 JpaRepository의 전체 CRUD가 필요한지와 일반 인터페이스 분리를 구분한다.

## 구체적인 검토 사례

**혼합·경계:** Spring Data 상속 API와 일반적인 저장소 인터페이스 분리 논의가 섞임.

- [ ] ReservationRepository가 JpaRepository 대신 Repository 인터페이스를 상속한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 Spring Data JPA 기능은 유지하면서 필요한 메서드만 노출해 테스트나 비JPA 구현체가 불필요한 메서드를 구현하지 않도록 하려는 설계라고 설명했다. 이 선택에 대한 후속 평가는 없다.

- [ ] JpaRepository를 상속하는 저장소 인터페이스에 @Repository를 별도로 명시한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 해당 어노테이션을 생략해도 구현체가 자동으로 빈에 등록되며 별도로 명시한 이유는 없다고 설명하고 삭제하겠다고 답했다. 삭제 완료 여부는 확인되지 않으며, 리뷰어의 원래 발언은 이유를 묻는 질문이다.

- [ ] ReservationRepository를 인터페이스로 분리한 필요와 이유를 물었다. (설계 질문)
  - 조건: 인터페이스 분리가 불필요하거나 잘못되었다고 단정하지 않았으며, 작성자의 설명은 제공되지 않았다.
