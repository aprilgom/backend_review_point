# FC0403 · 테스트 계층별 검증 범위

[소속 분야: 테스트 대상·검증](../21-test-behavior.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0408](FC0408.md) · [다음 FC: FC0411 →](FC0411.md)

## 검토 질문

- [ ] 단위·슬라이스·통합 테스트가 각각 잡는 실패를 구분하고 같은 검증을 불필요하게 중복하지 않는가?

**직접 작성한 예시**

```java
// 통합: 실제 HTTP부터 DB까지 생성 흐름
assertEquals(201, client.post("/tasks", new CreateTaskRequest("read")).status());
// 단위: 경계값 계산 등 통합 테스트가 다루지 않는 분기
```

**적용 설명:** 각 계층 테스트가 잡는 실패가 다른지 확인한다. 같은 성공 흐름을 여러 층에서 반복할 필요는 없다.

## 구체적인 검토 사례

- [ ] 모든 컨트롤러와 서비스에 통합·슬라이스 테스트를 각각 작성하는 이유와 검증 범위 차이를 묻고, 현재 상황에서는 통합 테스트만 구현하는 방안을 제안했다. (토론)
  - 조건: 작성자는 학습 목적으로 두 종류를 작성했으며 외부 연동 범위가 다르다고 설명했다. 현재 규모에서는 두 종류를 모두 작성하는 이점을 크게 느끼지 못하고 통합 테스트 실행 부담도 작다고 보았다. 리뷰어는 현재 모든 계층에 두 종류를 개별 작성하는 비용이 장점에 비해 크다는 맥락에서, 작성자가 통합 테스트를 선택했다면 앞으로 그것만 구현하자고 제안했고 작성자는 동의했다. 슬라이스 테스트가 일반적으로 불필요하다는 주장이나 실제 테스트 제거 완료를 의미하지 않는다.

- [ ] 통합 테스트라는 명칭의 정답보다 테스트 목적과 필요한 검증 범위를 고민하고, 필요하다면 상태 코드 외에 응답 데이터나 화면 표시까지 검증할 것을 제안했다. (개선 제안)
  - 조건: 참여자는 통합 테스트의 의미가 맥락에 따라 달라 해당 테스트의 분류를 단정하기 어렵다고 했다. 화면 표시까지의 검증은 작성자가 그 범위가 필요하다고 판단하는 경우의 제안이며, RestAssured로 응답 데이터도 참조할 수 있다고 안내했다.

- [ ] 응답 본문이 있는 인수 테스트에서는 상태 코드와 헤더뿐 아니라 본문 값도 검증하자고 제안한다. (개선 제안)
  - 조건: 응답 body가 있는 경우에 적용하는 심화 개선 제안이다. 제시된 노선 생성 테스트는 상태 코드와 Location 헤더를 검증하며, 본문 검증 추가 여부는 확인되지 않는다.
