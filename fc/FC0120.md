# FC0120 · 존재 여부 조회의 양쪽 결과

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0119](FC0119.md) · [다음 FC: FC0122 →](FC0122.md)

## 검토 질문

- [ ] 존재·부재를 모두 테스트해 조회가 항상 같은 참·거짓 값을 반환하는 오류를 잡는가?

**직접 작성한 예시**

```java
assertFalse(bookings.existsForSlot(emptySlot));
bookings.save(newBooking(emptySlot));
assertTrue(bookings.existsForSlot(emptySlot));
```

**적용 설명:** 항상 true인 구현을 잡기 위해 존재·부재를 모두 확인한다.

## 구체적인 검토 사례

- [ ] existReservationByTimeId 함수가 항상 true를 반환하는 것은 아닌지 확인을 요청했다. (설계 질문)
  - 조건: 확인을 요청한 발언이므로 항상 true를 반환하는 결함으로 확정하지 않는다. 제공된 코드에는 해당 함수 본문이 없으며, 작성자는 수정 완료라고만 보고해 원인과 수정 내용은 확인되지 않는다.

- [ ] 다른 저장소에서는 연관 객체의 ID로 파생 쿼리가 동작하는데 findAllByTableGroupId에서는 그렇지 않은 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 OrderTable의 getTableGroupId()가 원인이라고 보고하고 메서드 이름 변경을 고려했다. 리뷰 참여자는 매핑 어노테이션 위치상 field-access가 예상되는데 getter가 영향을 주는 이유는 여전히 의문이라고 했으며, 우선 넘어가고 추가로 알아보겠다고 했다. 실제 원인이나 JPA 접근 방식과의 관계는 확정되지 않았다.

- [ ] 예약대기 삭제 메서드에서 결과를 사용하지 않는 existsById 호출이 필요한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 구현 방식을 변경하면서 삭제하지 못한 호출이라고 설명하고 반영하겠다고 답했다. 실제 삭제 여부는 확인되지 않는다.
