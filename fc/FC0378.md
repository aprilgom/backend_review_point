# FC0378 · 역할에 맞는 서비스 호출

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0375](FC0375.md) · [다음 FC: FC0370 →](FC0370.md)

## 검토 질문

- [ ] 필요한 기능을 실제로 담당하는 서비스에 요청하며 관련 없는 서비스를 경유하지 않는가?

**직접 작성한 예시**

```java
Station departure = stationService.requireStation(departureId);
Station arrival = stationService.requireStation(arrivalId);
```

**적용 설명:** 역 조회를 담당하는 기능에 직접 요청한다. 단순 전달용 서비스 체인이 늘지 않도록 한다.

## 구체적인 검토 사례

- [ ] PathService에서 역을 조회할 때 LineService를 경유하기보다 해당 역할을 맡은 StationService를 활용하자는 제안이다. (개선 제안)
  - 조건: 작성자는 LineService가 이미 StationService에 의존하므로 이를 경유했다고 설명했으나, LineService에 역할이 과도하게 모일 수 있다는 의견을 받아들여 수정했다고 보고했다. 변경 결과는 이 대화만으로 검증되지 않는다.

- [ ] Line의 getLineStationsId와 유사한 서비스 로직을 Line에서 처리하도록 옮기는 방안을 제안했다. (개선 제안)
  - 조건: 작성자는 도메인으로 옮길 수 있다고 판단한 메서드는 이동했다고 보고했다. 다만 findLineStationsWithOutSourceLineStation처럼 단일 노선이 아닌 전체 노선의 구간을 다루는 처리는 도메인에서 처리하기 어렵다고 보아 남겼다고 설명했다. 이 판단에 대한 후속 답변은 없다.

- [ ] LineService에 책임이 많아 파악하기 어렵다는 관점에서 SectionService로 구간 관리 책임을 분리하는 리팩터링을 제안했다. (토론)
  - 조건: 리뷰 참여자는 하나의 컨트롤러가 두 서비스를 사용하거나 컨트롤러도 분리할 수 있다고 제시했다. 작성자는 Line 관리에 Section 관리가 포함된다고 생각해 함께 구현했으나 SectionService와 SectionController를 분리했다고 보고했다. 후속 댓글에서 리뷰 참여자는 구간을 노선의 하위 자원으로 관리하는 기존 방식과 분리 방식 모두 틀리지 않다고 명확히 했으며, 이번 분리로 서비스와 테스트의 맥락을 이해하기 쉬워졌다는 의견을 남겼다. 최초 제안을 철회한 것은 아니다.
