# FC0414 · 데이터 접근 계약의 직접 검증

[소속 분야: 테스트 대상·검증](../21-test-behavior.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0413](FC0413.md) · [다음 FC: FC0412 →](FC0412.md)

## 검토 질문

- [ ] 서비스 테스트 통과만으로 충분하다고 보지 않고 매핑·부재·제약 같은 저장소 동작을 직접 확인하는가?

**직접 작성한 예시**

```java
User saved = dao.insert(new User("reader"));
assertEquals("reader", dao.find(saved.id()).orElseThrow().name());
assertTrue(dao.find(missingId).isEmpty());
```

**적용 설명:** DAO의 매핑·부재 계약을 직접 검증한다. 실제 DB 통합 테스트와 서비스 대역 테스트의 역할을 구분한다.

## 구체적인 검토 사례

- [ ] 실제 DAO를 사용하는 서비스 테스트가 통과해도 DAO 자체의 동작을 충분히 검증했다고 볼 수 없으므로 계층별 단위 테스트가 필요하다는 의견이다. (토론)
  - 조건: 작성자는 실제 DAO를 쓰면 DAO도 자연스럽게 검증할 수 있다는 장점을 제시했다. 리뷰 참여자는 이를 일부 인정하면서도, 잘못된 쿼리가 예외를 발생시키지 않고 서비스 테스트까지 통과할 수 있다는 반례로 검증 범위의 한계를 설명했다.

- [ ] Service 통합 테스트가 DAO 동작까지 검증한다면 별도 DAO 테스트가 중복될 수 있지만, DAO를 모킹한 Service 테스트라면 DAO 실제 동작 테스트도 필요하다는 의견을 제시했다. (조건부 제안)
  - 조건: 작성자는 Service와 DAO에서 같은 검증을 반복하는 것 같다고 질문했다. 리뷰어는 현재 통합 테스트에서는 DAO 테스트를 굳이 추가하지 않아도 된다고 보았으며, 모킹할 때는 Service의 DAO 사용 방식과 DAO 자체 동작을 각각 검증해야 한다고 설명했다.

- [ ] 서비스 테스트에서 실제 DAO까지 함께 검증할지, DAO를 모킹하고 별도 DAO 테스트를 둘지는 테스트 목적에 따라 선택할 문제라는 의견을 제시했다. (토론)
  - 조건: 참여자는 정답이나 필수 변경이 아니라 개인 취향과 팀 규약의 문제라고 밝혔다. 모킹의 구현 결합도와 리팩터링 부담, 서비스 트랜잭션 단위의 실제 협력 검증, EmbeddedDB와 @Transactional을 이용한 구현 편의 및 실행 시간, 향후 JPA 전환에 대한 우려를 자신의 선택 근거로 들었다. 작성자는 모킹의 변경 부담에는 동의했지만, 이번 미션에서는 기존 비즈니스 동작과 예외를 유지하면서 내부를 리팩터링하려 하므로 현재 구조를 유지하겠다고 답했다. DAO 메서드 시그니처가 JPA와 같고 테스트 실패를 동작 변경의 신호로 활용할 수 있다는 것은 작성자의 설명이다.
