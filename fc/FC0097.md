# FC0097 · 복제 지연과 조회 일관성

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0109](FC0109.md) · [다음 FC: FC0110 →](FC0110.md)

## 검토 질문

- [ ] 복제본에 데이터가 없을 때의 대체 조회가 필요한 일관성을 보장하며 오래된 값과 장애도 구분하는가?

**직접 작성한 예시**

```java
Optional<Item> item = replica.find(id);
if (item.isEmpty()) item = primary.find(id);
return item;
```

**적용 설명:** 복제 지연에서 누락을 보완하는 한 방법이다. 이미 존재하지만 오래된 값은 해결하지 못하며 primary 부하와 일관성 요구를 확인한다.

## 구체적인 검토 사례

- [ ] 복제 지연 대응으로 reader 조회 결과가 없을 때 writer를 조회하는 방식을 선택한 이유를 묻는다. (설계 질문)
  - 조건: 작성자는 캐시 서버 등 추가 데이터베이스 없이 현재 가능한 최선이라고 판단했다고 설명했고, 특정 상황에서 트래픽이 writer로 몰릴 가능성도 인정했다. 이 위험은 작성자가 제시한 한계이며 리뷰어가 별도로 확정한 결함은 아니다.

- [ ] getCoupon에 함께 적용된 커스텀 복제 지연 어노테이션과 Redis 캐시의 실행 우선순위 및 동작 전략을 설명해 달라고 요청한다. (설계 질문)
  - 조건: 작성자는 캐시 적중 시 캐시 값을 반환하고, 미적중 시 메서드를 실행해 결과를 캐싱한다고 설명했다. Redis 설정 여부에 따른 저장소 차이도 설명했지만, 커스텀 어노테이션과 캐시 처리 사이의 실행 우선순위는 답변에서 명시적으로 확인되지 않는다.

- [ ] calculate()만 동기화하더라도 public setSum()을 통한 변경이 열려 있으므로, 읽기와 변경이 겹칠 때의 일관성을 고려해 해당 접근도 막는 방안을 제안했다. (개선 제안)
  - 조건: 참여자는 현재 테스트 상황에서는 큰 문제가 없다고 한정했다. getSum() 자체는 읽기 작업이라 안전하다고 설명하면서도 다른 스레드의 setSum() 호출과 겹치는 경우를 우려했다. 이는 참여자의 설명이며 재현된 결함으로 확정하지 않는다.
