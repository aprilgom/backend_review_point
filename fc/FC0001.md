# FC0001 · 요구사항 변화에 대응하는 책임 분리

## 검토 질문

- [ ] 요구사항의 처리 순서를 그대로 옮긴 코드에서 함께 바뀌는 규칙을 구분하고, 변경 범위를 줄일 수 있는가?

**직접 작성한 예시**

```java
Order order = Order.from(request.lines());
order.apply(pricingPolicy);
store.save(order);
```

**적용 설명:** 계산 규칙은 Order·정책에, 저장 순서 조율은 호출자에 둔 예시다. 짧은 메서드 수보다 변경 책임이 나뉘는지 확인한다.

## 구체적인 검토 사례

- [ ] 요구사항을 절차적으로 나열한 듯한 구현으로 요구사항의 복잡함이 코드에 그대로 드러나는 구조를 개선할 수 있을지 검토하자. (개선 제안)
  - 조건: 리뷰 참여자의 설계 평가이며 구체적인 대체 구조는 제시되지 않았다. 미션의 난도를 인정하면서 가능한 범위의 리팩터링을 권했다.

- [ ] 새로운 요구사항이 생길 때 수정해야 하는 코드의 범위를 최소화할 수 있는 구조를 고민하도록 요청한다. (설계 질문)
  - 조건: 작성자는 향후 요구사항에 유연하게 대응하도록 리팩터링하겠다는 생각을 밝혔다. 후속 승인과 긍정적인 평가는 특정 확장성 문제가 해결되었다는 증거로 보지 않는다.

- [ ] 현재 별도 기능이 없는 DiscountCondition 포장이 복잡성만 늘리는 것은 아닌지 묻고, 확장은 필요한 시점에 추가하는 편을 선호한다고 밝혔다. (토론)
  - 조건: 작성자는 현재는 나이만 있지만 향후 할인 조건이 추가될 때 관련 파라미터를 모두 바꾸는 일을 줄이려 미리 객체를 만들었다고 설명했다. 리뷰 참여자는 이 설명 이후에도 필요할 때 추가하는 것이 좋다는 개인 의견을 유지했으며, 원래 관심사를 철회하지 않았다.
