# FC0100 · Session 내부 HashMap에도 동시성 고려가 필요한지, 필요하다면 어떤 상황에서 동시 접근이 발생하는지 질문했다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0103 →](FC0103.md)

- [ ] Session 내부 HashMap에도 동시성 고려가 필요한지, 필요하다면 어떤 상황에서 동시 접근이 발생하는지 질문했다. (설계 질문)
  - 조건: 작성자는 조회와 작성이 같은 작업 단위일 때 동시성을 고려해야 하며, Session의 Map은 객체별 인스턴스 변수라 공유 자원이 아니므로 고려하지 않아도 된다고 답했다. 이는 작성자의 설명이며, 이후 승인만으로 해당 설명의 타당성이 확인된 것은 아니다.

- [ ] 같은 세션에 동시 요청이 들어올 가능성과, SessionManager뿐 아니라 Session 내부 HashMap에도 동시성 처리가 필요한지 질문했다. (토론)
  - 조건: 참여자는 여러 클라이언트의 동일 SessionId 사용이나 한 클라이언트의 동시 변경 요청을 조건으로 제시했다. 작성자는 setAttribute와 getAttribute가 겹치는 경우 등을 들어 현재 Session의 스레드 안전성을 보장하기 어렵다고 판단하고 동시성 컬렉션으로 바꾸겠다고 답했다. 참여자는 그 설명이 자신의 의도와 같으며 자신도 같은 이유로 변경했다고 밝혔다. 변경 계획과 상호 동의는 보존하되 실제 변경 완료나 모든 세션 연산의 안전성까지 확정하지 않는다.

- [ ] Session 내부 속성을 일반 HashMap으로 보관하는 부분에도 동시성 문제가 발생할 가능성을 지적했다. (위험 지적)
  - 조건: 작성자는 동일 Session에 여러 스레드가 접근할 수 있음을 인정하고, 4단계에서 SessionManager의 컬렉션과 함께 스레드 안전성을 고려해 개선하겠다고 답했다. 현재 해결되었다는 근거는 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
sessionAttributes.compute("visits", (key, old) ->
    old == null ? 1 : ((Integer) old) + 1);
```

**적용 설명:** sessionAttributes가 ConcurrentHashMap이라는 전제다. 같은 세션에 여러 요청이 오므로 복합 갱신도 원자적으로 수행한다.
