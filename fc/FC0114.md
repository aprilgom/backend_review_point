# FC0114 · 엔티티 식별과 상태 비교의 구분

## 검토 질문

- [ ] 같은 엔티티를 판단하는 식별 기준과 현재 속성이 같은지를 판단하는 기준을 구분했는가?

**직접 작성한 예시**

```java
record BookingId(long value) {}
boolean sameBooking(Booking a, Booking b) { return a.id().equals(b.id()); }
```

**적용 설명:** 저장되어 ID가 있는 객체라는 전제다. 엔티티 equals를 변경할 때는 미저장 객체·프록시·해시 컬렉션 동작도 별도로 정한다.

## 구체적인 검토 사례

- [ ] Reservation을 비롯한 엔티티의 동등성을 나머지 속성이 아니라 id만으로 판단하도록 다뤄보자고 제안했다. (개선 제안)
  - 조건: 처음에는 같은 주민등록번호를 가진 사람의 시간·이름 변화 사례로 식별 기준을 질문했다. 작성자는 속성이 다른 경우의 동등성과 식별자가 같은 경우의 동일성을 구분해 설명했다. 리뷰 참여자는 식별자를 기준으로 두 사례 모두 같은 대상으로 보자는 취지였다고 명확히 하고, 엔티티를 id로 식별하며 나머지 값의 변화를 추적하는 객체로 설명했다. 작성자의 용어 설명 전체를 기술적 정답으로 확정하거나 실제 구현 변경을 확인한 것은 아니다.

- [ ] id는 같지만 다른 속성이 다른 Reservation을 같은 객체로 볼 것인지 동등성 기준을 질문한다. (설계 질문)
  - 조건: 작성자는 Reservation을 엔티티로 설계했으므로 id로만 식별해야 한다고 답했다. DB에서 id를 생성하면 저장 전 null을 허용해야 하고 equals와 hashCode 구현이 복잡해진다는 판단에 따라, 애플리케이션에서 UUID를 생성하도록 변경했다고 보고했다. 리뷰 참여자는 변경의 사고 과정이 납득된다고 답했지만, 작성자의 동등성 구현 설명 전체나 변경 결과가 기술적으로 검증된 것은 아니다.

- [ ] Reservation의 동등성을 id만으로 비교하는 이유와, id는 같지만 다른 속성이 다른 객체를 동등하게 보아도 되는지 물었다. (설계 질문)
  - 조건: 작성자는 이번에 추가한 코드는 아니며 Theme에도 유사한 구현이 있다고 설명하고, DB의 id 유일성이 보장되므로 나머지 속성 비교가 불필요하다고 답했다. 리뷰 참여자는 id가 같고 다른 속성이 다른 경우에 대한 의견을 다시 요청했으며, 이에 대한 추가 답변이나 결론은 없다.
