# FC0206 · 도메인 모델의 도입 기준

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0205](FC0205.md) · [다음 FC: FC0207 →](FC0207.md)

## 검토 질문

- [ ] 데이터를 모으는 객체가 불변식·계산·행동을 담당할 필요가 있는지 판단했는가?

**직접 작성한 예시**

```java
class Cart {
    private final List<CartLine> lines;
    Money total() { return lines.stream().map(CartLine::subtotal).reduce(Money.ZERO, Money::add); }
}
```

**적용 설명:** 컬렉션과 계산 규칙이 함께 있으면 모델의 역할이 분명해진다. 항상 풍부한 도메인 모델을 강제하는 것은 아니다.

## 구체적인 검토 사례

- [ ] 도메인과 엔티티를 어떻게 정의하며, Cart에 별도 조건이나 로직이 없다는 이유로 도메인 모델을 두지 않는 판단이 적절한지 논의했다. (토론)
  - 조건: 작성자는 검증이나 비즈니스 로직이 있으면 도메인을 두고, 그렇지 않은 Cart는 엔티티를 도메인이자 영속성 계층 DTO로 사용한다고 설명했다. 리뷰 참여자는 DB 없는 콘솔 애플리케이션에서도 Product와 Member만 도메인으로 만들고 Cart는 만들지 않았을지 검토해 보라고 제안했다. Cart 모델의 결함을 확정하거나 특정 구조를 강제한 것은 아니다.

- [ ] Entity와 도메인 객체를 구분하는 기준을 묻고, 도메인 객체도 동일성 판단에 필요한 ID를 가질 수 있다는 견해를 제시했다. (토론)
  - 조건: 작성자는 Entity를 ID와 테이블 매핑 중심, 도메인 객체를 비즈니스 규칙·행위 중심으로 설명하며 현재 객체에는 두 역할이 섞였다고 보았다. 리뷰 참여자는 ID가 영속 이후 동일성을 판단하는 수단이므로 도메인이 보유해도 자연스럽다고 설명하고, Entity와 Domain의 구분을 테이블과 객체지향 사이의 간극과 관련지었다. 작성자는 ID 보유에 동의했지만, 이후 도메인 책임 확대 계획은 작성자의 구상이며 구현 결과는 확인되지 않는다.

- [ ] 도메인 객체와 엔티티를 별도로 나눈 이유와 분리의 장단점을 설명해 달라고 요청한다. (토론)
  - 조건: 작성자 외 참여자는 도메인 객체도 엔티티가 될 수 있는지 물으며, 개인적으로 분리 비용에 비해 큰 이점을 아직 느끼지 못했다고 밝혔다. 작성자는 도메인과 DB 테이블 구조가 달라졌고 DAO 인자를 정리하며 DB 접점 객체를 두기 위해 분리했으며 가독성도 좋아졌다고 설명했다. 엔티티만 수정하면 DAO 변경을 피할 수 있다는 점은 작성자의 기대다. 후속 참여자는 경험에 감사하고 자신도 시도해 보고 싶다고 했으나, 분리의 보편적 우월성을 확정하거나 질문을 철회한 것은 아니다.
