# FC0268 · 질문과 답변을 한 번의 쿼리로 조회해야 하는 실제 성능상 필요가 있는지 확인하고, 조기 최적화로 코드 복잡도를 높이지 않는 방안을 고려하자.

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0266 →](FC0266.md)

- [ ] 질문과 답변을 한 번의 쿼리로 조회해야 하는 실제 성능상 필요가 있는지 확인하고, 조기 최적화로 코드 복잡도를 높이지 않는 방안을 고려하자. (설계 질문)
  - 조건: 객체 관계를 설정해 질문을 조회한 뒤 답변의 삭제 여부를 구분하는 대안을 제시했다. 사용자가 1천 명도 안 되는 상황과 두 번의 쿼리에 대한 성능 우려를 질문했으며, 실제 부하나 성능 측정 결과는 제공되지 않았다.

- [ ] 고정된 두 번의 조회를 횟수만으로 성능 문제로 보지 말고, 반복 쿼리나 대량 데이터 처리와 구분해 단일 쿼리 최적화의 필요성을 판단하도록 보완한다. (토론)
  - 조건: 작성자는 데이터 모수가 작아 두 번의 쿼리가 미치는 영향이 미미하다고 판단했다고 설명했다. 리뷰 참여자는 현재처럼 고정된 두 번의 쿼리는 성능 이슈로 보기 어렵다는 의견을 제시하면서 N+1 같은 반복 쿼리나 대량 데이터 조인과 구분했다. 단일 SQL로 합칠 때의 복잡성과 향후 요구사항 확장 비용도 언급했으며, 실제 성능 측정 결과는 제공되지 않았다.

- [ ] 검증용 DB 조회 횟수만을 이유로 과도하게 최적화하기보다는 쿼리 비용과 개선 가능한 문제를 구분하자는 의견이다. (의견)
  - 조건: 작성자는 사전 검증으로 쿼리가 늘어나는 비효율을 우려했다. 리뷰 참여자는 인덱스를 잘 사용하는 SELECT라면 추가 조회를 큰 비용으로 보지 않는다는 개인적 견해를 밝혔고, 커넥션 풀이나 서버 비용을 늘리는 선택도 언급했다. 다만 SELECT 하나에 1초가 걸리는 경우는 문제로 보며, 애플리케이션에서 고칠 수 있는 N+1과 가능한 Bulk 처리는 개선해야 한다고 구분했다. 실제 성능 측정 결과가 제시된 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Question question = questions.get(id);
List<Answer> answers = answersForQuestion.find(id);
```

**적용 설명:** 단순한 두 번 조회로 시작하는 대안이다. 지연·쿼리 수·결과 크기를 측정해 조인 필요성을 판단한다.
