# FC0107 · 비동기 전환의 목적과 실패 처리

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0102](FC0102.md)

## 검토 질문

- [ ] 동기 작업을 비동기로 옮긴 이유가 명확하고 완료·실패·자원 제한·경쟁 조건을 처리하는가?

**직접 작성한 예시**

```java
CompletableFuture<Void> renewal = CompletableFuture.runAsync(
    () -> cache.extendTtl(key, ttl), ioExecutor);
renewal.exceptionally(error -> { recordRenewalFailure(error); return null; });
```

**적용 설명:** 가상 동기 캐시 호출을 별도 실행기로 옮긴 예다. 실패 관측·실행기 제한·갱신 전 만료 경쟁을 검토하며 API 이름만으로 비동기를 판단하지 않는다.

## 구체적인 검토 사례

- [ ] RedisTemplate의 내부 호출이 동기인지 비동기인지, 그리고 캐시 TTL 연장 메서드에 비동기를 사용한 이유가 무엇인지 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 RedisTemplate이 Lettuce 클라이언트 기반이라는 자신의 이해를 전제로 질문했다. 작성자 답변이 없어 내부 실행 방식이나 @Async 선택의 타당성은 확인되지 않으며, 비동기 사용을 결함으로 단정하지 않는다.

- [ ] @Async의 동작 방식과 현재 프로그램에서 비동기 처리가 필요한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 예약 삭제와 대기 1순위의 예약 전환을 독립적으로 실행하려는 의도라고 설명했다. 후속 발언자는 두 작업을 반드시 같은 트랜잭션으로 묶을 필요가 없다는 판단으로 이해했고, 다른 사람의 대기 처리 실패로 본인의 예약 취소까지 실패하는 것은 사용자에게 어색할 수 있다고 공감했다. 비동기 도입 자체를 오류라고 확정한 대화는 아니다.

- [ ] 스트림 최종 연산에서 외부 객체를 변경하는 접근은 비동기 동작 시 문제가 될 수 있으므로 가급적 피하자고 제안한다. (개선 제안)
  - 조건: 리뷰 참여자는 중요한 부분은 아니라며 비동기 동작을 위험 조건으로 들었다. 현재 코드에서 실제 비동기 실행이나 경합이 발생한다는 근거는 없으며, 작성자는 해당 부분을 for문으로 바꿨다고 보고했다.
