# FC0060 · 요청 인자 해석 대상의 제한

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0067](FC0067.md) · [다음 FC: FC0069 →](FC0069.md)

## 검토 질문

- [ ] 인자의 타입뿐 아니라 명시적 표식과 맥락을 확인해 필요한 파라미터에만 인증 정보 등을 주입하는가?

**직접 작성한 예시**

```java
boolean supports(Parameter parameter) {
    return parameter.getType() == Actor.class
        && parameter.isAnnotationPresent(CurrentActor.class);
}
```

**적용 설명:** 자체 인자 해석기와 런타임 애너테이션을 가정한다. 타입만 같은 일반 파라미터에 인증 정보를 잘못 주입하지 않는다.

## 구체적인 검토 사례

**혼합·경계:** 인자 해석·인증 정보 주입 원리와 Spring 확장 API 사례가 겹침.

- [ ] LoginMember 타입만으로 인자 해석 대상을 정하지 말고, hasParameterAnnotation()을 활용해 특정 조건을 만족하는 파라미터에만 로그인 정보를 제공하도록 제안했다. (개선 제안)
  - 조건: 작성자는 @CurrentLoginMember 어노테이션을 추가해 해당 어노테이션이 붙은 파라미터에만 로그인 정보를 주입하도록 구현했다고 보고했다. 요청 처리 비용 감소는 작성자가 예상한 효과이며 검증 결과는 제시되지 않았다.

- [ ] 외부에서 사용하지 않는 ViewName 인자 생성자를 공개하면 생성자 선택을 어렵게 하고 내부 표현을 노출할 수 있으므로, 공개 생성자 구성을 재검토하자고 제안했다. (토론)
  - 조건: 작성자는 ViewName을 받는 주 생성자로 객체 간 협력을 드러내고 String 부 생성자로 편의성을 제공하려는 의도라고 반론했다. 리뷰어는 그 의도를 이해하면서도 현재 호출부는 모두 String 생성자만 사용하므로 ViewName을 몰라도 되며, 협력을 드러내는 것이 내부 사정 노출일 수도 있다고 재차 설명했다. 다음 미션에서 캡슐화 관점으로 함께 고민하자는 수준으로 완화했으며 지적을 철회하지는 않았다.

- [ ] WinnerCarDto 생성자의 우승자 입력을 String 대신 CarDto로 받아도 괜찮겠다고 제안한다. (개선 제안)
  - 조건: 코드상 우승자 입력은 List<String>이다. 리뷰 참여자는 CarDto를 사용하는 대안을 제시했으며, 현재 타입이 잘못되었다고 확정하거나 변경 결과를 보고하지는 않았다.
