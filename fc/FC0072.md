# FC0072 · 전체 교체와 부분 수정의 구분

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0071](FC0071.md) · [다음 FC: FC0062 →](FC0062.md)

## 검토 질문

- [ ] 수정 API가 전체 교체인지 부분 수정인지 명확하고 생략 필드와 null의 의미를 구분하는가?

**직접 작성한 예시**

```http
PATCH /items/17 HTTP/1.1
Content-Type: application/merge-patch+json

{"name":"updated"}
```

**적용 설명:** JSON Merge Patch 계약 예시다. 생략 필드와 null의 의미를 구분하고 PUT 전체 교체 계약과 혼용하지 않는다.

## 구체적인 검토 사례

- [ ] 상품 수정 API에서 PUT과 PATCH의 차이를 이해하고 PATCH 사용도 고려했는지 묻는다. (설계 질문)
  - 조건: 작성자는 PATCH를 처음 알게 되었다며 두 메서드의 의미를 조사한 설명을 제시하고, 수정 목적에 PATCH가 더 적절하다고 판단해 변경했다고 보고했다. 리뷰어가 PUT 사용을 확정적인 결함으로 지적한 것은 아니며, 작성자의 메서드 해석이나 변경의 타당성이 후속 검증된 것은 아니다.

- [ ] 상품 수정에 PATCH를 선택한 이유를 묻고, 모든 상품 정보를 받아 수정하는 현재 API에는 PUT이 더 적절하다는 의견을 제시했다. (토론)
  - 조건: 처음에는 PATCH와 PUT의 차이를 학습하도록 제안했다. 작성자가 전체 정보를 보내므로 PUT이 맞는지 묻자, 참여자는 PUT은 완전 변경, PATCH는 부분 변경이라는 설명과 함께 현재 API에는 PUT이 더 적절하다고 답했다. 실제 메서드 변경 완료 여부는 이 대화만으로 확인되지 않는다.

- [ ] 상품 수정 API의 HTTP 메서드 선택과 관련하여 POST, PUT, PATCH의 차이를 질문했다. (설계 질문)
  - 조건: 작성자는 각 메서드의 의미와 멱등성에 대한 자신의 이해를 설명하고, 수정 시 변경되지 않은 데이터도 모두 전송하므로 PATCH보다 PUT이 맞다고 판단해 변경했다고 보고했다. 이 설명의 기술적 타당성이나 실제 변경 결과를 리뷰 참여자가 확인한 내용은 없다.
