# FC0424 · 생성한 데이터를 지울 수 없어 테스트 사이에 의존이 생긴다는 문제에 대해 @Sql로 테스트별 필요한 SQL을 실행하는 방안을 제안한다.

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0421 →](FC0421.md)

**혼합·경계:** @Sql 외에 테스트 데이터 준비·격리·파일 관리 사례가 포함됨.

- [ ] 생성한 데이터를 지울 수 없어 테스트 사이에 의존이 생긴다는 문제에 대해 @Sql로 테스트별 필요한 SQL을 실행하는 방안을 제안한다. (개선 제안)
  - 조건: 데이터 삭제 메서드가 없어 의존성이 생겼다는 내용은 리뷰 참여자가 인용한 작성자의 설명이다. 리뷰 참여자는 @Sql 활용 가능성을 제안했으며 구체적인 SQL이나 격리 문제가 해결되었는지는 확인되지 않는다.

- [ ] 테스트 준비 데이터를 SQL 파일로 구성하는 방식이 테스트 가독성에 좋은 선택인지 재검토해보자는 제안이다. (개선 제안)
  - 조건: 작성자 외 참여자 verus-j가 가독성 관점에서 고민을 권했으며, SQL 파일 사용을 결함으로 단정하거나 특정 대안으로 교체하라고 요구하지는 않았다. 이 단위에는 해당 제안에 대한 작성자의 설명이나 변경 보고가 없으며, 이후 승인·머지 안내만으로 반영 여부를 확인할 수 없다.

- [ ] 실제 운영에서는 data.sql을 사용하지 않을 가능성을 고려해, 중복 파일이 생기더라도 테스트 쪽에 별도의 data.sql을 두도록 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 테스트 측 data.sql의 오버라이드 가능 여부는 모른다고 명시했다. 작성자는 실험 결과 오버라이드가 가능했고 수정했다고 보고했으며, 해당 동작은 이 대화에서 독립적으로 검증된 사실은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
-- 테스트 전용 DB에서 실행할 준비 SQL
INSERT INTO category(id, name) VALUES (10, 'fixture');
```

**적용 설명:** SQL 준비 파일을 명시적으로 실행하는 예시다. 정리·트랜잭션·병렬 실행 정책과 함께 사용하며 운영 DB에서는 실행하지 않는다.
