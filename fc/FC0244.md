# FC0244 · 오류 처리에 ResponseErrorHandler를 채택한 이유와 검토한 대안을 질문했다.

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0246](FC0246.md) · [다음 FC: FC0247 →](FC0247.md)

- [ ] 오류 처리에 ResponseErrorHandler를 채택한 이유와 검토한 대안을 질문했다. (설계 질문)
  - 조건: 작성자는 try-catch보다 onStatus 체이닝의 가독성이 좋다고 판단했으며, onStatus에 조건과 처리 로직을 람다로 전달하는 방식보다 현재 방식이 읽기 좋다고 설명했다. 특정 방식의 결함이나 변경 요구가 확정된 대화는 아니다.

- [ ] 동일한 요청에 대해 오류 응답이 매번 달라지는 비일관성을 확인한다. (문제 보고)
  - 조건: 리뷰 참여자는 첨부 이미지와 함께 응답이 달라진다고 보고했다. 작성자는 FieldError 반환 순서가 JVM 리플렉션 순서에 의존하여 메시지 순서가 달라졌다고 설명하고, 필드명 기준 정렬을 추가했다고 보고했다. 원인 설명과 변경 결과는 작성자의 주장으로 보존하며 첨부 이미지의 세부 내용은 추정하지 않는다.

- [ ] Bearer 토큰 검증 실패 응답에는 BAD_REQUEST보다 UNAUTHORIZED가 더 적절하다는 제안이다. (개선 제안)
  - 조건: 토큰이 유효하지 않은 경우의 HTTP 상태 코드에 대한 의견이다. 작성자도 인증 실패이므로 UNAUTHORIZED가 더 적절하다고 동의했지만, 실제 변경 여부는 답변에서 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
RemoteReply reply = transport.send(request);
if (reply.status() >= 400) throw remoteErrors.translate(reply);
return decode(reply.body());
```

**적용 설명:** 외부 오류 해석을 한 경계에 모은 대안이다. 상태별 재시도·파싱 실패·민감 정보 제거를 따로 정의한다.
