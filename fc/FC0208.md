# FC0208 · 금액의 정밀도와 단위

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0209](FC0209.md) · [다음 FC: FC0211 →](FC0211.md)

## 검토 질문

- [ ] 금액 타입이 통화·소수 자리·반올림·범위를 표현하며 부동소수점 오차를 피하는가?

**직접 작성한 예시**

```java
BigDecimal price = new BigDecimal("12.35");
BigDecimal total = price.multiply(BigDecimal.valueOf(quantity));
```

**적용 설명:** 십진 금액을 문자열로 생성한다. 정수 최소 화폐 단위도 대안이며 통화·소수 자리·반올림 규칙을 정한다.

## 구체적인 검토 사례

- [ ] 상품 가격을 int로 표현하는 대신 BigDecimal 사용을 고려하자고 제안했다. (개선 제안)
  - 조건: 리뷰어는 금액에 BigDecimal이 거의 필수라는 개인 견해를 밝히고, 달러 등 소수 단위가 필요한 통화로 확장할 경우와 소수점 연산 오차 가능성을 이유로 들었다. 작성자는 이에 동의하고 반영 의사를 밝혔지만, 필수성의 기술적 검증이나 실제 반영 완료를 의미하지는 않는다.

- [ ] 여러 결제 정보 중 paymentKey와 amount를 저장 대상으로 선택한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 amount를 클라이언트에 자주 전달하고 paymentKey로 조회와 결제 취소를 수행하기 위해 저장했으며, 다른 정보는 paymentKey로 조회할 수 있다고 판단했다고 설명했다. 리뷰어는 amount를 자주 전달해야 한다는 근거를 중요하게 평가했다. 다른 정보를 저장하지 않아도 된다는 기술적 타당성까지 확인된 것은 아니다.

- [ ] 결제 금액에 사용한 BigDecimal이 주로 어떤 상황에 적합한 타입인지 질문했다. (설계 질문)
  - 조건: 작성자는 큰 숫자도 정확하게 표현하며 돈을 다루는 로직에 쓰는 타입으로 알고 있고, 현재 규모와 별개로 실제 결제의 정확성을 위해 선택했다고 설명했다. 리뷰 참여자는 금전 관련 값을 BigDecimal로 더 정확하게 표현하는 선택을 지지했다. 타입 변경 요구나 현재 구현의 정밀도 결함을 보고한 대화는 아니다.
