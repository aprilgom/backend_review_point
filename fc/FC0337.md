# FC0337 · 요청 DTO의 방향과 목적

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0318](FC0318.md) · [다음 FC: FC0320 →](FC0320.md)

## 검토 질문

- [ ] 타입 이름에서 요청·응답 방향과 생성·수정 등의 목적을 구분할 수 있는가?

**직접 작성한 예시**

```java
record CreateTaskRequest(String title, LocalDate dueDate) {}
```

**적용 설명:** 요청 방향과 사용 목적을 이름에 포함한다. 수정 요청과 계약이 같다면 과도한 타입 분리는 피한다.

## 구체적인 검토 사례

- [ ] 요청용 DTO라면 Request를 이름에 포함하고, 필요하면 생성 등 구체적인 용도도 드러내도록 명명하자고 제안했다. (개선 제안)
  - 조건: 향후 Response DTO와 혼동하지 않도록 하려는 제안이다. ItemCreateRequest처럼 용도를 추가하는 방식은 선택적인 개선안으로 제시했다.

- [ ] Request나 Response라는 이름만으로 DTO임을 알 수 있으므로 클래스 이름에서 Dto를 빼는 것을 제안했다. (개선 제안)
  - 조건: 일반적인 명명 관행에 근거한 제안이며 필수 규칙으로 제시되지는 않았다. 작성자는 반영했다고 답했다.

- [ ] DTO 이름에 Dto와 Request·Response 방식을 혼용하는 이유를 확인하고, 명명 기준을 일관되게 선택하도록 제안했다. (개선 제안)
  - 조건: 작성자는 역할을 드러내기 위해 Param·Condition 명명 방식을 참고하여 변경했다고 답했다. 리뷰어는 이 변경도 Param·Condition과 Request·Response의 혼용이므로 최초의 일관성 관심사가 해소된 것은 아니라는 취지로, 다음 단계에서 더 고민하도록 요청했다.
