# FC0013 · 생성자 초기화 경로의 통합

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0005](FC0005.md) · [다음 FC: FC0007 →](FC0007.md)

## 검토 질문

- [ ] 여러 생성자가 같은 검증과 초기화를 수행하도록 위임 관계를 정리할 수 있는가?

**직접 작성한 예시**

```java
Counter() { this(0); }
Counter(int initial) {
    if (initial < 0) throw new IllegalArgumentException();
    this.value = initial;
}
```

**적용 설명:** 생성자 내부 조각이다. 검증과 초기화를 한 곳에 모으면 생성 경로별 규칙 차이를 줄일 수 있다.

## 구체적인 검토 사례

- [ ] 기본 생성자에서 다른 생성자를 호출해 변수 초기화를 한 생성자로 모으고 그 장점을 생각해 보자고 제안했다. (개선 제안)
  - 조건: 작성자는 공통 변경사항을 한곳에서 관리하고 중복 코드를 줄일 수 있다고 설명하며 수정했다고 보고했다. 실제 변경 결과는 대화만으로 확인되지 않는다.

- [ ] 생성자를 단순히 감싸는 정적 팩토리를 도입한 이유를 검토하고, 장점을 활용할 상황이나 코드 전반의 명확하고 일관된 의도를 기준으로 생성 방식을 선택하자. (토론)
  - 조건: 작성자는 매개변수 조합이 달라 정적 팩토리 오버로딩이 더 낫겠다고 막연히 판단했으며 이후 빌더를 적용했다고 설명했다. 리뷰어는 정적 팩토리 사용 자체를 금지하지 않았고, 단순 프로퍼티로 생성할 때는 생성자, 내부 처리 로직이 있을 때는 정적 팩토리를 쓴다는 자신의 기준을 예시로 들었다. 이 기준을 보편 규칙이나 빌더 적용에 대한 승인으로 해석하지 않는다.

- [ ] PathResponse처럼 생성자가 여러 개로 늘어나는 구조에서는 팩터리 메서드 사용을 검토하자는 제안이다. (개선 제안)
  - 조건: 작성자는 실제로 하나의 생성자만 사용하여 나머지는 삭제했다고 보고하고, 이름 부여 외의 팩터리 메서드 장점과 다수 생성자의 단점을 질문했다. 리뷰 참여자는 이펙티브 자바의 관련 아이템을 읽어보도록 권했으며, 구체적인 장단점에 대한 답변은 본문에 없다.
