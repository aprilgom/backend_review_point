# FC0102 · 요청 처리 단계의 실행 순서

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0105](FC0105.md) · [다음 FC: FC0107 →](FC0107.md)

## 검토 질문

- [ ] 전처리·인자 해석·핸들러·후처리의 실제 순서를 관측하고 각 단계의 전제를 검증했는가?

**직접 작성한 예시**

```java
trace.add("interceptor.before");
Actor actor = actorResolver.resolve(request);
trace.add("argument.resolved");
Reply reply = handler.handle(actor);
trace.add("handler.done");
```

**적용 설명:** 자체 파이프라인에서 순서를 명시한 예시다. 사용하는 프레임워크의 실제 순서를 추측하지 말고 관측·테스트로 확인한다.

## 구체적인 검토 사례

- [ ] ArgumentResolver와 Interceptor를 사용할 때 각각 요청이 처리되는 순서를 질문한다. (설계 질문)
  - 조건: 작성자는 Interceptor가 핸들러 호출 전후에 요청·응답을 처리하고 ArgumentResolver가 핸들러 호출 시 인자를 변환한다고 설명했다. 다만 두 구성요소를 포함한 구체적인 전체 실행 순서에 대한 후속 확인은 없다. 비동기 경합 지적이 아니라 요청 처리 순서에 관한 질문이다.

- [ ] SELECT FOR UPDATE가 락 획득에만 사용되는지, 조회한 데이터를 애플리케이션 로직에서는 사용할 필요가 없는지 묻는 질문이다. (설계 질문)
  - 조건: 작성자는 reservation_slot이 락을 위한 우회용 테이블이어서 그 행의 ID는 비즈니스 의미가 없고, 현재는 조회 결과를 사용하지 않고 락 획득에만 활용한다고 설명했다. 조회 결과를 사용하지 않는 것을 결함으로 확정한 발언은 아니다.

- [ ] LazyHolder 내부 클래스를 둔 의도와 getInstance 및 init의 차이를 묻고, getInstance에서도 init을 호출하여 데이터베이스가 초기화되는 것 아니냐는 의문을 제기한다. (설계 질문)
  - 조건: 참여자는 두 메서드에 차이가 없어 보인다고 해석했다. 작성자는 동시성 문제를 고려한 싱글턴 구현으로 LazyHolder를 의도적으로 사용했다고 설명하고, init은 private으로 바꿔야 하는데 누락했다고 밝혔다. 초기화 동작에 대한 참여자의 해석을 확정된 결함으로 취급하지 않으며, 접근 제한 변경 여부도 확인되지 않는다.
