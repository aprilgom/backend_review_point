# FC0202 · 검증 가능한 요구사항 표현

## 검토 질문

- [ ] 입력·성공 결과·실패 조건을 테스트할 수 있을 만큼 구체적으로 정의했는가?

**직접 작성한 예시**

```text
입력: 제목은 앞뒤 공백 제거 후 1~80자
성공: 생성된 식별자 반환
실패: 빈 제목이면 저장하지 않고 입력 오류 반환
```

**적용 설명:** 입력·결과·실패를 검증 가능한 요구로 적는 예시다.

## 구체적인 검토 사례

- [ ] 구현할 사항을 더 잘 정리할 수 있도록 README의 요구사항을 명확하게 작성하자고 제안했다. (개선 제안)
  - 조건: 작성자는 수정했다고 보고했으며, 변경된 요구사항의 구체적인 내용은 이 대화에서 확인되지 않는다.

- [ ] README의 기능 요구 사항 목록을 더 상세하게 작성할 것을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 레벨 1 때보다 기능 목록이 단순해 보인다고 언급했다. 작성자는 1·2단계가 주어진 API 스펙 구현 위주라 현재 수준으로 작성했으며, 3단계에서는 더 상세히 작성할 수 있을 것이라고 답했다. 현재 문서의 수정 완료를 보고한 것은 아니다.

- [ ] README 요구사항 목록에서 완료한 항목을 체크해 실제 진행 상태를 반영하도록 제안했다. (개선 제안)
  - 조건: 작성자는 체크를 빠뜨렸다며 완료 표시를 했다고 답했다. 체크 표시 변경 보고가 해당 요구사항의 실제 구현 완료를 입증하는 것은 아니다.
