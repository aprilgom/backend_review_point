# FC0407 · 의도한 이유로 예외가 발생했는지 확인하도록 테스트에서도 예외 메시지를 검증하자고 제안했다.

[소속 분야: 테스트 대상·검증](../21-test-behavior.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0399](FC0399.md) · [다음 FC: FC0410 →](FC0410.md)

- [ ] 의도한 이유로 예외가 발생했는지 확인하도록 테스트에서도 예외 메시지를 검증하자고 제안했다. (개선 제안)
  - 조건: 예외 메시지 설정과 함께 제시된 테스트 검증 제안이다. 작성자는 메시지 또는 커스텀 예외 도입 계획만 밝혔으며, 테스트 검증을 추가했다는 보고는 없다. 리뷰 참여자는 다음 단계에서 확인하겠다고 했다.

- [ ] 예외 테스트 전반에서 예외 타입뿐 아니라 예외 메시지도 함께 검증하자고 제안했다. (개선 제안)
  - 조건: HandlerAdaptorRegistryTest에 남긴 댓글이지만 제안 범위는 테스트 전반이다. 반영 여부는 제시되지 않았다.

- [ ] 다건 결과 예외 테스트가 하위 타입인 EmptyResultDataAccessException까지 허용하므로 정확한 예외 타입이나 actualSize를 검증하자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 EmptyResultDataAccessException이 IncorrectResultSizeDataAccessException을 상속하므로, 2건 이상에서 잘못된 예외를 던져도 현재 isInstanceOf 검증이 통과할 수 있다고 설명했다. 대안으로 isExactlyInstanceOf 또는 actualSize 확인을 제시했다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
InvalidQuantity error = assertThrows(InvalidQuantity.class, () -> changeQuantity(-1));
assertEquals("QUANTITY_MUST_BE_POSITIVE", error.code());
```

**적용 설명:** 다른 이유의 예외로 우연히 통과하지 않도록 확인한다. 문구가 자주 바뀌면 안정된 오류 코드가 더 적합하다.
