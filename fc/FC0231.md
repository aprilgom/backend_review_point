# FC0231 · public인 addMenuProduct로 외부에서 상품을 추가할 때 가격 제약조건을 별도로 검증해야 하지 않는지 질문했다.

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0230](FC0230.md) · [다음 FC: FC0237 →](FC0237.md)

- [ ] public인 addMenuProduct로 외부에서 상품을 추가할 때 가격 제약조건을 별도로 검증해야 하지 않는지 질문했다. (설계 질문)
  - 조건: 작성자는 처음에 isOverPrice로 검증하며 메서드명을 checkPriceCondition으로 바꿨다고 답했다. 리뷰 참여자는 생성 시 검증이 아니라 공개 추가 메서드를 통한 임의 변경이 관심사라고 명확히 했다. 작성자는 이후 addMenuProduct가 사용되지 않아 삭제했다고 보고했으며, 실제 변경 결과는 별도로 확인되지 않았다.

- [ ] 주문 항목 수와 메뉴 ID 조회 개수를 비교하던 검증이 현재 어디에 있는지, 제거했다면 의도와 이유가 무엇인지 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 자신이 찾지 못했을 가능성을 열어 두었다. 작성자는 해당 로직을 존재하지 않는 메뉴의 주문 방지로 재해석하여 findById 검증으로 대체했다고 설명했다. 이후 직접 쿼리를 실행해 중복 ID가 조회 개수에 중복 반영되지 않음을 확인했고, 메뉴 중복 금지로 다시 해석하여 검증과 테스트를 추가했다고 보고했다. 이 해석과 변경 결과는 작성자의 설명이다.

- [ ] 메뉴는 메뉴 그룹에 속할 수 있다는 표현보다 반드시 하나의 메뉴 그룹에 속해야 한다는 제약이 필요하다고 제안했다. (개선 제안)
  - 조건: 요구사항 문서의 메뉴 소속 제약에 대한 제안이다. 작성자는 추가했다고 보고했으며, 실행 코드의 검증 로직 변경 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
void addProduct(Product product) {
    requirePriceWithinLimit(product.price());
    products.add(product);
}
```

**적용 설명:** 공개 변경 메서드도 제약을 보장해야 한다. 외부에서 컬렉션을 직접 수정할 수 없도록 한다.
