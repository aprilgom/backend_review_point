# FC0204 · 주문 테이블에 updated_at이 필요한지 확인하고, 수정 가능한 데이터와 수정하지 않는 이력 데이터를 구분해 판단하도록 논의했다.

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0207](FC0207.md) · [다음 FC: FC0209 →](FC0209.md)

- [ ] 주문 테이블에 updated_at이 필요한지 확인하고, 수정 가능한 데이터와 수정하지 않는 이력 데이터를 구분해 판단하도록 논의했다. (토론)
  - 조건: 작성자는 shopping_order와 ordered_item이 주문 당시 정보를 보존하고 취소는 DELETE로 처리하므로 수정되지 않는다고 설명했다. 리뷰어는 이력용 테이블이라면 updated_at이 없어도 된다고 수용하고, 수정될 일이 있는 테이블에는 넣는다는 기준을 제시했다. 누락 결함으로 확정하거나 지적의 명시적 철회로 해석하지 않는다.

- [ ] 쿼리가 지나치게 복잡해지면 쿼리 자체보다 현재 기능에 맞지 않는 데이터 구조가 원인인지 검토할 수 있다는 의견을 제시했다. (의견)
  - 조건: 리뷰어 개인의 설계 관점으로 제시되었다. 현재 데이터 구조에 결함이 있다고 확정하거나 구체적인 구조 변경을 요구한 것은 아니다.

- [ ] 동일한 파라미터 키가 여러 번 전달되면 값이 덮어써지므로 Map<String, List<String>>처럼 복수 값을 보존하는 구조로 확장할 수 있다고 제안했다. (개선 제안)
  - 조건: 같은 키가 반복되는 요청을 고려한 확장 제안이며, 복수 값 지원이 현재 요구사항이라고 확정한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record AuditEntry(Instant occurredAt, String action) {}
```

**적용 설명:** 변경하지 않는 이력이라면 수정 시각이 필요한지 검토한다. 정정 이력을 별도 기록하는 정책도 고려한다.
