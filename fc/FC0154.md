# FC0154 · 서비스 인터페이스의 도입 기준

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0152](FC0152.md) · [다음 FC: FC0164 →](FC0164.md)

## 검토 질문

- [ ] 구현 수만이 아니라 계약 분리·대체·경계의 필요를 기준으로 서비스 인터페이스를 도입하는가?

**직접 작성한 예시**

```java
final class PriceService {
    Money price(Basket basket) { return basket.subtotal(); }
}
```

**적용 설명:** 교체 가능한 계약이 아직 필요하지 않다면 구체 클래스만으로 시작할 수 있다. 구현체 수만으로 인터페이스 필요성을 결정하지 않는다.

## 구체적인 검토 사례

- [ ] 구현체가 하나인 서비스에도 인터페이스를 두는 기준과 인터페이스를 사용하기 적절한 시점을 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 인터페이스 의존 원칙이 모든 클래스의 의존성을 인터페이스로 바꿔야 한다는 뜻인지 되물었다. 인터페이스를 제거하라는 확정적 요구나 해당 설계가 결함이라는 판정은 아니다.

- [ ] 메서드 내부에서 구체 구현체를 직접 참조하는 상황에서 인터페이스를 분리한 이유를 묻고, 인터페이스의 장점을 활용하는 구조를 고민하도록 제안했다. (토론)
  - 조건: PathService가 DijkstraPathCalculator.from(lines)를 직접 사용하는 맥락이다. 리뷰 참여자는 현재 구조에서 인터페이스 분리의 장점이 드러나지 않는 것 같다고 했으며, 특정 주입 방식이나 변경안을 확정하지 않았다.

- [ ] HandlerExecution 인터페이스 타입을 사용할 수 있는데도 구체 구현체 타입을 선택한 이유를 물었다. (설계 질문)
  - 조건: 참여자는 이를 반환 타입에 관한 질문으로 표현했고, 작성자는 더 구체적인 반환 타입을 선호하기 때문이라고 답했다. 제공된 인라인 코드에는 지역 변수 선언이 보이므로, 질문에서 말한 반환 타입과 코드 위치 사이에는 차이가 있다. 인터페이스 사용을 강제하거나 구체 타입 선택을 결함으로 확정한 발언은 없다.
