# FC0363 · 서비스 경계의 입력·출력 모델

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0360](FC0360.md) · [다음 FC: FC0356 →](FC0356.md)

## 검토 질문

- [ ] 서비스가 요청·응답 DTO를 직접 사용할지 별도 계약을 둘지 결합도와 변환 비용으로 판단했는가?

**직접 작성한 예시**

```java
CreateTaskResult result = tasks.create(new CreateTaskCommand(input.title()));
return new TaskReply(result.id(), result.title());
```

**적용 설명:** 서비스용 계약과 HTTP 응답 계약을 나눈 대안이다. 작은 앱에서 DTO 계층을 늘리는 비용도 비교한다.

## 구체적인 검토 사례

- [ ] 컨트롤러에서 도메인과 DTO를 변환하는 대신 서비스가 요청 DTO를 받고 응답 DTO를 반환하는 구조를 검토한다. (토론)
  - 조건: 작성자는 뷰 통신 책임, 여러 컨트롤러의 서비스 재사용, 서비스 비대화 및 의존 방향 우려를 이유로 현재 구조를 택했고, 컨트롤러 비대화와 도메인 노출이라는 단점도 인정했다. 리뷰 참여자는 현재 구조를 유지해도 된다고 했으며, 해당 서비스들이 애플리케이션 서비스에 가까워 DTO를 반환해도 무방하다는 입장을 설명했다. 제안 자체를 철회한 것은 아니다.

- [ ] 서비스는 도메인을 반환하고 컨트롤러가 응답 DTO로 변환하도록 책임을 배치하는 방안에 대해 의견을 물었다. (토론)
  - 조건: 리뷰 참여자는 응답 변경이 컨트롤러와 서비스 모두에 영향을 준다는 점에서 컨트롤러 변환을 선호했다. 작성자는 요청 DTO도 이미 서비스에 전달되고 있고 도메인의 외부 변경 위험을 줄이고 싶으며 현재 서비스 간 재사용이 필요하지 않다는 이유로 서비스에서 응답 DTO를 만드는 방식을 옹호했다. 후속 답변은 양쪽의 장단점을 인정했으며 변경을 확정하거나 최초 관심사를 철회한 것은 아니다.

- [ ] 서비스에서 응답 DTO를 직접 반환하는 방식과 도메인을 반환해 컨트롤러에서 DTO로 변환하는 방식의 장단점과 계층별 변환 책임을 검토하자는 논의다. (토론)
  - 조건: 작성자는 도메인 변경이 API 반환값에 미치는 영향을 줄이려고 DTO를 사용했으며, 계층마다 동일한 값을 다시 감싸는 DTO를 추가하기보다는 필요할 때 확장하겠다고 설명했다. 리뷰 참여자는 그 이유가 명확하므로 현재 구조를 유지해도 좋다고 했고, 서비스가 도메인을 반환하는 대안의 장단점도 생각해 보도록 권했다. 기존 지적을 철회한 것은 아니다.
