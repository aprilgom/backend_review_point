# FC0458 · 도메인과 저장 모델의 null 의미

[소속 분야: 타입·타입 테스트](../24-type-safety.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0459](FC0459.md) · [다음 FC: FC0465 →](FC0465.md)

## 검토 질문

- [ ] 기본형·래퍼 차이가 없음과 0의 업무 의미를 보존하며 변환 과정에서 사라지지 않는가?

**직접 작성한 예시**

```java
int fixedDiscount = 100;
Integer optionalDiscount = null;
```

**적용 설명:** 없음과 0의 의미가 다를 때만 래퍼의 null을 사용한다. 도메인·엔티티 변환에서 의미가 사라지지 않게 한다.

## 구체적인 검토 사례

- [ ] CouponType의 할인액은 int인데 CouponTypeEntity에서는 Integer로 설정한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 변경을 깜빡한 것 같다고 답하고 수정했다고 보고했다. 어느 타입으로 통일했는지와 실제 변경 내용은 제공되지 않았다.

- [ ] 패키지명을 String으로 형변환해 사용한다면 생성자에서도 String으로 받는 방안을 제안하고, Object로 받은 이유를 물었다. (개선 제안)
  - 조건: 작성자는 빠르게 구현하다 그렇게 되었으며 특별한 이유는 없다고 답했다. 실제 타입 변경 여부는 대화에서 확인되지 않는다.

- [ ] 존재 여부를 반환하는 메서드에 int보다 boolean이 적합하지 않은지 묻고 int를 선택한 이유를 확인했다. (설계 질문)
  - 조건: 작성자는 서비스에서 반환된 정수를 비교하는 로직이 있었으며 boolean으로 처리하는 것이 더 깔끔해 보인다고 답했다. 페어와 두 타입을 고민해 int를 선택했지만 구체적인 이유는 기억하지 못한다고 했다. 반환 타입 변경이 실제로 반영됐다는 보고는 없다.
