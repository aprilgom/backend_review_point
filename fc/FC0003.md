# FC0003 · 모든 테스트 메서드에 반복되는 API 요청 로직을 별도 메서드로 추출하고, 중복 제거의 장점을 검토해 보자는 제안이다.

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0002 →](FC0002.md)

- [ ] 모든 테스트 메서드에 반복되는 API 요청 로직을 별도 메서드로 추출하고, 중복 제거의 장점을 검토해 보자는 제안이다. (개선 제안)
  - 조건: 작성자는 RestAssured 요청 부분을 Fixture로 분리했다고 보고하며, 다른 인수 테스트에서의 재사용과 테스트 흐름의 가독성 향상을 장점으로 설명했다. 실제 변경 결과는 별도로 확인되지 않았다.

- [ ] initializeMethod 안의 RequestMethod 획득 및 기본값 처리 로직도 별도 메서드로 분리할 수 있다고 제안했다. (개선 제안)
  - 조건: 작성자는 RequestMapping에서 메서드 목록을 얻고, 비어 있으면 모든 RequestMethod를 반환하는 getRequestMethods 메서드로 분리했다고 설명하며 코드를 제시했다. 실제 반영 여부는 별도로 확인되지 않는다.

- [ ] 단순 조회와 부재 예외 처리를 감싼 getStationFromId를 별도 메서드로 분리할 필요가 있는지 검토하자는 의견이다. (의견)
  - 조건: 작성자는 DAO의 Optional 반환에 따라 반복되는 orElseThrow 표현이 장황해져 분리했다고 설명했다. 리뷰어는 메서드 이름과 findById().orElseThrow()의 의미 차이가 크지 않다는 취향 차원의 의견이라고 한정했으며, 분리 자체를 결함으로 확정하거나 의견을 철회하지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Response response = createTask("read", Priority.NORMAL);
assertEquals(201, response.status());
assertEquals("read", response.body().title());
```

**적용 설명:** createTask에 반복 요청 구성을 모은 사용 예시다. 응답 검증까지 숨겨 테스트 의도가 사라지지 않게 한다.
