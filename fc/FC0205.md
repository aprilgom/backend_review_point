# FC0205 · 불변 모델과 상태 변화

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0203](FC0203.md) · [다음 FC: FC0206 →](FC0206.md)

## 검토 질문

- [ ] 상태 변경으로 복잡해지는 규칙을 불변 값과 명시적인 새 객체 생성으로 단순화할 수 있는가?

**직접 작성한 예시**

```java
record Balance(long amount) {
    Balance add(long delta) { return new Balance(Math.addExact(amount, delta)); }
}
```

**적용 설명:** 원본 대신 새 값을 반환한다. 불변성이 여러 객체 사이 트랜잭션을 자동 보장하지는 않는다.

## 구체적인 검토 사례

- [ ] 복잡한 비즈니스 로직에서 객체 상태 변화로 코드가 복잡해지는 점을 고려하여 도메인 객체를 가능한 한 불변 객체로 만들어 보자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 final 사용 자체를 문제 삼은 것이 아니라 상태 변화에 따른 복잡성과 안전성을 관심사로 제시했다. 작성자는 반영했다고 보고했으나 구체적인 변경 내용과 불변성 확보 여부는 대화에서 확인되지 않는다.

- [ ] 도메인 객체의 잦은 상태 변경으로 코드가 복잡해지고 있으므로 가능한 한 불변 객체로 만드는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 Rich Domain Model을 채택한 현재 구조에서 안전성과 복잡도 개선을 기대했다. 작성자는 수정했다고 답했으나 구체적인 변경 결과는 이 대화에서 확인되지 않는다.

- [ ] 값 객체를 반드시 불변으로 구현하려는 이유도 검토하도록 제안했다. (토론)
  - 조건: 작성자는 값 객체의 재사용과 여러 곳에서의 참조가 늘어날 때 변경에 대한 신뢰를 줄 수 있다는 점을 불변 설계의 이점으로 제시했다. 리뷰어는 이후 불변 @Embedded 값 객체가 JPA 사용에 문제가 없다는 설명을 이어갔으며, 불변 설계를 철회하라고 요구한 것은 아니다.
