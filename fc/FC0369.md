# FC0369 · 데이터를 가진 객체에 판단 위임

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0362](FC0362.md) · [다음 FC: FC0365 →](FC0365.md)

## 검토 질문

- [ ] 서비스가 객체의 여러 값을 꺼내 판단하기보다 관련 데이터를 가진 객체에 규칙을 위임할 수 있는가?

**직접 작성한 예시**

```java
boolean isPast(Clock clock) {
    return startsAt.isBefore(LocalDateTime.now(clock));
}
```

**적용 설명:** 예약의 시간 판단을 모델에 둔 예다. 모델의 시간대와 현재 시각 경계를 일관되게 정의한다.

## 구체적인 검토 사례

- [ ] 서비스가 예약의 날짜와 시간을 꺼내 과거 예약인지 계산하기보다 Reservation 객체에 판단을 요청하자는 제안이다. (개선 제안)
  - 조건: 리뷰어의 짧은 제안은 연결된 isPastReservation 코드에 관한 것이다. 작성자는 TDA 관점에서 동의하며 Reservation이 자신의 예약 시점을 기준으로 판단하고 validator는 현재 시점 기준의 과거 여부를 묻도록 변경했다고 설명했다. 변경의 실제 구현은 확인되지 않는다.

- [ ] 과거 날짜 예약 검증이 서비스가 아니라 Reservation 도메인에서 수행할 로직인지, 도메인과 서비스의 책임을 다시 검토하자고 묻는다. (토론)
  - 조건: 작성자는 신규 예약에만 적용되는 규칙과 영속성 협력이 필요해 서비스에서 검증했다고 설명하면서도 도메인 로직으로 볼 여지가 있어 결론을 내리지 못했다고 밝혔다. 리뷰 참여자는 레벨 1에서의 도메인 핵심 가치를 중심으로 다시 보자고 권했다. 검증 책임의 이동이나 최종 구현은 이 대화에서 확인되지 않는다.

- [ ] 조회한 Reservation에 예약 가능 여부를 묻고, 자신의 상태를 확인하는 판단을 도메인 객체에 맡기는 방식을 제안한다. (개선 제안)
  - 조건: 작성자는 Member에 OneToMany 예약 목록을 추가하라는 의미인지 물었다. 리뷰 참여자는 회원 연관관계 추가가 아니라, 상태 조건 없이 조회한 Reservation에 메시지를 보내 자체 상태를 판단하게 하자는 의미라고 설명했다. 작성자의 이해 표시는 구현 반영의 증거가 아니다.
