# FC0203 · ID만 받고 나머지 필드를 null로 두는 `Member` 생성자가 왜 필요한지 질문하며 어색하다는 의견을 제시했다.

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0205 →](FC0205.md)

- [ ] ID만 받고 나머지 필드를 null로 두는 `Member` 생성자가 왜 필요한지 질문하며 어색하다는 의견을 제시했다. (설계 질문)
  - 조건: 작성자는 예약 도메인 테스트에서 객체를 쉽게 생성하기 위한 생성자였다고 설명했다. 이어 프로덕션 코드의 위험성을 고려해 삭제했다고 보고하고 테스트 픽스처나 테스트용임을 드러내는 정적 팩터리를 대안으로 언급했다. 위험 판단과 대안은 작성자의 설명이며, 리뷰어가 확정적으로 결함을 지적하거나 삭제 결과를 확인한 것은 아니다.

- [ ] ID를 모르는 생성 단계에서도 ReservationTime과 ID를 강제해야 하는지, 다른 객체나 ID 없는 표현을 사용할 수 없는지 설계 이유를 물었다. (토론)
  - 조건: 리뷰어는 심화 질문으로 제시했다. 작성자는 DTO의 DAO 전파, 개별 인자 전달, ID 없는 별도 도메인, 기존 도메인 재사용의 장단점을 비교하고, null ID를 가진 기존 객체 재사용이 가장 낫다고 판단했다고 설명했다. 의미 없는 ID 필드가 혼동을 줄 수 있다는 단점도 인정했으며, 이 판단에 대한 리뷰어의 후속 답변은 없다.

- [ ] 예약 ID를 Integer로 표현한 이유와, DB 연결을 Long으로 변경해야 하는 근거로 삼은 이유를 질문했다. (토론)
  - 조건: 작성자는 처음에는 소규모 프로젝트라 Integer로 충분하다고 판단했으나 향후 DB 연결 시 수정을 줄이려고 Long으로 변경했다고 보고했다. 리뷰어는 DB에서도 Int를 사용할 수 있다고 반문했다. 작성자는 장기적으로 자동 증가 ID가 Integer 범위를 넘을 가능성을 고려해 BIGINT와 Long을 선택했다고 설명했다. DB 연결 자체가 Long을 요구한다는 결론이나 리뷰어의 Long 변경 요구로 해석하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record CustomerId(long value) {}
void assignOwner(CustomerId id) { this.ownerId = id; }
```

**적용 설명:** 식별자만 필요하면 나머지가 null인 가짜 Customer 대신 ID 타입을 받는다.
