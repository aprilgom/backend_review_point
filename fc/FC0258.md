# FC0258 · 화면 캐시와 최종 업무 검증

## 검토 질문

- [ ] 화면 표시에 쓰는 캐시와 결제·확정 단계의 최신 상태 검증을 구분하는가?

**직접 작성한 예시**

```javascript
const cached = cartSnapshot.get(productId);
renderQuantity(cached?.quantity ?? 0);
// 주문 확정 시 서버가 현재 가격·재고·권한을 다시 검증한다.
```

**적용 설명:** 화면 표시 캐시는 편의를 위한 값이다. 결제의 정합성 판단을 클라이언트 캐시에 맡기지 않는다.

## 구체적인 검토 사례

- [ ] 매번 GET으로 존재 여부를 확인하는 대신 프론트엔드에서 상품 존재 여부와 수량을 캐싱해 표시하고, 결제 시점에 다시 검증하는 방식을 대안으로 제시했다. (개선 제안)
  - 조건: 작성자가 설명한 반복 조회와 사용자 경험 우려에 대한 대안이다. 리뷰 참여자는 현재 프론트엔드 구현을 모른다고 전제했고, 캐싱과 결제 시 검증은 예시로 제안했다. 현 구조의 결함이나 이 대안의 적용 가능성이 확정된 것은 아니다.

- [ ] 액세스 토큰을 store에만 저장하면 새로고침 시 store가 초기화되는지 확인을 요청한다. (설계 질문)
  - 조건: 작성자는 새로고침을 고려하지 않았다고 답하고, vuex-persistedstate를 사용해 member와 auth 모듈의 상태만 저장하도록 변경했다고 보고했다. 새로고침 후 동작이 검증된 것은 아니다.

- [ ] 전체 시간 목록도 변경될 수 있으므로 캐싱할 때 갱신·초기화 방안과 페이지 체류 중 데이터가 바뀌는 경우의 트레이드오프를 고려하자는 의견이다. (토론)
  - 조건: 작성자는 전체 시간 목록이 항상 같다고 판단해 최초 조회 결과를 저장했다고 설명했다. 리뷰 참여자는 공사 등으로 가능 시간이 변경될 수 있다고 지적했으나, 후속 답변에서는 현재 구조가 예약 페이지 재진입 시 다시 조회하므로 그때 갱신되어 괜찮다고 범위를 좁혔다. 페이지에 머무는 동안의 변경 가능성은 남아 있지만 이번 미션 규모에서는 드문 상황으로 보았으며, 즉각적인 수정 요구보다는 캐시 전략 학습과 트레이드오프 검토를 권했다.
