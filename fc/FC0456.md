# FC0456 · basePackage의 타입을 Object 대신 String으로 제한하여 타입 오류를 컴파일 시점에 확인하는 방안에 대한 의견을 물었다.

[소속 분야: 타입·타입 테스트](../24-type-safety.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0464](FC0464.md) · [다음 FC: FC0459 →](FC0459.md)

- [ ] basePackage의 타입을 Object 대신 String으로 제한하여 타입 오류를 컴파일 시점에 확인하는 방안에 대한 의견을 물었다. (토론)
  - 조건: 리뷰 참여자는 자신의 방식일 뿐 반영할 필요는 없으며, 현재 전달되는 인자도 모두 String이므로 넘어가도 된다고 명시했다. 제안을 철회한 것은 아니다. 작성자는 String으로 한정하는 편이 더 안전하다고 판단하여 수정했다고 답했다.

- [ ] HandlerExecution을 추상화했으므로 테스트에서 getHandler 결과를 AnnotationHandlerExecution으로 형변환하지 않아도 된다고 제안했다. (개선 제안)
  - 조건: 참여자는 형변환 없이 var로 받는 코드를 제시했다. 작성자는 일괄 변경 과정에서 해당 부분도 함께 바뀌었다고 설명했으며, 이 대화 안에서는 수정 완료가 확인되지 않는다.

- [ ] 이미 Student로 생성한 객체를 studentClass로 다시 캐스팅하는 이유를 묻고, studentClass를 사용하려는 의도라면 리플렉션으로 생성하는 대안을 제시한다. (설계 질문)
  - 조건: 리플렉션 생성 대안은 위에서 선언한 studentClass를 활용하려는 경우라는 조건으로 제시됐다. 작성자는 관성적으로 작성하다 놓친 부분이라며 수정 의사를 밝혔지만, 제시된 대안의 적용이나 기술적 타당성은 이 대화만으로 확정하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
List<Class<?>> scan(String basePackage) { return scanner.find(basePackage); }
```

**적용 설명:** Object 대신 필요한 타입을 받으면 잘못된 인자를 컴파일 단계에서 줄일 수 있다. 문자열 내용 검증은 별도다.
