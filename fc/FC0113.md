# FC0113 · 필요한 경우 equals와 hashCode를 재정의해 사용할 수 있다는 의견을 제시했다.

[소속 분야: 엔티티 동등성·식별](../06-identity.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0114 →](FC0114.md)

- [ ] 필요한 경우 equals와 hashCode를 재정의해 사용할 수 있다는 의견을 제시했다. (조건부 제안)
  - 조건: 필요성에 따른 선택으로 표현했다. 응답 대상인 원래 질문과 구체적인 객체가 제공되지 않아 어떤 동등성 기준을 논의했는지는 확인할 수 없다.

- [ ] equals와 hashCode를 재정의하는 목적을 질문했다. (설계 질문)
  - 조건: 작성자는 Reservation의 ID를 동등성 기준으로 삼고 Set·Map에서도 그 기준대로 동작하게 하려는 목적이라고 설명했다. 이 기준의 타당성을 리뷰 참여자가 확인하거나 변경을 요구한 후속 발언은 없다.

- [ ] equals와 hashCode를 재정의한 객체와 재정의하지 않은 객체를 구분한 기준을 질문했다. (설계 질문)
  - 조건: 작성자는 bookedTimes.contains(reservationTime)에서 ReservationTime을 값 기준으로 비교하려고 재정의했다고 설명했다. contains와 equals·hashCode의 관계에 대한 설명은 작성자의 주장으로 남기며, 모든 객체에 재정의를 요구한 질문으로 해석하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record Position(int x, int y) {}
assertEquals(new Position(2, 3), new Position(2, 3));
assertEquals(1, new HashSet<>(List.of(new Position(2, 3), new Position(2, 3))).size());
```

**적용 설명:** 값 객체에는 구성 값 기준 동등성이 자연스러울 수 있다. 직접 equals를 구현하면 hashCode 계약도 맞춘다.
