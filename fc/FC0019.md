## 검토 질문

- [ ] 날짜·시간 등 반복되는 출력 형식을 공통 설정으로 통일할 수 있으며 개별 예외도 명시할 수 있는가?

**직접 작성한 예시**

```java
DateTimeFormatter clockFormat = DateTimeFormatter.ofPattern("HH:mm");
String rendered = time.format(clockFormat);
```

**적용 설명:** 시간 출력 규약을 공통화하는 최소 예시다. JSON 직렬화에 적용하려면 사용하는 직렬화기의 공통 설정에도 연결해야 한다.

## 구체적인 검토 사례

- [ ] LocalTime도 LocalDate처럼 공통 포맷 처리를 적용하여 필드의 @JsonFormat을 제거할 수 있지 않은지 제안했다. (개선 제안)
  - 조건: 작성자는 LocalTime 공통 처리는 했지만 해당 필드의 어노테이션 제거를 놓쳤다며 반영했다고 보고했다.

- [ ] 결제 금액을 FE와 BE 코드에 중복 관리하면 양쪽을 함께 수정해야 하고, 서로 다른 배포 주기에서 값이 일시적으로 어긋날 수 있으므로 현재 방식을 재검토할 필요가 있다. (토론)
  - 조건: 작성자가 금액 위조 방지를 위해 서버 측 가격 검증을 추가했다고 설명한 데 대해, 리뷰어는 취약점 대응 자체는 인정하면서 중복 관리 문제를 제기했다. 현재는 FE와 BE가 한 프로젝트에서 함께 배포되지만, 별도 배포되는 경우 사용자 오류가 발생할 수 있다는 조건이다. 작성자는 클라이언트의 가격 입력을 받지 않고 서버 값을 사용하도록 수정했다고 보고했으며, 실제 구현 결과는 확인되지 않았다.

- [ ] racingcar 도메인에 속한 난수 생성기는 범용적으로 보이는 이름과 달리 도메인에 맞춰 0~9 범위를 내부에 두어도 괜찮다는 의견을 제시한다. (의견)
  - 조건: 리뷰 참여자는 다른 도메인에서는 기존 클래스를 재사용하기보다 각자 필요한 형태로 만드는 경우가 많다는 이유를 들었다. 작성자는 생성자로 범위를 받으면 외부가 난수 생성 조건을 알아야 한다고 생각해 변경했다고 설명했다. 모든 난수 생성기의 범위를 고정하라는 보편 규칙이나 제시된 계산식의 정확성 검증으로 해석하지 않는다.
