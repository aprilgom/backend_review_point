# FC0391 · JSESSIONID가 없는 모든 요청이 아니라 로그인 성공 시에만 세션 쿠키를 발급하도록 한 판단 기준을 논의했다.

[소속 분야: 인증·보안·비밀값](../20-security.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0389](FC0389.md) · [다음 FC: FC0390 →](FC0390.md)

- [ ] JSESSIONID가 없는 모든 요청이 아니라 로그인 성공 시에만 세션 쿠키를 발급하도록 한 판단 기준을 논의했다. (토론)
  - 조건: 리뷰 참여자는 미션 3번 설명의 해석을 질문했다. 작성자는 로그인 상태 유지라는 목적과 로그인 전 저장할 정보가 없다는 이유를 설명하고, 문서와 서버 코드를 검토한 자신의 해석으로 세션 생성 시점은 구현 측에서 정한다고 답했다. 후속 발언에서 리뷰 참여자는 로그인 과정에서 세션을 생성하고 쿠키를 전달하는 흐름에 동의하며 현 구현을 유지해도 된다고 했다. 결함 확정이나 지적의 명시적 철회가 아니라 요구사항 해석에 관한 논의다.

- [ ] JSESSIONID가 없는 첫 GET 요청에도 세션 쿠키를 발급해야 하는지, 로그인 성공 시에만 발급해도 되는지 요구사항 해석을 논의했다. (토론)
  - 조건: 리뷰 참여자는 요청 Cookie에 JSESSIONID가 없으면 Set-Cookie를 반환한다는 문장을 근거로 최초 GET /login 및 GET /index.html의 처리 경로 확인을 제안했다. 작성자는 로그인 성공 시 상태를 유지한다는 요구와 미션 예시를 근거로 성공 시에만 발급했다고 설명했다. 리뷰 참여자는 로그인 정보 저장 시점과 쿠키 발급 시점을 구분해 해석했음을 밝히고 작성자의 의도를 이해하며 논의를 마무리했다. 명시적인 지적 철회나 변경 요구는 없으며, 어느 해석이 요구사항에 부합하는지는 확정하지 않는다.

- [ ] 요청 쿠키에 JSESSIONID가 있다는 이유만으로 로그인 상태로 판단하면, 서버 세션 저장소에 해당 세션이 없어도 리다이렉트될 수 있으므로 실제 세션 존재 여부를 확인하자고 제안했다. (위험 지적)
  - 조건: JSESSIONID는 있지만 SessionManager의 SESSIONS에는 해당 세션이 없는 경우를 지적했다. 참여자는 findSession 사용을 제안했으나, 작성자는 그 방식이 복잡해져 getSession을 이용했다고 보고했다. 참여자는 대안을 긍정적으로 받아들였지만, 변경 코드의 실제 동작이나 해결 여부가 검증된 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Actor actor = authenticator.authenticate(credentials);
Session session = sessions.rotateAfterLogin(previousSessionId, actor);
reply.addCookie(sessionCookie(session));
```

**적용 설명:** 로그인 성공 시 새 세션 식별자를 발급해 고정 공격을 방어하는 계약이다. 익명 세션이 필요한 서비스는 별도 생명주기를 정한다.
