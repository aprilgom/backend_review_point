# FC0384 · DAO와 Repository의 책임 차이

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0379](FC0379.md) · [다음 FC: FC0385 →](FC0385.md)

## 검토 질문

- [ ] 테이블 행 접근과 도메인 저장 계약의 차이를 이해하고 이름·구현·계층을 일관되게 선택했는가?

**직접 작성한 예시**

```java
interface Orders { Optional<Order> find(OrderId id); }
interface OrderRows { Optional<OrderRow> selectById(long id); }
```

**적용 설명:** 도메인 컬렉션 같은 계약과 테이블 행 접근 계약의 차이를 보인다. 두 계층을 항상 동시에 만들 필요는 없다.

## 구체적인 검토 사례

**혼합·경계:** @Repository 외에 DAO·Repository의 일반적인 역할 구분이 중심.

- [ ] DAO에 @Repository를 사용한 이유를 묻고 DAO와 Repository의 역할 차이를 논의했다. (토론)
  - 조건: 작성자는 직접 쿼리와 JDBC를 사용하는 DAO와 ORM 기반 추상화로 이해한 Repository를 구분하며 @Component로 변경했다고 보고했다. 리뷰어는 데이터베이스 접근 세부사항이 드러나는 DAO와 도메인 객체를 컬렉션처럼 다루게 하는 Repository라는 관점으로 설명을 보완하고, 현재 DAO를 @Component로 지정한 선택도 좋다고 평가했다. 이 대화를 DAO의 @Repository 사용이 항상 잘못이라는 보편 규칙으로 해석하지 않는다.

- [ ] 현재 구조에서 Repository가 의미하는 역할과 DAO와의 차이를 질문했다. (토론)
  - 조건: 작성자는 구분 기준이 아직 명확하지 않다고 전제하면서, 테이블과 직접 일대일 대응하기보다 도메인 값에 따라 객체를 조회하므로 Repository로 명명했다고 설명했다. 리뷰어는 설명을 들은 뒤 현재 형태가 DB 구조보다 도메인 모델에 가까워 Repository라는 이름이 더 적합하다는 의견을 밝혔다. 질문 자체를 철회한 것은 아니다.

- [ ] Repository와 DAO의 역할 차이를 어떻게 이해하고 있는지 물었다. (설계 질문)
  - 조건: 작성자는 DAO를 테이블 CRUD를 캡슐화하는 객체로, Repository를 도메인 엔티티 컬렉션 역할의 객체로 이해한다고 설명했다. 리뷰어는 이론적으로 그렇게 구분한다며 현재 코드도 크게 어색하지 않다고 답했으며, 역할 구분의 결함을 확정하지 않았다.
