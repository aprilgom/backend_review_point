# FC0433 · 트랜잭션 제어의 상호작용 검증

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0439](FC0439.md) · [다음 FC: FC0438 →](FC0438.md)

## 검토 질문

- [ ] 커밋·롤백·해제 호출 계약을 대역으로 검증하고 실제 원자성은 DB 테스트로 보완하는가?

**직접 작성한 예시**

```java
assertThrows(IllegalStateException.class, () ->
    tx.run(() -> { throw new IllegalStateException("failed"); }));
verify(connection).rollback();
verify(connection, never()).commit();
```

**적용 설명:** Mockito 형태로 자원 제어 계약을 검증한다. tx가 이 대역 커넥션을 사용하는 준비가 필요하며 실제 DB 원자성은 통합 테스트로 확인한다.

## 구체적인 검토 사례

- [ ] 평소 Mockito 등의 모킹을 테스트에 사용하는지, 이번 TransactionManager 테스트에서 모킹을 선택한 이유는 무엇인지 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 단순한 호기심이라고 명시했다. PR 작성자는 평소 모킹을 잘 쓰지 않지만 실제 DB의 성공·실패 상태를 검증할 별도 객체를 만들고 검증하는 비용 때문에 선택했다고 설명했다. 또한 현재 테스트가 코드에서 확인 가능한 호출을 검증하지만 다른 개발자에게 신뢰를 줄 수 있다고 보았다. 모킹 사용의 결함이나 변경 요구가 제기된 것은 아니다.

- [ ] 대부분의 테스트에서 mock을 사용하는 것으로 보이는데 mocking을 선호하는 이유가 있는지 질문했다. (설계 질문)
  - 조건: 작성자는 단위 테스트에 집중하기 위한 선택이며 각 클래스의 단위 테스트가 충실하다면 서비스의 Repository 의존성을 모킹해도 충분하다고 설명했다. Fake는 추가 구현과 테스트 등 유지보수 대상이 되고 현재 H2 메모리 DB의 비용도 크지 않다고 보아 당장은 mocking을 선호한다고 덧붙였다. 이는 작성자의 선택 근거이며 리뷰어가 Fake 사용이나 mock 제거를 요구한 것은 아니다.

- [ ] 서비스 테스트에서 Mockito를 선택한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 현재 프로젝트 규모에서 Fake 구현보다 준비 비용이 적고, 호출 대상의 반환값과 의도한 호출을 명시하기 편하다는 이유를 제시했다. 반면 성공 테스트를 위해 여러 호출을 설정하는 불편함도 언급하며, 설정 대상이 3개 이상이 되면 Fake를 고려하겠다는 개인 기준을 밝혔다. 이는 리뷰어가 요구한 전환 기준이 아니다.
