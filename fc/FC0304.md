# FC0304 · SQL 상수 추출의 필요성

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0327](FC0327.md) · [다음 FC: FC0326 →](FC0326.md)

## 검토 질문

- [ ] SQL을 별도 상수로 옮길 때 재사용·길이·의미 측면의 이점이 사용처와 멀어지는 비용보다 큰가?

**직접 작성한 예시**

```java
String sql = "SELECT id, name FROM tag WHERE id = ?";
return runner.queryOne(sql, bind(id), mapper);
```

**적용 설명:** 한 번 쓰는 짧은 SQL을 가까이 두는 대안이다. 재사용·길이·의미에 따라 상수 추출을 결정한다.

## 구체적인 검토 사례

- [ ] SQL을 별도 상수로 추출할 필요가 있는지 질문했다. (설계 질문)
  - 조건: 작성자는 복잡한 쿼리의 가독성을 위해 분리했으나 메서드 안에서 의도를 바로 파악하기 어려운 단점도 있다고 설명했다. 공통으로 여러 번 쓰는 SQL만 상수로 두고 단일 메서드에서 쓰는 SQL은 해당 메서드 안에 선언하도록 수정했다고 보고했다. 이 구분 기준은 작성자의 설명이며 리뷰 참여자가 직접 요구한 기준은 아니다.

- [ ] 여러 리터럴을 모두 상수로 분리하기는 어렵더라도 중복되는 값은 상수로 분리하자는 제안이다. (개선 제안)
  - 조건: 모든 값을 일괄적으로 상수화하라는 요구가 아니라 중복되는 값에 우선 적용하자는 취지다. 작성자는 리팩터링하면서 상수도 분리하겠다고 답했다.

- [ ] minusDays의 인자로 사용하는 상수 이름에서는 과거 방향을 뜻하는 AGO를 생략해도 된다. (개선 제안)
  - 조건: NUMBER_TO_MAKE_WEEK_AGO 상수가 minusDays에 전달되는 사용 맥락을 전제로 한 명명 제안이다.
