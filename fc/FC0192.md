# FC0192 · 직접 작성하지 않은 기존 코드의 문제도 프로젝트에 도움이 된다면 드러내고 수정할지 판단하자.

[소속 분야: 문서·개발·학습 과정](../10-workflow.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0193](FC0193.md) · [다음 FC: FC0195 →](FC0195.md)

- [ ] 직접 작성하지 않은 기존 코드의 문제도 프로젝트에 도움이 된다면 드러내고 수정할지 판단하자. (의견)
  - 조건: 작성자가 이전 미션 코드를 자신의 코드가 아니라는 이유로 넘겼다고 회고한 데 대한 조언이다. 리뷰 참여자는 개인의 잘잘못을 따지려는 것이 아니라 프로젝트의 방향성에 도움이 되는지를 기준으로 판단하라는 취지라고 한정했다.

- [ ] 코드를 제거하고 처음부터 구현하기보다 기존 코드를 리팩터링하면서 기능을 추가하는 경험을 해보았으면 좋겠다는 의견을 제시했다. (의견)
  - 조건: 현업에서는 기존 코드를 수정하고 확장하는 일이 많다는 이유로 제시한 개인적인 학습 과정 의견이며, 전면 재작성을 금지하는 요구는 아니다. 이후 승인과 미션 마무리 안내는 이 의견의 반영 여부를 입증하지 않는다.

- [ ] 프론트엔드·Android 개발자와 API를 함께 설계한 경험이 백엔드 개발자끼리의 페어 작업과 어떻게 달랐는지 돌아보자. (설계 질문)
  - 조건: 작성자는 같은 파트끼리는 서버 처리라는 전제를 공유했지만, 프론트엔드와는 계산 책임 및 가격 정보를 요청에 포함할지를 두고 의견 차이가 있었다고 설명했다. 리뷰어는 열린 태도로 조율하자는 의견을 덧붙였으며, 특정 협업 방식이 잘못되었다고 확정한 질문은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
@Test void emptyTitleIsRejected() {
    assertThrows(IllegalArgumentException.class, () -> new Task(""));
}
```

**적용 설명:** 기존 코드의 문제를 발견하면 재현 가능한 검증으로 드러낸다. 요청 범위와 영향도를 확인해 수정 범위를 정한다.
