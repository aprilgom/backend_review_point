# FC0155 · 구현 탐색과 등록 방식

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0149](FC0149.md) · [다음 FC: FC0151 →](FC0151.md)

## 검토 질문

- [ ] 구현을 직접 등록할지 동적으로 탐색할지 결정하고 초기화 실패·순서·운영 복잡성을 처리하는가?

**직접 작성한 예시**

```java
List<HandlerMapping> mappings = ServiceLoader.load(HandlerMapping.class)
    .stream().map(ServiceLoader.Provider::get).toList();
```

**적용 설명:** 구현 탐색을 위한 JDK 대안이다. 서비스 제공자 등록·초기화 실패·순서를 명시하고 동적 탐색의 복잡성을 비교한다.

## 구체적인 검토 사례

- [ ] DispatcherServlet에서 특정 매핑 구현체를 직접 생성하는 대신 HandlerMapping 구현체를 리플렉션으로 찾는 방식을 고려해 보자는 의견이다. (개선 제안)
  - 조건: 추상화를 한 단계 더 확장하는 선택지로 제시했으며, 리뷰 참여자 스스로 장단점을 비교하지 않은 개인적 생각이므로 크게 신경 쓰지 않아도 된다고 완화했다. 제안 자체를 철회한 것은 아니며 실제 적용 여부도 확인되지 않는다.

- [ ] HandlerMappings와 HandlerAdapters에 들어갈 구체 구현체를 DispatcherServlet에서 직접 구성해 넣은 이유를 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 구현체 구성 위치의 이유를 질문했으며, 반드시 다른 클래스로 옮기라고 요구하지는 않았다. 작성자는 Adapters와 HandlerMappings에 역할을 더 분담하도록 수정하겠다고 답했지만, 직접 구성한 이유를 별도로 설명하거나 변경 결과를 제시하지는 않았다.

- [ ] DispatcherServlet 생성 후 HandlerMapping을 추가하던 방식에서 HandlerMapping과 HandlerAdapter 목록을 생성자로 주입하는 방식으로 바꾼 이유를 물었다. (설계 질문)
  - 조건: 작성자는 DispatcherServlet의 핸들러 매핑을 불변으로 관리하고 싶었다고 설명했다. 리뷰어가 기존 방식이나 생성자 주입 방식의 결함을 확정한 것은 아니다.
