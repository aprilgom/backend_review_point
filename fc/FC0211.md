# FC0211 · Reservation과 ReservationWaiting이 거의 동일한 도메인인 현재 구조에서, 대기를 예약의 상태로 표현하지 않은 이유를 물었다.

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0208](FC0208.md) · [다음 FC: FC0212 →](FC0212.md)

- [ ] Reservation과 ReservationWaiting이 거의 동일한 도메인인 현재 구조에서, 대기를 예약의 상태로 표현하지 않은 이유를 물었다. (설계 질문)
  - 조건: 작성자는 슬롯당 하나인 예약과 순번을 가진 다수의 대기는 생명주기가 다르고, 예약 변경을 기존 대기열이 따라가면 안 된다는 이유로 분리했다고 답했다. 상태로 표현하면 중복은 줄지만 대기열의 생명주기와 순번 표현이 애매하다는 것이 작성자의 판단이다. 리뷰 참여자는 현재 구조로 다음 사이클을 진행하자고 답했다.

- [ ] 예약 포함 여부를 다루려면 단일 Reservation보다 Reservation의 복수형 도메인을 만들어 풀어보는 대안을 제시했다. (개선 제안)
  - 조건: 리뷰 참여자는 단일 예약에 contains를 묻는 구조를 Team이 아닌 Member에게 포함 여부를 묻는 것에 비유했다. 복수형 도메인은 자신이라면 시도할 설계 대안으로 제시했으며 필수 변경으로 단정하지 않았다. 작성자의 앞선 책임 분리 보고가 이 제안을 반영했다는 근거는 없다.

- [ ] ReservationDate와 ReservationTime을 ReservationDateTime으로 묶어 얻는 이점이 무엇인지 질문했다. (설계 질문)
  - 조건: 작성자는 과거 날짜와 시간으로 예약하지 못하게 하는 추가 규칙 때문에 날짜와 시간을 함께 검증해야 했으며, 그 책임을 Reservation에서 분리하기 위해 묶었다고 설명했다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
enum BookingState { WAITING, CONFIRMED, CANCELLED }
record Booking(BookingId id, BookingState state) {}
```

**적용 설명:** 대기를 같은 생명주기의 상태로 표현한 대안이다. 데이터·행동·수명이 크게 다르면 분리할 수 있다.
