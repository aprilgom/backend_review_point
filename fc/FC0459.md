# FC0459 · 필수 인자의 nullable 여부

[소속 분야: 타입·타입 테스트](../24-type-safety.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0456](FC0456.md) · [다음 FC: FC0458 →](FC0458.md)

## 검토 질문

- [ ] 정상 호출에서 반드시 필요한 값이라면 경계에서 부재를 처리하고 내부 타입의 null 가능성을 줄일 수 있는가?

**직접 작성한 예시**

```java
void delete(long requiredId) { repository.delete(requiredId); }
```

**적용 설명:** 정상 호출에서 필수 식별자라면 nullable을 줄일 수 있다. HTTP 파싱에서 누락·오류를 먼저 처리한다.

## 구체적인 검토 사례

- [ ] 삭제 요청의 값은 null로 들어오지 않을 것으로 보이므로 nullable 타입의 필요성을 재검토하는 의견이다. (관찰)
  - 조건: 리뷰어는 null 요청이 없을 것 같다는 판단을 제시했고, 작성자는 long으로 수정하겠다고 답했다. 실제 null 유입 가능성 검증이나 변경 완료는 확인되지 않는다.

- [ ] Optional로 표현할 수 있는 조회 결과의 부재를 orElse(null)로 다시 null로 바꿀 필요가 있는지 검토하자. (토론)
  - 조건: 처음에는 필요성을 묻는 질문이었고, 후속 발언에서는 Optional로 표현 가능한 정보이므로 별도 null이 필요하지 않겠다는 취지를 명시했다. 작성자는 없는 대기를 삭제할 때 정상 응답을 주도록 바꾸는 과정에서 해당 코드를 넣었다고 설명하고, null 검사 대신 ifPresent 내부에서 처리하도록 수정했다고 보고했다. 부재 삭제 시 정상 응답이라는 정책은 작성자가 이전 리뷰를 설명한 내용이지, 이 스레드에서 새로 제기된 요구는 아니다.

- [ ] SECTION의 관련 칼럼이 모두 NOT NULL인데 엔티티 필드에 래퍼 타입을 사용할 필요가 있는지 검토하자. (설계 질문)
  - 조건: 리뷰 참여자는 스키마의 null 불가 조건을 근거로 질문했다. 작성자는 null이 포함되지 않으므로 원시 타입으로 변경했다고 보고했다. 래퍼 타입 사용이 곧 실행 오류라는 지적은 아니다.
