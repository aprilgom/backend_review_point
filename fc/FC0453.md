# FC0453 · 읽기 DB 조회 실패 후 쓰기 DB를 조회하는 경로에서 의도한 트랜잭션이 동작하는지와 그 원인을 확인해 달라고 요청했다.

[소속 분야: 트랜잭션·자원 수명](../23-transaction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0450](FC0450.md) · [다음 FC: FC0451 →](FC0451.md)

**혼합·경계:** 트랜잭션 경계·외부 호출·보상 처리 원리는 Spring에 한정되지 않음.

- [ ] 읽기 DB 조회 실패 후 쓰기 DB를 조회하는 경로에서 의도한 트랜잭션이 동작하는지와 그 원인을 확인해 달라고 요청했다. (설계 질문)
  - 조건: 질문자는 트랜잭션이 의도와 달리 동작하지 않는 것으로 보인다고 표현했다. 작성자는 같은 객체 내부 호출이 프록시를 거치지 않아 REQUIRES_NEW 설정이 적용되지 않는 문제라고 분석했다. 프록시 강제 호출, AspectJ, 별도 서비스 분리를 검토했으나 각각 결합도·설정 및 학습 비용·구조적 부담을 이유로 선택하지 않았고, Supplier를 받아 실행하는 별도 트랜잭션 컴포넌트로 해결했다고 보고했다. 이는 작성자의 원인 분석과 변경 보고이며 실행 결과를 독립적으로 확인한 것은 아니다.

- [ ] 현재 트랜잭션 경계에서는 결제 정보 저장 실패 시 기존 DB 변경이 롤백되지 않고 예약 삭제 보정까지 필요하므로, 외부 결제 호출을 먼저 수행한 뒤 DB 저장을 하나의 트랜잭션으로 묶도록 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 외부 API 호출을 트랜잭션 밖에 두려는 의도 자체는 긍정했다. 작성자는 결제 후 예약 생성 실패에 따른 결제 취소를 줄이려던 것이 기존 순서의 이유라고 설명했다. 이어 중복·과거 날짜 예약이 프론트에서 차단되어 실패 가능성이 낮을 것이라는 자신의 판단을 근거로 결제를 먼저 하는 구조를 반영했다고 보고했다. 해당 실패 확률이나 실제 트랜잭션 동작은 이 대화에서 검증되지 않았다.

- [ ] 예약 취소를 트랜잭션으로 처리하면 취소 변경을 롤백할 수 있을 텐데, 별도로 결제 데이터를 새로 저장하는 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 처음 질문을 새 객체 생성 이유로 이해하여, merge의 선행 조회를 피하려 ID가 null인 복사본을 저장한다고 설명했다. 작성자 외 참여자는 질문이 혼동될 수 있었다고 밝히고, 의도는 cancelReservation에 @Transactional을 선언하는 경우에도 수동 재저장이 필요한지 묻는 것이라고 명확히 했다. 지적을 철회한 것은 아니며, 실제 트랜잭션 범위의 적절성이나 최종 해결은 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
try { return readerTransactions.read(() -> replica.find(id)); }
catch (ReplicaUnavailable failure) {
    return writerTransactions.read(() -> primary.find(id));
}
```

**적용 설명:** 가상 트랜잭션 경계를 분리한 개념 코드다. 실패한 트랜잭션 안에서 그대로 재조회해도 되는지, 단순 부재와 장애를 구분하는지 확인한다.
