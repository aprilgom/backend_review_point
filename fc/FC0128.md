# FC0128 · 정렬 기준과 순번의 의미

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0127](FC0127.md)

## 검토 질문

- [ ] ID·생성 시각·커밋 순서가 같은 의미라고 가정하지 않고 업무상 순서와 동률 처리를 정의했는가?

**직접 작성한 예시**

```sql
SELECT id, ROW_NUMBER() OVER (ORDER BY created_at, id) AS queue_position
FROM waiting WHERE slot_id = :slot;
```

**적용 설명:** 동일 시각의 순서를 ID로 보완한다. 자동 증가 ID만으로 커밋 순서나 실제 접수 순서가 보장되지는 않는다.

## 구체적인 검토 사례

- [ ] 예약 대기 순번을 created_at 대신 자동 증가하는 id 기준으로 계산해도 되는지 검토하자는 논의다. (토론)
  - 조건: 작성자는 서비스에서 생성 시각을 설정한 순서와 DB 삽입 순서가 달라질 가능성을 고려했다고 설명하고, @Transactional을 사용하면 id로 충분한지 질문했다. 리뷰어는 서로 다른 예약 요청을 동시성 문제로 볼지 의문을 제기하면서도 생성 시각이 빠른 데이터가 늦게 삽입될 가능성은 추측으로 인정했다. API 호출 순서와 DB 저장 순서 중 무엇을 우선할지 정책으로 정할 문제라고 설명하며 저장 완료를 기준으로 id 사용이 가능하지 않겠냐는 의견을 냈다. 트랜잭션의 효과나 실제 순서 역전 여부는 확인되지 않았다.

- [ ] id 비교로 대기 순번을 계산하면 실제 등록 시점을 표현하기 어려울 수 있으므로 createdAt을 기준으로 삼는 방안을 제안했다. (위험 지적)
  - 조건: 리뷰 참여자는 id가 생성 순서를 보장하지 않는다고 주장하고, 장애 등으로 DB에 값을 수동 삽입할 때 원하는 시점을 지정하지 못해 항상 마지막 순번이 되거나 고객에게 순번 근거를 설명하기 어렵다는 상황을 들었다. 작성자는 AUTO_INCREMENT라 괜찮다고 생각했으나 수동 삽입 상황을 놓쳤다고 답하고 학습 후 사용하겠다고 했다. createdAt 적용 결과나 순서 보장에 관한 기술적 검증은 확인되지 않는다.

- [ ] 예약 대기 순번을 테이블에 저장하는 방법 대신 조회 시 DB에서 계산하는 방식을 선택한 이유를 질문한다. (설계 질문)
  - 조건: 작성자는 앞선 대기의 취소·자동 승인 때 후속 순번을 갱신해야 하고 동시 취소 시 일관성 유지 비용이 커질 수 있어 매번 계산한다고 설명했다. 이는 작성자가 제시한 선택 근거이며 두 방식의 성능이나 정확성을 비교 검증한 결과는 아니다.
