# FC0331 · 전송 메서드와 업무 메서드명의 구분

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0324](FC0324.md) · [다음 FC: FC0302 →](FC0302.md)

## 검토 질문

- [ ] HTTP 메서드만으로 이름을 정하지 않고 조회 대상·조건·역할을 드러내는가?

**직접 작성한 예시**

```java
List<InvoiceReply> findUnpaidInvoices(CustomerId customerId) {
    return invoices.findUnpaid(customerId);
}
```

**적용 설명:** HTTP GET이라는 이유만으로 모든 메서드를 read로 부르지 않는다.

## 구체적인 검토 사례

- [ ] GET 요청이라는 이유로 조회 메서드를 모두 read로 명명하기보다 조회 대상과 역할을 드러내는 이름을 사용하자는 제안이다. (개선 제안)
  - 조건: 작성자는 HTTP 메서드에만 맞춰 이름을 정했다고 설명하고, read뿐 아니라 컨트롤러 메서드 전반을 의도가 드러나도록 변경했다고 보고했다.

- [ ] 서로 다른 조회 메서드를 모두 read로 명명하기보다 findAll과 findAvailableTimes처럼 역할이 드러나는 이름을 사용하도록 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 먼저 read의 의미와 같은 이름의 두 메서드가 같은 동작을 하는지 질문한 뒤 구체적인 이름을 제안했다. 작성자는 GET 매핑에 read라는 명명 관례가 있다고 오해했다며, 의도가 드러나도록 컨트롤러 메서드명을 수정했다고 보고했다.

- [ ] 조회 메서드의 이름을 find와 get의 구분 기준에 따라 일관되게 정하면 읽기 편하다는 명명 관례를 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 보편적인 원칙이 아닌 개인적으로 사용하는 컨벤션이라고 명시했다. 작성자는 값의 존재가 필요한 DAO 메서드를 구분하고 팀 컨벤션으로 협의할 수 있겠다고 답했다. 링크 본문에만 있을 구체적인 구분 규칙은 추출하지 않았다.
