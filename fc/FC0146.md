# FC0146 · 인터페이스를 분리한 뒤에도 알고리즘 변경 시 서비스 내부 구현을 수정해야 하는 의존 구조를 검토하고, OCP 관점에서 교체 가능한 구조를 고민하도록 제안한다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0149 →](FC0149.md)

- [ ] 인터페이스를 분리한 뒤에도 알고리즘 변경 시 서비스 내부 구현을 수정해야 하는 의존 구조를 검토하고, OCP 관점에서 교체 가능한 구조를 고민하도록 제안한다. (개선 제안)
  - 조건: 리뷰 참여자는 클래스 분리로 가독성과 테스트 용이성이 좋아졌다고 평가하면서도 남은 변경 의존성을 지적했다. 인터페이스 타입의 저장소에 여러 구현체를 연결하는 예시와 비교하고 OCP를 학습하도록 권했으며, 후속 구현 결과는 제시되지 않았다.

- [ ] 경로 도메인이 외부 라이브러리에 직접 의존하므로, 알고리즘 구현을 교체할 때 도메인 변경을 줄일 수 있도록 인터페이스로 분리하는 방안을 제안했다. (개선 제안)
  - 조건: 외부 라이브러리를 직접 구현한 알고리즘으로 교체하는 요구사항 변경을 가정한 제안이다. 작성자는 Path와 Graph를 각각 인터페이스로 분리했다고 보고했으며, 실제 변경의 적절성은 이 답변만으로 확인되지 않는다.

- [ ] 리플렉션으로 생성자를 찾는 대신 함수형 인터페이스로 객체 생성 방법을 주입하여 RowMapper를 구현하는 방안을 제안했다. (개선 제안)
  - 조건: 레벨 2에서 JdbcTemplate과 RowMapper를 사용했던 경험을 떠올려 보라는 학습 맥락의 제안이다. 리플렉션도 가능한 방법이라고 인정하면서 대안을 제시했으며, 작성자의 답변이나 적용 결과는 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
final class RouteService {
    private final PathFinder finder;
    RouteService(PathFinder finder) { this.finder = finder; }
    Path route(Node a, Node b) { return finder.find(a, b); }
}
```

**적용 설명:** 알고리즘 교체 시 서비스 내부 분기가 바뀌지 않는지 확인한다.
