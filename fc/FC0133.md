# FC0133 · 예약 시간을 삭제할 때 연결된 예약까지 삭제해야 하는 요구사항이 있는지 확인하고, 예약이 남아 있으면 오류로 삭제를 막는 방안을 제안했다.

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0131](FC0131.md) · [다음 FC: FC0132 →](FC0132.md)

- [ ] 예약 시간을 삭제할 때 연결된 예약까지 삭제해야 하는 요구사항이 있는지 확인하고, 예약이 남아 있으면 오류로 삭제를 막는 방안을 제안했다. (개선 제안)
  - 조건: 작성자는 명시적인 요구사항은 없으며, 시간 삭제가 관련 예약 전체 삭제 의도를 포함한다는 동료들의 의견에 따라 구현했다고 설명했다. 본래는 참조 무결성에 따른 예외 발생을 선호했고, 리뷰 후 그 방향으로 다시 구현할 의사를 밝혔다. 실제 변경 여부는 확인되지 않는다.

- [ ] 예약이 연결된 테마의 삭제 처리도 사용 중인 예약 시간의 삭제 제한과 일관된 정책으로 검토하자는 제안이다. (개선 제안)
  - 조건: 참여자는 ReservationTimeService에는 사용 여부 검증이 있지만 ThemeService에는 유사한 검증이 없다고 지적하고 삭제 결과를 물었다. 작성자는 DB 제약 오류가 발생한다고 설명하며 애플리케이션 검증과 명시적인 오류 처리를 추가하겠다고 답했다. 실제 변경 완료는 이 대화에서 확인되지 않는다.

- [ ] 참조 중인 예약 시간의 삭제 정책을 설계해보고, 이번 구조에서는 연관 예약까지 삭제하기보다 삭제를 거부하는 방식을 우선 검토하도록 제안한다. (개선 제안)
  - 조건: 참여자는 CASCADE, 참조 시 거부, soft delete를 대안으로 들되 반영한다면 거부 방식이 현실적이라고 했다. 작성자는 데이터 손실 우려로 CASCADE에 반대하고 거부 정책을 선택하겠다고 답했다. 후속 설명에서는 soft delete가 분쟁 대비·감사·통계·복구 등에 쓰이지만 이번 미션에는 적용하지 않아도 된다고 범위를 정했다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
FOREIGN KEY (slot_id) REFERENCES slot(id) ON DELETE RESTRICT
```

**적용 설명:** 참조 중인 슬롯 삭제를 막는 테이블 제약 조각이다. 자동 연쇄 삭제는 실제 요구가 있을 때만 선택한다.
