# FC0126 · 인기 테마를 하나의 쿼리로 조회한 이유와, 예약 조회 후 테마 ID로 테마를 일괄 조회하는 대안을 검토했는지 논의했다.

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0123](FC0123.md) · [다음 FC: FC0127 →](FC0127.md)

- [ ] 인기 테마를 하나의 쿼리로 조회한 이유와, 예약 조회 후 테마 ID로 테마를 일괄 조회하는 대안을 검토했는지 논의했다. (토론)
  - 조건: 작성자는 대안을 날짜별 조회로 이해해 최소 7번 이상의 쿼리가 발생할 수 있고 조인 한 번이 더 효율적이라고 설명했다. 리뷰 참여자는 일주일 예약을 theme_id 기준으로 정렬한 뒤 테마 ID들을 `findAllByIdIn` 형태로 조회하는 방안을 생각했다고 명확히 했으며, 변경 요구가 아니라 다른 구현 방법도 고려했는지 묻는 의도였다고 밝혔다. 어느 방식의 성능이 우수한지는 확인되지 않았다.

- [ ] 인기 테마 집계는 전날까지의 예약을 대상으로 해야 하는데, 오늘을 endDate로 전달하고 쿼리에서도 이를 포함해 요구된 날짜 범위를 벗어난다고 지적했다. (문제 보고)
  - 조건: 리뷰 참여자는 오늘이 5월 8일이면 5월 1일부터 7일까지 집계해야 한다는 미션 예시를 근거로 들었다. 클라이언트가 오늘을 넘기는 것으로 보인다는 표현이 포함되어 있다. 작성자는 지적에 수긍했지만 변경된 쿼리나 동작 결과는 제시하지 않았다.

- [ ] 날짜에 맞게 예약 데이터를 넣어도 인기 테마 조회 API 결과가 계속 비어 있는 문제를 보고했다. (문제 보고)
  - 조건: 리뷰 참여자는 적절한 날짜의 데이터를 넣었는데도 결과가 비어 있다고 설명했다. 작성자는 날짜 데이터 때문인 것 같으며 data.sql을 수정한 뒤 정상 작동한다고 답했다. 원인과 수정 결과는 작성자의 추정 및 보고이며, 이 대화에서 별도로 검증되지는 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
SELECT topic_id, COUNT(*) AS uses
FROM booking GROUP BY topic_id ORDER BY uses DESC, topic_id;
```

**적용 설명:** 집계 후 상세를 일괄 조회하는 방식과 조인 한 번으로 가져오는 방식을 왕복 횟수·중복 전송량으로 비교한다.
