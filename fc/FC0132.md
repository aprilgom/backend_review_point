# FC0132 · 현재 요구에 맞는 DB 제약

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0133](FC0133.md) · [다음 FC: FC0134 →](FC0134.md)

## 검토 질문

- [ ] 미래 변경 가능성만으로 제약을 생략하지 않고 현재의 유일성·필수값·범위 규칙을 보장하는가?

**직접 작성한 예시**

```sql
ALTER TABLE account ADD CONSTRAINT email_unique UNIQUE (email);
ALTER TABLE cart_line ADD CONSTRAINT positive_quantity CHECK (quantity > 0);
```

**적용 설명:** 현재 불변식을 DB에서도 보장한다. 기존 데이터 정리와 마이그레이션 순서를 먼저 확인한다.

## 구체적인 검토 사례

- [ ] 향후 변경을 줄이려는 이유로 DB 제약을 생략하거나 요구사항보다 느슨하게 두기보다, 현재 요구사항과 데이터 무결성에 맞춰 제약을 설정해야 하는지 논의했다. (토론)
  - 조건: 리뷰 참여자는 테마 이름의 유일성 자체는 요구사항에 달렸다고 인정하면서, 유일성이 요구되어도 제약을 생략할 것인지와 이름 길이 제한을 더 넓게 둘 이유를 물었다. 작성자는 과거 스키마 변경 경험과 요구사항 변경 가능성을 이유로 들었으나, 이후 그 경험은 제약조건과 무관한 관계 설계 문제였다고 정정하고 DB 제약의 안전장치 역할에 동의했다. 리뷰 참여자는 제약 추가보다 완화가 문제없는 경우가 많다는 의견을 밝혔고, 마지막에는 일부 제약을 신중하게 설정하는 경우도 있다고 조건을 보완했다. 지적을 철회한 것은 아니다.

- [ ] 현재 예약과 과거 예약내역의 요구 차이를 해소하는 대안으로 별도 이력 테이블을 두고 예약 시점에 두 데이터를 함께 저장하는 방식을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 별도 저장 방식을 가능한 대안 중 하나로 제시했다. 작성자는 예약 완료 여부나 스케줄링에 따른 테이블 이동·처리가 필요하지 않을지 추가로 생각을 밝혔으나, 그 처리가 실제로 필요한지 또는 구현되었는지는 확인되지 않았다.

- [ ] 예약과 예약 대기의 중복을 이유로 하나의 클래스를 사용하는 판단에 대해, 테이블 설계를 다시 고민하고 적용한 뒤 논의하자는 요청이다. (개선 제안)
  - 조건: 작성자는 중복 칼럼·코드와 현재 요구사항 범위를 근거로 한 클래스에 두었다고 설명했다. 리뷰 참여자는 구체적인 대체 스키마를 제시하지 않고 테이블 설계 재검토를 요청했다. 작성자는 구현하면서 문제점을 더 느꼈으며 수정해보겠다고 답했지만, 이 대화에는 최종 설계가 제시되지 않았다.
