# FC0122 · SQL 파라미터의 타입 보존

## 검토 질문

- [ ] 모든 값을 문자열로 바꾸지 않고 대상 SQL 타입에 맞게 바인딩하며 null도 명확히 처리하는가?

**직접 작성한 예시**

```java
statement.setLong(1, accountId);
statement.setBigDecimal(2, amount);
statement.setDate(3, java.sql.Date.valueOf(day));
```

**적용 설명:** 타입에 맞춰 바인딩한다. NULL은 대상 SQL 타입과 함께 setNull로 전달할 수 있다.

## 구체적인 검토 사례

- [ ] 모든 SQL 파라미터를 String으로 변환해 setString으로 바인딩하면 어떤 문제가 생길 수 있는지 질문했다. (설계 질문)
  - 조건: 작성자는 드라이버에 따라 잘못된 결과가 나올 수 있다고 이해하고 타입별 메서드를 사용하도록 변경했다고 보고했다. 다만 떠오르는 타입만 처리했으며 추가 확장은 학습상 의미가 크지 않다고 설명했다. 실제 드라이버별 동작이나 처리 범위의 충분성은 확인되지 않았다.

- [ ] JdbcTemplate에서 SQL 설정에 PreparedStatement를 사용하는 이유를 질문하고, 간단한 파라미터 바인딩 호출도 내부적으로 이를 사용한다는 점을 설명했다. (설계 질문)
  - 조건: 현재 사용 방식이 잘못되었다는 지적은 아니다. 작성자는 SQL 인젝션 방어, 타입 바인딩, 실행 계획 재사용 등을 학습했다고 답했다. 리뷰어는 명시적으로 PreparedStatement를 생성하지 않는 update·query 호출도 내부에서 생성과 바인딩을 수행한다고 설명하며 보안상 이유도 언급했다.

- [ ] SQL 파라미터를 문자열로 변환해 setString으로 설정하는 대신 PreparedStatement.setObject를 활용하는 방안을 제안한다. (개선 제안)
  - 조건: 리뷰어는 setObject가 내부적으로 null을 확인하고 String으로도 변환해 준다는 설명을 제안 근거로 들었다. 이 설명의 기술적 정확성이나 실제 적용 결과는 대화에서 검증되지 않았다.
