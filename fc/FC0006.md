# FC0006 · 저장 구현 사이의 공통 계약

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0023](FC0023.md) · [다음 FC: FC0028 →](FC0028.md)

## 검토 질문

- [ ] 메모리와 데이터베이스 등 서로 다른 저장 구현을 같은 계약으로 교체할 수 있으며, 부재·중복 처리 의미도 일치하는가?

**직접 작성한 예시**

```java
CustomerStore store = useDatabase
    ? new SqlCustomerStore(dataSource)
    : new MemoryCustomerStore();
CustomerService service = new CustomerService(store);
```

**적용 설명:** 서로 다른 저장 구현을 같은 계약으로 교체한다. 두 구현에서 부재·중복 처리 의미도 일치해야 한다.

## 구체적인 검토 사례

- [ ] 메모리와 데이터베이스처럼 서로 다른 저장 방식을 추상화하고 어떤 코드를 왜 재사용할지 고민하는 것을 학습 목표로 제시한다. (학습 제약)
  - 조건: 요구사항의 방향성을 설명한 것으로, 현재 저장 추상화에 구체적인 결함이 있다고 주장하지 않았다.

- [ ] 영속성 계층의 구현 방식 때문에 클라이언트가 DAO와 Repository를 구분하지 않도록 일관된 컴포넌트를 제공하는 방안을 제안한다. (개선 제안)
  - 조건: 작성자는 단일 테이블 대응에는 DAO, 여러 DAO로 도메인을 조립하는 경우에는 Repository를 사용했다고 설명했다. 또한 Order의 1:N 관계를 조립할 때 DAO 간 책임과 비대한 RowMapper를 피하려 했다고 밝혔다. 리뷰 참여자는 이러한 내부 구현 사정과 무관하게 클라이언트에 일관된 접근 방식을 제공하자는 입장을 유지했으며, 최종적으로 반드시 Repository라는 이름만 쓰도록 제한하지는 않았다.

- [ ] 콘솔과 웹 컨트롤러에 각각 구현된 기능에서 공통 컴포넌트를 도출하도록 제안했다. (개선 제안)
  - 조건: 독립적으로 구현된 컨트롤러 기능의 공통화가 관심사이며, 특정 클래스 구조를 정답으로 지정하지는 않았다. 후속 총평의 중복 제거에 대한 칭찬만으로 구체적인 구현 결과를 확정할 수는 없다.
