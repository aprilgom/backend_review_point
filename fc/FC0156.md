# FC0156 · 도메인과 저장 모델의 변환 경계

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0150](FC0150.md) · [다음 FC: FC0152 →](FC0152.md)

## 검토 질문

- [ ] 도메인이 저장 엔티티를 알아야 하는 구조를 피하고 변환을 적절한 어댑터에 배치했는가?

**직접 작성한 예시**

```java
Customer toDomain(CustomerRow row) {
    return new Customer(new CustomerId(row.id()), row.name());
}
```

**적용 설명:** 매핑을 저장 어댑터에 두면 도메인이 DB 엔티티를 알 필요가 없다.

## 구체적인 검토 사례

- [ ] 도메인 Member가 MemberEntity를 받아 변환하면 MemberEntity의 변경이 도메인에 영향을 준다는 의존성 문제를 짚었다. (위험 지적)
  - 조건: 작성자는 영속성 엔티티와 도메인을 분리하는 과정에서 타협한 부분이며, 테이블과 일대일 대응하는 Entity는 변경이 적을 것으로 예상했다고 설명했다. 이후 해당 부분을 제거했다고 보고했지만 실제 변경 결과는 확인되지 않는다.

- [ ] 도메인이 외부 라이브러리에 직접 의존하면 라이브러리 변경으로 도메인도 변경될 수 있으므로, 인터페이스를 통한 의존성 역전을 검토하도록 했다. (토론)
  - 조건: 처음에는 도메인과 라이브러리·인프라의 관계 및 직접 의존의 문제를 생각해 보라는 질문이었다. 작성자는 PathStrategy 인터페이스에 의존하도록 변경했다고 보고했고, 리뷰 참여자는 후속 답변에서 외부 라이브러리 변경의 영향을 줄이려는 의도였으며 인터페이스 기반 DIP가 그 방법이라고 설명했다. 실제 변경 코드의 동작까지 검증된 것은 아니다.

- [ ] 도메인이 프레임워크에 의존하거나 빈으로 관리되는 것이 왜 잘못이라고 생각하는지, 구체적으로 어떤 문제가 생기는지 설명을 요청했다. (설계 질문)
  - 조건: 리뷰어는 최초 설명만으로 고민의 대상을 파악하기 어렵다고 전제했으며, 도메인의 빈 등록을 금지하거나 권장한 것은 아니다. 작성자는 도메인 영역을 직접 관리해야 한다는 관점과 상태가 자주 바뀌는 도메인의 빈 관리에 대한 우려를 설명하고, Configuration과 의존 객체 등록은 더 학습하겠다고 답했다. 이 설명의 기술적 타당성에 대한 후속 판단은 없다.
