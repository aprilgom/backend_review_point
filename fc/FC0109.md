# FC0109 · 예약과 대기의 API가 분리된 상태에서 예약 취소와 해당 슬롯의 대기 신청이 동시에 발생해도 문제가 없는지 검토하도록 요청했다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0108](FC0108.md) · [다음 FC: FC0097 →](FC0097.md)

- [ ] 예약과 대기의 API가 분리된 상태에서 예약 취소와 해당 슬롯의 대기 신청이 동시에 발생해도 문제가 없는지 검토하도록 요청했다. (위험 지적)
  - 조건: 작성자는 unique 제약과 트랜잭션 처리로 보완하고 createWaiting에서 예약 존재 여부를 서버 측에서 검증하도록 추가했다고 보고했다. 다만 두 요청이 동시에 진입하는 레이스 컨디션은 남아 있어 사이클 2의 대기→예약 전환 로직 구현 시 함께 처리할 예정이라고 명시했다.

- [ ] 예약 변경 시 새 슬롯에만 락을 걸면 기존 슬롯의 대기 승격과 다른 예약 요청이 경합할 수 있다는 우려다. (위험 지적)
  - 조건: 예약 이동으로 비게 되는 기존 슬롯에 다른 요청이 동시에 들어오는 상황을 지적한 것으로, 실제 경합 발생이나 후속 수정 여부는 확인되지 않는다.

- [ ] 이미 예약된 슬롯에 예약을 시도하면 자동으로 예약 대기로 넘겨야 한다는 요구사항이 추가될 경우, 현재의 동시성 처리 방식을 어떻게 확장할지 질문했다. (설계 질문)
  - 조건: 작성자의 제약조건 기반 충돌 처리와 비관적 락 회피 설명에 대한 가정적 질문이다. 작성자는 서비스 선검증으로 기존 예약을 확인해 대기를 등록하고, 경합 시 DuplicateKeyException을 재시도하여 선검증에서 대기로 전환하는 방안을 선호한다고 답했다. 예외 처리에서 직접 대기를 등록하는 대안도 언급했으나 서비스 복잡성 때문에 덜 선호했으며, 실제 구현을 완료했다고 보고한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
BEGIN;
SELECT id FROM slot WHERE id = :id FOR UPDATE;
-- 같은 슬롯의 취소와 대기 등록 모두 이 잠금을 먼저 획득
UPDATE reservation SET state = 'CANCELLED' WHERE id = :reservation_id;
COMMIT;
```

**적용 설명:** 서로 다른 API도 공유 자원의 정합성 규칙은 같아야 한다. 대기 승격·등록의 실제 변경 로직은 생략했다.
