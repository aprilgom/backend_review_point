# FC0016 · 반복 처리 규칙의 공통화

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0034](FC0034.md) · [다음 FC: FC0010 →](FC0010.md)

## 검토 질문

- [ ] 응답 구성이나 자원 처리에서 반복되는 규칙과 달라지는 동작을 분리해 중복을 줄일 수 있는가?

**직접 작성한 예시**

```java
record ErrorReply(int status, String code) {}
ErrorReply mapFailure(AppFailure failure) {
    return new ErrorReply(failure.status(), failure.publicCode());
}
```

**적용 설명:** 반복 응답 구성의 공통 규칙만 독립 함수로 표현했다. 프레임워크 예외 처리 등록은 생략하고 안전한 공개 코드만 반환한다.

## 구체적인 검토 사례

**혼합·경계:** ControllerAdvice 외에 템플릿·콜백과 Auditing 사례가 섞임.

- [ ] ControllerAdvice의 상태 코드별 응답 구성에서 반복되는 규칙을 활용해 코드를 줄여 볼 것을 제안했다. (개선 제안)
  - 조건: 리뷰어는 반복 규칙이 보인다는 수준으로 제안했으며, 구체적인 추출 방식이나 구현 결과는 제시되지 않았다.

- [ ] 중복된 트랜잭션 처리 코드를 템플릿 메서드로 묶고, 달라지는 부분만 콜백으로 받는 방식을 제안했다. (개선 제안)
  - 조건: TxUserService의 반복 코드에 대한 제안이며, 작성자의 응답이나 반영 결과는 제시되지 않았다.

- [ ] 생성 시각을 직접 설정하는 생명주기 콜백 대신 프레임워크의 Auditing 기능을 사용할지 논의한다. (토론)
  - 조건: 리뷰어는 Auditing 사용을 제안하고, 기능이 같다면 프레임워크 기능을 쓰지 않을 이유를 재차 물었다. 작성자는 공통 상위 클래스의 콜백으로 기능을 제공할 수 있고 재호출 시 시각 변경을 막는 조건을 추가했다고 설명했다. 또한 Auditing 활성화에 필요한 추가 어노테이션과 다른 Auditing 기능의 불필요성을 들어 기존 방식을 유지하겠다고 답했다. 기능적 동등성은 작성자의 설명이며, 합의나 실제 동작 검증은 확인되지 않았다.
