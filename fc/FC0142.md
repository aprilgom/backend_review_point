# FC0142 · Section이 Line과 Station의 ID만 보유하기보다 해당 객체를 직접 보유하는 관계 표현을 제안한다.

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0141](FC0141.md) · [다음 FC: FC0143 →](FC0143.md)

- [ ] Section이 Line과 Station의 ID만 보유하기보다 해당 객체를 직접 보유하는 관계 표현을 제안한다. (개선 제안)
  - 조건: 더 나은 설계인지 묻는 형태의 제안이며, ID 참조 방식이 실제 결함이라는 근거나 변경 결과는 제시되지 않았다.

- [ ] Section이 LineId를 갖는 방식도 결국 Line과 Section의 관계를 설정하는 것이 아닌지 질문한다. (설계 질문)
  - 조건: 작성자는 양방향 객체 참조를 피하기 위해 Line 객체 대신 LineId를 선택했다고 설명했다. 리뷰 참여자는 객체 참조를 피하는 것과 관계 자체를 없애는 것을 구별하도록 질문했으며, 이후 답변이나 설계 변경은 없다.

- [ ] Section이 역과 노선의 ID만 보유하는 대신 Station과 Line 객체를 참조하도록 설계를 바꾸는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 DB를 의식하지 않았다면 어떤 필드를 가졌을지 질문하며 객체 참조 예시를 제시했고, 비대한 서비스에 대한 작성자의 고민도 이 변경을 검토한 뒤 다시 논의하자고 했다. 작성자는 처음에는 Station을 보유할 필요를 느끼지 못했으나, 역 이름 조회에 추가 쿼리와 긴 서비스 로직이 필요해져 Station 참조가 더 낫다고 판단했다고 답했다. 실제 변경 완료나 Line 참조 채택 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record Segment(Station start, Station end) {
    boolean touches(Station station) { return start.equals(station) || end.equals(station); }
}
```

**적용 설명:** 구간이 역의 동작과 협력할 때 객체 참조가 의미를 드러낸다. 객체 그래프 크기·로딩 비용과 동등성 계약이 전제다.
