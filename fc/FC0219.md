# FC0219 · 구성 값 사이의 관계 검증

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0218](FC0218.md) · [다음 FC: FC0223 →](FC0223.md)

## 검토 질문

- [ ] 개별 값이 유효해도 조합이 잘못될 수 있는 규칙을 객체 생성 경계에서 확인하는가?

**직접 작성한 예시**

```java
record Segment(StationId start, StationId end) {
    Segment { if (Objects.equals(start, end)) throw new SameEndpoint(); }
}
```

**적용 설명:** 서로 다른 양 끝점이라는 규칙을 생성 시 보장한다. null 허용 여부와 이름 대신 ID로 비교할지도 정한다.

## 구체적인 검토 사례

- [ ] 구간의 두 역 이름이 중복되는지 검사하는 유효성 검증을 Section 객체 생성 시 수행하면 어떨지 제안했다. (개선 제안)
  - 조건: LineService의 validateStationsNames에 달린 제안이다. 실제 책임 이동이나 구현 결과는 대화에서 확인되지 않는다.

- [ ] 요청을 파싱해 추출한 값의 유효성을 검증하고, 별도 객체에 검증을 위임하거나 현재 위치에서 검증하는 방식을 제안했다. (개선 제안)
  - 조건: 별도 객체 생성은 유일한 요구가 아니라 검증 구현의 대안으로 제시되었다. 작성자는 RequestLine에 대해 URL·QueryParameter를 포함하는 Path 객체와 ProtocolVersion 객체를 추가해 값을 검증하고, RequestHeader와 RequestBody는 입력 형식만 검증하도록 두었다고 보고했다. 이 범위가 충분한지에 대한 후속 판단은 없다.

- [ ] 역 이름 입력 검증을 클라이언트와 서버 양쪽에서 처리하고, 두 곳에서 검증해야 하는 이유를 생각해 보도록 제안했다. (개선 제안)
  - 조건: 대상 코드는 빈 값·공백·숫자 포함 여부를 검사하는 클라이언트 코드다. 작성자는 클라이언트 검증은 빠른 피드백과 불필요한 요청 방지에, 서버 검증은 지정된 클라이언트를 거치지 않는 요청에 대한 데이터 보호에 필요하다고 설명했다. 후속 칭찬은 서버 검증 구현 완료의 근거로 보지 않는다.
