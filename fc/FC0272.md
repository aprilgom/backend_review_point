# FC0272 · 대기 순번 계산의 성능 우려를 구체화하고, 실제 쿼리 실행 계획을 확인한 뒤 데이터베이스 최적화 가능성을 검토하자는 제안이다.

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0281](FC0281.md) · [다음 FC: FC0279 →](FC0279.md)

- [ ] 대기 순번 계산의 성능 우려를 구체화하고, 실제 쿼리 실행 계획을 확인한 뒤 데이터베이스 최적화 가능성을 검토하자는 제안이다. (개선 제안)
  - 조건: 작성자는 단건 조회에도 해당 슬롯의 모든 데이터를 조회해야 하는 부담을 우려했다. 리뷰 참여자는 모든 데이터를 읽어야 한다는 전제가 불명확하다고 되물었고, 실행 계획에서 전체 탐색이 확인되는 경우 인덱스나 파티션 등을 검토할 수 있다고 설명했다. 해결책은 실행 계획과 비즈니스 로직에 따라 다르며, 실제 성능 문제나 전체 탐색 여부는 확인되지 않았다.

- [ ] 주문 생성 과정에서 계산 결과까지 저장하면 주문 성공 확인이 늦어질 수 있으므로, 이 방식을 택한다면 계산을 비동기로 처리하는 방안을 제안했다. (조건부 제안)
  - 조건: 계산 후 DB에 저장하는 설계를 선택하는 경우에 대한 제안이다. 실제 응답 지연이 측정되거나 비동기 처리가 구현되었다는 근거는 없다.

- [ ] 데이터가 많아질 경우 조회 성능을 고려해 관련 내용을 학습하고 프로젝트에 적용해 보도록 제안했다. (조건부 제안)
  - 조건: 리뷰 참여자는 향후 데이터 증가를 조건으로 참고용 조언을 남겼으며, 현재 성능 결함이나 특정 최적화 방법을 확정하지 않았다. 작성자는 존재 여부 조회에서 * 대신 단일 컬럼을 사용하도록 수정했다고 보고했지만, 이 변경의 성능 효과는 대화에서 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
EXPLAIN SELECT COUNT(*) FROM waiting
WHERE slot_id = :slot AND created_at < :created_at;
```

**적용 설명:** 실제 데이터 분포로 실행 계획·인덱스·조회 건수를 확인한다. DB별 EXPLAIN 구문과 실행 여부는 구별한다.
