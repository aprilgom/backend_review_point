# FC0449 · 외부 API의 실제 동작을 확인하면서도 반복 실행 테스트가 외부 서버 상태나 호출 제한에 좌우되지 않도록 테스트 실행 방식을 고민하자는 논의다.

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0448](FC0448.md) · [다음 FC: FC0437 →](FC0437.md)

- [ ] 외부 API의 실제 동작을 확인하면서도 반복 실행 테스트가 외부 서버 상태나 호출 제한에 좌우되지 않도록 테스트 실행 방식을 고민하자는 논의다. (토론)
  - 조건: 작성자는 예외 처리 검증에는 MockRestServiceServer를 사용하되 실제 호출 테스트도 명세 변경이나 장애 확인에 필요하다고 주장했다. 리뷰 참여자는 최초 연동이나 수정 시 실제 호출의 필요성에는 동의하면서 매번 실행할 필요는 없다고 설명했다. 작성자는 유효한 PaymentKey 확보의 어려움 때문에 잘못된 키의 오류 응답을 확인하는 테스트와 @Disabled를 통한 선택 실행을 제안했다. 후속 답변은 운영 서버 직접 호출의 제약과 테스트 서버·키 제공 여부를 조건으로 들며, @Disabled 처리 후 필요할 때 직접 실행하는 방식을 수용했다. 실제 테스트 추가나 실행 결과는 제시되지 않았다.

- [ ] 외부 서비스 문제 때문에 전체 테스트 실행이 영향을 받는 것이 불필요하다면, 실제 외부 API 테스트를 로컬에서만 실행하고 비활성화해 두는 방안을 제안했다. (조건부 제안)
  - 조건: 외부 서비스의 장애는 자체 서비스의 문제와 다르다는 이유로 제시한 선택지다. 전체 테스트에 포함할 필요가 없다고 판단하는 경우에 한해 로컬 실행과 `@Disabled` 사용을 제안했으며, 실제 적용 여부는 언급되지 않았다.

- [ ] 실제 외부 API 상태에 따라 테스트가 실패하지 않도록 외부 호출과 독립적인 테스트 구성을 제안했다. (토론)
  - 조건: 작성자는 모킹 테스트와 실제 호출 테스트의 결과를 비교하면 내부 문제와 외부 API 문제를 구분하기 쉽고, 테스트용 URL의 반복 호출도 문제없다고 판단했다고 반론했다. 리뷰 참여자는 테스트가 항상 같은 결과를 내야 한다는 의미로 '멱등성'을 언급하며 외부 요인으로 실패하지 않아야 한다는 입장을 유지했다. 실제 호출 테스트의 변경 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
@Tag("external-contract")
@Test void remoteSandboxMatchesContract() { verifyRemoteContract(); }
```

**적용 설명:** 외부 연동 확인을 별도 태그로 분리하고 일반 테스트는 통제된 대역을 사용한다. 자격증명·호출 제한·실행 조건을 명시한다.
