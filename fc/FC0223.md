# FC0223 · 생성 시 보장한 제약의 재검증

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0219](FC0219.md) · [다음 FC: FC0226 →](FC0226.md)

## 검토 질문

- [ ] 이미 유효성이 보장된 불변 값을 받을 때 같은 검증을 반복할 필요가 있으며 외부 상태 의존 검증과 구분하는가?

**직접 작성한 예시**

```java
void changeQuantity(Quantity quantity) {
    this.quantity = Objects.requireNonNull(quantity);
}
```

**적용 설명:** Quantity가 생성 시 양수 조건을 보장하는 불변 값이면 같은 수치 검사를 반복하지 않을 수 있다. 재고 같은 외부 상태 검증은 별개다.

## 구체적인 검토 사례

- [ ] 생성 시 검증으로 보장할 수 있다면 예약 변경 메서드의 검증이 불필요하지 않은지 논의했다. (조건부 제안)
  - 조건: 작성자는 생성 시 과거 날짜로 예약하는 것을 막는 검증과, 시간이 지나 과거가 된 기존 예약의 변경을 막는 검증은 목적이 다르다고 반론했다. 리뷰 참여자는 다른 스레드를 참조하며 필드 추가와 불변 객체 생성 시 검증을 전제로 불필요할 수 있다고 재질문했다. 이 단위에는 해당 필드 설계의 구체적 맥락이 없고, 지적을 철회한 것은 아니다.

- [ ] 생성자에서 이미 수행하는 검증 메서드를 불필요하게 중복 호출하고 있으므로 해당 호출을 제거해 달라고 요청했다. (문제 보고)
  - 조건: 중복 호출이라는 문제는 리뷰 참여자의 지적이다. 작성자는 작업 중 제거하지 못한 부분이라고 답했으나, 실제 제거 결과는 이 대화만으로 확인되지 않는다.

- [ ] 유효성 검증을 도메인 이벤트로 수행하면 검증 실패를 저장 호출 시점까지 늦추게 되므로 적절하지 않다는 의견을 제시했다. (의견)
  - 조건: 리뷰 참여자는 JPA Repository의 save·delete 호출 시 이벤트가 발송되어, 도메인이 이미 유효하다고 간주한 뒤 저장 단계에서 실패하고 롤백할 수 있다고 설명했다. 이는 참여자의 기술적 설명이며 이 대화에서 검증되지는 않았다.
