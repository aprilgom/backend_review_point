# FC0110 · 작업 실행에 submit() 대신 execute()를 선택한 이유를 질문했다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0097](FC0097.md) · [다음 FC: FC0111 →](FC0111.md)

- [ ] 작업 실행에 submit() 대신 execute()를 선택한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 결과 확인용 Future가 필요하지 않아 execute()를 사용했다고 설명했다. 이후 참여자는 구두 논의를 바탕으로 submit()으로 변경했다고 언급했지만, 구두 논의 내용과 변경 판단의 근거는 제공되지 않았다. submit()이 반드시 적합하다는 결론이나 실제 변경 결과를 확정할 수 없다.

- [ ] 작업 실행에 execute 대신 submit을 선택한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 반환 결과와 예외 발생 시 스레드 재사용의 차이를 근거로 설명했으며, 현재는 작업 결과가 필요하지 않아 execute를 사용해도 무방할 것 같다고 답했다. 이 설명의 기술적 타당성이나 변경 여부는 확인되지 않았다.

- [ ] 요청 처리 작업을 execute 대신 submit으로 실행한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 반환값이 없으므로 Future를 받는 방식보다 void 반환 방식이 좋겠다는 의견을 밝혔다. 리뷰 참여자의 질문을 submit 사용이 확정적인 결함이라는 지적으로 바꾸지 않으며, 실제 변경 여부도 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Future<Result> result = executor.submit(this::calculate);
try { consume(result.get()); }
catch (ExecutionException failed) { report(failed.getCause()); }
```

**적용 설명:** 결과·실패를 회수해야 하면 Future를 관찰한다. InterruptedException은 상위에 전파하거나 인터럽트를 복원한다.
