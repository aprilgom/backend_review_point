# FC0381 · 조회 실행과 변경 실행의 계약

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0376](FC0376.md) · [다음 FC: FC0371 →](FC0371.md)

## 검토 질문

- [ ] 목록 결과를 만드는 조회와 변경 건수를 반환하는 실행을 구분해 서로 다른 책임을 명확히 했는가?

**직접 작성한 예시**

```java
List<User> queryUsers(String sql, StatementBinder binder) { /* 조회 */ }
int executeChange(String sql, StatementBinder binder) { /* 변경 건수 */ }
```

**적용 설명:** 조회 결과와 변경 건수의 계약을 분리한 시그니처 조각이다. 본문은 생략했으므로 그대로 컴파일되는 구현은 아니다.

## 구체적인 검토 사례

- [ ] 조회 결과를 리스트로 반환하는 로직과 executeUpdate 실행 로직이 한 메서드에 있으므로 두 역할을 분리하는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 분리에 대한 의견을 물었다. 작성자는 SELECT 처리와 INSERT·UPDATE·DELETE 처리를 분리했다고 보고했으나, 실제 변경의 적절성이나 결과가 이 대화에서 확인되지는 않는다.

- [ ] 기존 로직을 core 모듈 하나로 옮기는 것만으로는 모듈화의 장점을 살리기 어려울 수 있으므로 모듈을 더 나누는 방안을 제안했다. (개선 제안)
  - 조건: core 분리를 선택했다면 api·common·web 같은 역할별 분리나 컨텍스트별 분리도 가능하다는 제안이었다. 후속 댓글에서 참여자는 application과 api가 분리된 것으로 언급했으나, 이것만으로 모듈화의 효과가 검증된 것은 아니다.

- [ ] HandlerExecution 내부의 조건별 인자 처리 로직을 ArgumentResolver로 분리하면 더 깔끔해질 것이라는 제안이다. (개선 제안)
  - 조건: 특정 조건에 대한 처리를 분리하자는 의견이며, 구체적인 분리 범위나 구현 결과는 제시되지 않았다.
