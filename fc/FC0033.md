# FC0033 · 함수형 인터페이스의 실제 활용

## 검토 질문

- [ ] 단일 동작을 표현하는 인터페이스를 람다·콜백으로 활용하며 별도 타입을 둔 이유가 드러나는가?

**직접 작성한 예시**

```java
StatementBinder binder = statement -> statement.setLong(1, userId);
sqlRunner.query(sql, binder, mapper);
```

**적용 설명:** StatementBinder는 SQLException을 허용하는 자체 함수형 인터페이스다. 단일 동작 계약을 람다 사용처와 연결한다.

## 구체적인 검토 사례

- [ ] PreparedStatementSetter를 함수형 인터페이스로 정의했지만 그 특성을 활용하지 않는 것으로 보이는데, 그렇게 정의한 이유가 무엇인지 질문했다. (설계 질문)
  - 조건: 리뷰 참여자가 선언 방식과 사용 방식의 차이에 대해 설명을 요청한 것이다. 함수형 인터페이스 선언이 잘못되었다고 확정하거나 특정 사용 방식으로 변경하라고 명시하지는 않았다.

- [ ] PreparedStatementSetter를 인터페이스로 분리한 이유와 그 추상화가 현재 구현에 필요한지 검토한다. (토론)
  - 조건: 리뷰어는 인터페이스화 자체가 클린 코드를 보장하지 않는다고 보고, 미션에서는 불필요한 추상 메서드 구현을 없애려는 목적이었다고 설명했다. 가변인자 도입 후 자신은 인터페이스를 삭제했다는 사례이지 삭제 요구는 아니다. 작성자는 후속 설명에서 타입별 처리 등 사용자 정의 가능성을 열어두려는 의도라고 밝혔다.

- [ ] PreparedStatement에 직접 값을 설정하는 방식과 비교하여 PreparedStatementSetter를 도입하면 어떤 장점이 있는지 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 기존 방식도 괜찮아 보인다며 도입 이점을 질문했으며, 불필요한 추상화라고 단정하지 않았다. 작성자는 값 설정 로직을 추상화하여 해당 로직이 바뀌어도 JdbcTemplate을 수정하지 않을 수 있다고 설명했다.
