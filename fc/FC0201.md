# FC0201 · API 문서화에 Swagger를 선택한 이유와 REST Docs를 대안으로 고려했는지 설명을 요청한다.

[소속 분야: 문서·개발·학습 과정](../10-workflow.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0197](FC0197.md) · [다음 FC: FC0200 →](FC0200.md)

- [ ] API 문서화에 Swagger를 선택한 이유와 REST Docs를 대안으로 고려했는지 설명을 요청한다. (설계 질문)
  - 조건: Swagger 사용을 결함으로 지적하거나 REST Docs로 전환하라고 요구한 것은 아니다. 작성자는 초기 프론트엔드 협업을 위한 빠른 구축, 수동 문서의 수정 비용과 불일치 우려, 익숙하지 않은 REST Docs의 구현 복잡도를 고려했다고 설명했다. 또한 Swagger 문서를 빠르게 배포해 공유하는 방식을 선호한다고 답했으며, 이는 작성자의 선택 근거다.

- [ ] Swagger와 REST Docs의 장단점을 비교해 댓글로 정리하고, 하나를 선택해 API 문서화를 자동화하도록 요청했다. (개선 제안)
  - 조건: 작성자는 프로덕션 코드와의 분리 및 테스트 기반 문서의 신뢰성을 이유로 REST Docs를 선택해 적용했다고 보고했다. 리뷰 참여자는 그 장점을 인정하면서도, 자신의 팀에서는 테스트 작성 시간과 관리 편의성, API 개발 시 문서가 바로 갱신되는 점 때문에 Swagger를 쓴다고 설명하고 다음에는 Swagger도 적용해 보길 권했다. 한 도구가 항상 우월하다는 결론은 아니다.

- [ ] Swagger나 REST Docs 적용이 선택 사항인지 확인하고, 시간이 된다면 API 문서 도구를 학습해 볼 것을 제안했다. (개선 제안)
  - 조건: 작성자는 필수 요구사항이 아니며 빠른 협업을 위해 노션으로 명세를 작성하고 리뷰용으로 옮겼다고 설명했다. Swagger는 추가 학습이 필요해 아직 적용하지 않았다고 답했다. 리뷰어의 후속 제안은 시간이 있을 때 학습하라는 권고이며 이번 미션의 필수 적용 요구는 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```yaml
openapi: 3.0.3
info: {title: Sample API, version: "1"}
paths:
  /health:
    get:
      responses:
        '200': {description: Service is ready}
```

**적용 설명:** API 명세 조각이다. 명세 중심 문서와 테스트에서 생성하는 문서를 동기화 비용·사용자·검증 방식으로 비교한다.
