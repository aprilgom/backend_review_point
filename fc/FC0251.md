# FC0251 · 오류 본문과 실제 응답 상태

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0250](FC0250.md) · [다음 FC: FC0249 →](FC0249.md)

## 검토 질문

- [ ] 본문에만 실패를 적지 않고 실제 HTTP 상태도 오류 계약과 일치시키는가?

**직접 작성한 예시**

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{"code":"ITEM_NOT_FOUND"}
```

**적용 설명:** 본문 오류 코드뿐 아니라 실제 HTTP 상태도 실패 계약에 맞춘다.

## 구체적인 검토 사례

- [ ] 예외가 발생했을 때 HTTP 오류 상태를 담은 에러 응답을 내려주는 방식을 제안했다. (개선 제안)
  - 조건: 400 Bad Request는 참고 예시로 언급되었으며 모든 예외를 400으로 처리하라는 요구는 아니다. 작성자는 catch로 예외를 잡아 응답하도록 바꿨다고 보고하면서 ControllerAdvice를 사용할 수 없어 혼란스럽다고 설명했다. 실제 응답과 예외별 상태 매핑은 확인되지 않는다.

- [ ] 지원하지 않는 HTTP 메서드에 어떤 상태 코드로 응답해야 하는지 찾아보라고 제안했다. (개선 제안)
  - 조건: 작성자는 찾아본 결과로 405 Method Not Allowed를 언급했다. 실제 응답 처리에 반영했는지는 이 대화에서 확인되지 않는다.

- [ ] 대부분의 API 실패를 동일한 공통 alert로 처리하기보다 HTTP 상태 코드나 오류 코드에 따라 적절한 메시지를 표시하는 방식을 참고하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 오류 코드를 프론트엔드 메시지에 매핑하면 페이지 내 표시 영역의 여백·줄바꿈과 다국어 요구에 대응할 수 있다고 설명했다. 현재는 alert를 사용하며, 이번 변경의 필수 요구가 아니라 참고 사항이라고 명시했다.
