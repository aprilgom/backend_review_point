# FC0184 · 확장 가능한 외부 연동 입력 계약

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0173](FC0173.md) · [다음 FC: FC0181 →](FC0181.md)

## 검토 질문

- [ ] 새 연동 방식이 다른 입력을 요구할 때 기존 인터페이스를 억지로 구현하지 않아도 되는가?

**직접 작성한 예시**

```java
sealed interface PaymentInput permits CardInput, WalletInput {}
record CardInput(String token) implements PaymentInput {}
record WalletInput(String walletId) implements PaymentInput {}
```

**적용 설명:** 결제수단마다 필요한 입력 차이를 타입에 드러낸다. 지원하지 않는 입력을 구현체에 강제로 넘기지 않는다.

## 구체적인 검토 사례

- [ ] 추가 결제수단에서 요청 내용이 달라질 경우에도 현재 PaymentClient 인터페이스를 그대로 구현할 수 있는지 물었다. (설계 질문)
  - 조건: 새 결제수단 도입을 가정한 확장 가능성 질문이다. 작성자는 PaymentConfirmRequest를 인터페이스로 만들고 TossPaymentConfirmRequest를 구현했으며 공통 요소를 주문 번호와 금액으로 두었다고 보고했다. 이 변경이 모든 결제수단을 수용하는지는 확인되지 않는다.

- [ ] 일반 결제 클라이언트처럼 보이는 PaymentRestClient가 토스에 의존하고 있어, 결제 제공처 교체 시 구현체 의존으로 변경이 발생하지 않을지 묻는다. (설계 질문)
  - 조건: 카카오뱅크로 교체하는 상황을 가정한 질문이다. 작성자는 PaymentClient 인터페이스와 토스 전용 TossPaymentClient 구현체로 분리했다고 보고했다. Rest라는 이름이 내부 구현을 드러낸다는 설명은 작성자의 판단이며 별도의 리뷰 요구로 취급하지 않는다.

- [ ] 외부 결제를 담당하는 PaymentClient가 Toss 구현에 묶여 있어 다른 결제 시스템으로 요구사항이 바뀌면 변경에 취약하지 않은지 우려한다. (위험 지적)
  - 조건: 다른 결제 시스템으로 교체되는 상황을 조건으로 한 우려다. 작성자는 인터페이스와 구현체를 분리해 리팩터링했다고 보고했으나, 실제 교체 가능성이나 구현 결과는 검증되지 않았다.
