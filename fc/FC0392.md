# FC0392 · MemberArgumentResolver의 구현이 인증인지 인가인지, 또는 둘 다인지 질문했다.

[소속 분야: 인증·보안·비밀값](../20-security.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0390](FC0390.md)

**혼합·경계:** ArgumentResolver 사례지만 핵심은 인증·인가 책임 구분.

- [ ] MemberArgumentResolver의 구현이 인증인지 인가인지, 또는 둘 다인지 질문했다. (설계 질문)
  - 조건: 작성자는 쿠키를 확인해 @AuthMember 파라미터에 사용자 정보를 넣는 인증 기능이라고 설명했다. 또한 인가는 AdminCheckInterceptor가 /admin/** 요청에 대해 수행한다고 답했다. 인증·인가 구현의 결함을 확정한 지적은 아니다.

- [ ] JWT가 무엇이며 인증 구현에 JWT를 사용한 이유가 무엇인지 질문했다. (설계 질문)
  - 조건: 작성자는 JWT의 서명된 사용자 정보, 무상태성, 자체 정보 포함 특성과 인증 흐름을 설명하고 Basic Auth, 세션, 일반 무작위 토큰 방식의 장단점을 비교했다. 이 비교는 작성자의 설명이며 리뷰어가 확인한 기술적 사실이나 JWT 선택의 적절성에 대한 확정 평가가 아니다.

- [ ] 사용하지 않는 것으로 보이는 name, role, email을 JWT claim에 넣은 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 토큰이 인증을 얼마나 담당할지 고민하면서 우선 정보를 넣었고 아직 수정하지 못했다고 설명했다. 인증 방식은 subject에서 ID를 추출해 DB의 Member 정보를 조회하는 방식으로 결정했다고 답했으나, claim 제거 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Actor actor = authenticate(request);
requireOwner(actor, document);
return document;
```

**적용 설명:** 누구인지 확인하는 인증과 해당 문서 권한을 확인하는 인가를 분리해 이름 붙인다.
