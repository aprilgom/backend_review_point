# FC0108 · Executors의 여러 스레드 풀 생성 방식 중 FixedThreadPool을 선택한 이유를 질문했다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0099](FC0099.md) · [다음 FC: FC0109 →](FC0109.md)

- [ ] Executors의 여러 스레드 풀 생성 방식 중 FixedThreadPool을 선택한 이유를 질문했다. (설계 질문)
  - 조건: 스레드 풀 종류의 선택 근거를 묻는 별도 관심사이며, 다른 종류가 더 적합하다고 확정하지 않았다.

- [ ] FixedThreadPool이나 CachedThreadPool 대신 ThreadPoolExecutor를 직접 구성한 이유를 물었다. (설계 질문)
  - 조건: 작성자는 스레드 수의 상한을 고정하면서 그 안에서 유동적으로 조정하려는 선택이라고 설명했다. 또한 FixedThreadPool에서 사용하는 LinkedBlockingQueue의 기본 용량이 매우 커 큐가 차지 않으면 최대 스레드 수까지 늘어나지 않는다는 학습 내용을 근거로 들었다. 이는 작성자의 설계 설명이며, 해당 구성이 요구량에 적합하다는 검증 결과는 아니다.

- [ ] newFixedThreadPool 대신 ThreadPoolExecutor를 직접 생성한 이유와 두 방식의 차이를 설명해 달라고 요청한다. (설계 질문)
  - 조건: 작성자는 작업 큐 크기를 기본 설정과 달리 100개로 제한하기 위해 직접 설정했다고 설명했다. 이는 작성자의 설계 설명이며, 큐 제한의 적절성이나 각 인자 설명의 기술적 정확성을 별도로 확정하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
ExecutorService workers = Executors.newFixedThreadPool(4);
// 지속적 입력이라면 기본 무제한 대기열이 메모리를 늘릴 수 있다.
```

**적용 설명:** 고정 스레드 수가 전체 작업량 제한을 뜻하지 않는다. 부하가 제한되지 않으면 유한 대기열과 거절 정책을 고려한다.
