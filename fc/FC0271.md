# FC0271 · 반복문과 스트림의 선택

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0293](FC0293.md) · [다음 FC: FC0296 →](FC0296.md)

## 검토 질문

- [ ] 표현의 가독성과 실제 비용을 비교하고 추측만으로 반복 처리 방식을 최적화하지 않는가?

**직접 작성한 예시**

```java
for (Item item : items) {
    validate(item);
}
```

**적용 설명:** 단순 반복은 읽기 쉬운 표현을 택한다. 스트림·루프의 성능 차이를 근거 없이 일반화하지 않는다.

## 구체적인 검토 사례

- [ ] 단순 반복에서 for와 forEach를 선택할 때 가독성과 컬렉션·스트림 생성 비용이 실제 서비스에 미치는 영향을 논의한다. (토론)
  - 조건: 리뷰 참여자는 가독성 이득 없이 생성 비용이 늘어난다는 이유로 for를 선호했던 기존 생각을 설명했지만, 작성자의 앞선 의견을 듣고 실제 영향은 미미할 수 있다며 그 선호를 재고했다. 앞선 작성자 의견의 상세 내용은 이 단위에 없으며, 성능 차이는 측정된 결과가 아니다. 작성자도 실제 차이는 추후 공부하겠다고 답했다.

- [ ] 리다이렉트 시에는 모델을 request 속성으로 복사할 필요가 없으므로, 해당 연산 전에 리다이렉트를 판단하고 바로 반환하는 방안을 제안한다. (개선 제안)
  - 조건: 작성자는 리다이렉트에서도 request 속성을 사용할 수 있다고 생각해 순서를 바꿨으나, 새 request를 사용한다는 점을 인지하고 수정했다고 답했다. 리뷰어는 forward는 request를 재사용하고 redirect는 재사용하지 않는다는 설명으로 이를 확인했다. 실제 변경 결과를 별도로 검증한 근거는 없다.

- [ ] basePackage 없이 Reflections를 사용하면 불필요한 클래스까지 스캔·로드하게 된다는 점을 들어 스캔 패키지를 명시하는 방식을 선호했다. (의견)
  - 조건: 작성자가 별도 basePackage 주입 없이도 동작하는 이유를 묻자 나온 후속 의견이다. 리뷰어는 인자 없는 경우 프로젝트 전체를 스캔하고, 패키지를 전달하면 해당 범위만 스캔한다고 설명했다. 불필요한 클래스 로드와 내부 구현을 알아야 이해할 수 있다는 점을 선호 근거로 들었으며, 실제 성능 측정이나 기술적 정확성 검증 결과는 제시되지 않았다.
