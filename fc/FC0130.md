# FC0130 · 질문과 답변을 일대일로 설정한 이유를 묻고, 실제 서비스 흐름과 가능한 사례를 검토해 연관관계를 결정할 것을 제안했다.

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0129 →](FC0129.md)

- [ ] 질문과 답변을 일대일로 설정한 이유를 묻고, 실제 서비스 흐름과 가능한 사례를 검토해 연관관계를 결정할 것을 제안했다. (토론)
  - 조건: 리뷰 참여자는 답변이 없는 질문, 여러 답변이 있는 질문, 삭제된 질문의 답변 조회 등을 고려하고 동료와 함께 사례를 검토할 것을 권했다. 작성자는 2단계 문서를 보지 않고 자율적인 부분으로 생각해 일대일로 설정했다고 설명하고 더 꼼꼼히 보겠다고 답했다. 관계 변경 여부는 확인되지 않는다.

- [ ] 연관 객체에 지연 로딩을 선택한 이유와 그로 인해 발생할 수 있는 문제를 질문했다. (설계 질문)
  - 조건: 작성자는 불필요한 연관 객체 조회를 줄이려는 선택이라고 설명하면서 프록시 초기화에 따른 추가 쿼리와 영속성 컨텍스트 밖에서의 지연 로딩 예외 가능성을 언급했다. 리뷰 참여자는 한 번에 필요하지 않은 객체를 모두 로딩할 필요가 없다는 취지에 동의했다. 설명된 문제들이 현재 코드에서 실제 발생했다는 보고는 아니다.

- [ ] 현재 사용처가 확인되지 않는 Question.answers와 양방향 연관관계를 추가한 이유를 검토하고, 실제 사용 필요가 생길 때 매핑을 확장하는 방안도 고려한다. (토론)
  - 조건: PR 작성자가 아닌 참여자 Combi153은 3단계 사용 예상, 외래 키 관리 위치와 추가 update 쿼리의 트레이드오프, 양방향 관계 학습 목적을 설명했다. solarsalt는 이 설명을 인정하면서도, 실제 서비스에서 getAnswers 사용 가능성이 낮다면 단순한 단방향 관계로 시작하는 자신의 경험을 제시했다. 학습 목적이 더 큰 경우 참고하라는 조건부 의견이며, 양방향 관계가 잘못되었다고 확정하거나 지적을 철회한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
CREATE TABLE reply (
  id BIGINT PRIMARY KEY,
  question_id BIGINT NOT NULL REFERENCES question(id)
);
```

**적용 설명:** 질문당 여러 답변을 허용한 모델이다. 하나만 허용한다면 question_id에 UNIQUE가 필요한지 요구사항으로 판단한다.
