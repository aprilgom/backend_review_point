# FC0164 · 서비스에서 사용하는 DTO를 ui 패키지에 두면 서비스가 컨트롤러 계층에 의존하는 형태가 되는 것 아닌지 구성 이유를 질문한다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0154](FC0154.md) · [다음 FC: FC0166 →](FC0166.md)

- [ ] 서비스에서 사용하는 DTO를 ui 패키지에 두면 서비스가 컨트롤러 계층에 의존하는 형태가 되는 것 아닌지 구성 이유를 질문한다. (설계 질문)
  - 조건: 작성자는 팀 프로젝트에서는 계층별 DTO를 변환했지만 이번 미션에서는 과하다고 보아 요청 DTO만 두었으며 패키지 의존성은 고려하지 못했다고 답했다. DTO 패키지를 ui 밖으로 옮기겠다고 했으나 실제 이동 결과는 제시되지 않았다.

- [ ] 서비스가 컨트롤러 DTO에 의존하는 방향은 피하고, DTO 분리나 서비스 DTO 공유 등 다른 구조의 장단점을 검토하자고 설명했다. (토론)
  - 조건: 참여자는 서비스가 여러 컨트롤러에 의존하면 컨트롤러 추가에 따라 서비스 수정이 필요해질 수 있다고 우려했다. 현재처럼 도메인이 단순하면 컨트롤러가 도메인을 변환해도 되지만, 필드가 많아지면 서비스 DTO 제공을 고려할 수 있다고 설명했다. 웹 DTO와 서비스 DTO가 동일해 동시 수정 부담이 크다면 서비스 DTO를 컨트롤러가 함께 쓰는 방안도 가능하다고 했으며, 특정 방안을 강제하지 않았다. 작성자는 의존 흐름을 맞추기 위해 DTO를 서비스 하위로 옮겼다고 보고했다.

- [ ] 계층 간 결합을 낮추기 위해 DTO를 분리했다면 서비스가 presentation DTO를 입력으로 받는 의존 방향도 점검해야 한다고 제안했다. (조건부 제안)
  - 조건: 리뷰 참여자는 DTO 분리 목적을 전제로 지적하며 서비스의 presentation 패키지 import를 확인하는 방법을 제시했다. 작성자는 그 목적이 맞지만 요청 DTO는 분리하지 못했다고 인정했다. 다만 현재 API와 서비스가 1:1이고 DTO 필드도 같아 엄격한 분리의 이점보다 변환 비용이 크다고 판단하여, DTO를 application에 두고 컨트롤러가 의존하도록 변경했다고 보고했다. 웹 포맷 변경 시 별도 DTO를 도입하겠다는 입장이며, Repository DTO를 컨트롤러까지 전달하는 구조 유지에 관한 추가 설명은 작성자 자신의 확장 논의로, 이에 대한 후속 답변은 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
package application;
public record CreateTaskCommand(String title) {}
```

**적용 설명:** 서비스 입력 계약을 애플리케이션 계층에 둔다. HTTP 요청 DTO는 컨트롤러에서 이 타입으로 변환한다.
