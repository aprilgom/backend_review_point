# FC0246 · queryForObject의 조회 결과가 없을 때 null을 직접 반환하기보다 Optional로 부재를 표현하거나 예외를 던지는 방안을 제안했다.

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0243](FC0243.md) · [다음 FC: FC0244 →](FC0244.md)

- [ ] queryForObject의 조회 결과가 없을 때 null을 직접 반환하기보다 Optional로 부재를 표현하거나 예외를 던지는 방안을 제안했다. (개선 제안)
  - 조건: 참여자는 취향 차이일 수 있다고 전제했으며, Optional의 호출부 처리 부담과 생성 비용이 고려된다면 예외 방식도 가능하다고 했다. 작성자는 EmptyResultDataAccessException을 던지도록 수정했다고 보고했으나 실제 변경은 별도로 확인되지 않았다.

- [ ] 단건 조회 결과가 없을 때 null을 반환하는 대신 Optional을 사용하거나 예외를 던지는 방식을 고려했는지 물었다. (설계 질문)
  - 조건: 작성자는 예외보다 Optional을 선호한다고 답했다. 예외 방식은 사용자에게 exists 조회 후 find하는 불필요한 로직을 유발할 수 있다는 자신의 판단과, JdbcTemplate은 조회에 집중하고 후처리를 사용자에게 맡기려는 의도를 설명하며 반영을 예고했다. 이 논거의 기술적 타당성이나 실제 반영 결과는 확인되지 않는다.

- [ ] queryForObject의 조회 결과가 없을 때 Optional을 반환하는 방식과 예외를 던지는 방식 중 무엇이 더 나은지 논의했다. (토론)
  - 조건: 리뷰 참여자는 실제 JdbcTemplate이 EmptyResultDataAccessException을 던진다는 설명과 함께 비교를 요청했다. 작성자는 결과 부재의 의미를 비즈니스 계층에서 판단하고 기본값을 선택할 수도 있으므로 Optional 반환도 타당한 선택이라고 답했고, 리뷰 참여자는 긍정적으로 응답했다. 명시적인 지적 철회나 구현 변경 요구는 없으며, 긍정적 응답을 기술적 검증으로 간주하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Optional<User> user = users.find(id);
return user.orElseThrow(UserNotFound::new);
```

**적용 설명:** 조회 부재를 저장소 계약에서 드러내고 예외 선택은 호출 맥락에서 한다.
