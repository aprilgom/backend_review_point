## 검토 질문

- [ ] 저비용으로 확인 가능한 오류를 먼저 검증해 뒤늦은 실패로 불필요한 작업을 수행하지 않는가?

**직접 작성한 예시**

```java
requireValidRequest(input);
Price price = expensiveQuote(input);
return place(input, price);
```

**적용 설명:** 값만으로 가능한 저비용 검증을 먼저 한다. 외부 상태 검증은 확정 시점에 다시 필요할 수 있다.

## 구체적인 검토 사례

- [ ] 도메인 이벤트를 통한 지연된 검증 전에 비용이 큰 작업이 실행된다면, 뒤늦은 검증 실패로 불필요한 비용이 발생할 수 있다고 우려했다. (조건부 제안)
  - 조건: 검증 이전 로직에 리소스가 많이 드는 작업이 있다는 가정에 따른 우려다. 실제로 그러한 작업이 존재하거나 성능 문제가 발생했다는 보고는 없다.

- [ ] 생성 요청에서 ID만 사용하는데 저장한 Line을 다시 조회하고 DTO로 감싸는 이유를 물으며 불필요한 추가 쿼리를 우려했다. (설계 질문)
  - 조건: 작성자는 DB 트리거 등이 name·color를 바꿀 가능성을 고려했다고 설명한 뒤, 오히려 DB 비즈니스 로직에 대한 의존을 강화하는 설계일 수 있다고 스스로 재고했다. 리뷰 참여자는 트리거의 구체적인 상황을 물었고, 생성 후 name·color가 필요하다면 재조회가 유의미할 수 있지만 현재는 ID만 필요하다는 조건을 명확히 했다. 추가 조회가 항상 불필요하다는 주장이나 지적 철회는 아니다.

- [ ] 응답을 구성할 때 getResponseBody()를 두 번 호출하는 중복을 지적했다. (관찰)
  - 조건: 작성자는 호출 결과를 변수로 추출했다고 답했다. 중복 호출로 인한 실제 비용이나 동작상 문제는 제시되지 않았고, 링크된 커밋의 내용은 확인 근거로 사용하지 않았다.
