# FC0362 · 도메인과 응답 표현의 분리

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0367](FC0367.md) · [다음 FC: FC0369 →](FC0369.md)

## 검토 질문

- [ ] 도메인 객체가 화면·전송 형식까지 과도하게 담당하지 않도록 응답 계약을 구분했는가?

**직접 작성한 예시**

```java
record AccountReply(long id, String displayName) {}
AccountReply reply = new AccountReply(account.id(), account.displayName());
```

**적용 설명:** 도메인 메서드에 HTTP·직렬화 책임을 몰지 않는다. 공개 필드는 명시적으로 선택한다.

## 구체적인 검토 사례

- [ ] 도메인 객체가 응답 역할까지 과도하게 담당하는지 검토하고 응답 객체 분리를 고려하자. (개선 제안)
  - 조건: 리뷰 참여자는 현재 요구사항에서도 응답 DTO 분리가 과한 설계는 아니라는 의견을 밝혔다. 작성자는 응답 DTO를 추가하고 도메인 객체를 불변으로 변경했다고 보고했으나, 해당 보고만으로 구현 결과를 검증할 수는 없다.

- [ ] 서비스가 절차적으로 수행하는 가격 계산 등의 역할을 도메인으로 옮기고, 도메인에 완전히 계산된 값만 전달하는 구조를 재검토하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 해당 메서드뿐 아니라 애플리케이션 전반에서 도메인의 역할이 부족해 보인다는 인상을 근거로 제안했다. 작성자의 답변이나 변경 결과는 제시되지 않았다.

- [ ] 테이블과 직접 대응하는 클래스와 객체 참조를 포함하는 도메인 표현이 혼재하므로, 도메인과 엔티티를 분리하는 방안을 고려하자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 User와 Products는 DB에 직접 대응하는 반면 CartItem은 두 ID가 아니라 ID와 Product를 가진다는 차이를 들었다. 도메인과 엔티티를 동시에 표현하려다 생긴 문제일 수 있다는 가설이며, 작성자의 감사와 리팩터링 계획만으로 원인이나 해결이 검증된 것은 아니다.
