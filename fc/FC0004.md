# FC0004 · 공통 유스케이스의 통합과 분리 시점

## 검토 질문

- [ ] 사용자 유형이나 진입점이 달라도 업무 규칙이 같다면 공통화할 수 있으며, 실제 차이가 생길 때 분리할 수 있는가?

**직접 작성한 예시**

```java
// 권한 검사는 진입점에서 별도로 수행한다.
Booking createBooking(BookingInput input) {
    return bookings.save(Booking.create(input));
}
```

**적용 설명:** 관리자·사용자의 생성 규칙이 같을 때만 공통화한다. 권한 차이까지 없애는 예시는 아니다.

## 구체적인 검토 사례

- [ ] 관리자와 일반 사용자의 예약 생성 로직이 동일하므로 서비스 메서드를 중복으로 두기보다 로직에 차이가 생길 때 분리하는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰어는 두 API를 구분하더라도 서비스 메서드까지 별도로 둘 필요는 없다는 의견이었다. 작성자는 사용자 유형을 기준으로 역할을 나누었지만 동일한 작업을 중복으로 분리하는 데 스스로도 고민이 있었다고 설명했다. 실제 통합 여부는 확인되지 않는다.

- [ ] LoginController에서 유저를 찾는 로직도 리팩터링해 보자고 제안했다. (개선 제안)
  - 조건: 리뷰어는 구체적인 리팩터링 방법을 명시하지 않았다. 작성자는 인터셉터 구현을 고려하겠다고 했다가 이후 포기했다고 밝혔고, 리뷰어는 놀라는 반응만 남겼다. 인터셉터는 작성자가 제시한 방안이며, 리뷰어의 지적 철회나 변경 완료로 해석하지 않는다.

- [ ] 유사한 검증이나 서비스 로직을 무조건 한곳에 모으기보다, 명확히 동일한 로직이고 쉽게 통합할 수 있을 때 중복을 제거하는 실용적 접근을 제시했다. (의견)
  - 조건: 작성자는 서비스 간 연계에서 순환 참조와 검증 책임 분산이 발생할 때의 설계 기준을 물었다. 리뷰 참여자는 도메인 로직과 서비스의 유스케이스 흐름이라는 구분을 유지하되, 통합이 어렵거나 부가 문제를 만들면 현재 도메인에 맞지 않는 통합인지 또는 실제로 다른 로직인지 검토하고 당장은 중복을 허용한다는 개인적 관점을 설명했다. 실제로 책임을 모아야 할 필요가 생겼을 때 재구성하는 방식을 선호하며, 특정 구조 변경을 요구한 것은 아니다.
