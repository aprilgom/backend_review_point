# FC0427 · mock 없이 검증하는 서비스 동작

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0432](FC0432.md) · [다음 FC: FC0429 →](FC0429.md)

## 검토 질문

- [ ] mock 상호작용만으로 가려지는 동작을 실제 객체나 단순 fake를 사용한 결과 검증으로 보완할 수 있는가?

**직접 작성한 예시**

```java
Users users = new MemoryUsers();
Registration service = new Registration(users);
service.register("reader");
assertTrue(users.findByName("reader").isPresent());
```

**적용 설명:** mock 호출 횟수 대신 동작 결과를 검증하는 대안이다. 실제 DB 제약은 별도 통합 테스트가 필요하다.

## 구체적인 검토 사례

- [ ] Mock 사용의 장단점을 인정하면서 Mocking 연습은 유지하되, 서비스 테스트 중 하나는 Mock 없이 작성해보도록 제안한다. (토론)
  - 조건: 리뷰 참여자는 메서드 구현 변경에 따라 Mock 테스트도 바뀔 수 있어 메모리 DB를 선호하는 의견이 있음을 소개했다. 반면 현업 테스트가 개발 DB를 직접 보는 사례를 이유로 Mocking 연습도 유익하다고 보았으며, Mock을 전면 제거하라는 요구는 아니다.

- [ ] 모킹된 조회 테스트의 문자열 "sql"이 실제 DB에서는 문법 오류를 일으킬 수 있다는 질문에서 출발해, 실제 DB 전환 시 테스트 일관성과 모킹을 통한 로직 검증의 적절성을 논의했다. (토론)
  - 조건: 작성자는 예외를 DataAccessException 계열로 바꾸라는 뜻인지 되물었다. 리뷰 참여자는 예외 변환 요구가 아니라 실제 DB로 바꿔도 일관된 테스트가 되기를 바랐던 질문이라고 설명하고, H2에서 SQLSyntaxErrorException이 발생했다고 보고했다. 다만 최종적으로는 여러 데이터소스에 일관된 기능을 제공하는 JdbcTemplate의 목적상 현재처럼 모킹으로 로직을 검증하는 편이 더 바람직하다는 의견으로 정리했다. 실제 DB 테스트 전환이나 예외 계약 변경을 요구한 것으로 해석하지 않는다.

- [ ] Mock 기반 손님 수 변경 테스트에서 numberOfGuests를 설정하지 않은 객체를 사용하는 등 테스트 준비 내용과 검증하려는 시나리오가 어긋날 수 있는 점을 논의한다. (토론)
  - 조건: 리뷰 참여자는 필요한 상태를 모두 준비하는 데 드는 시간도 언급하며 의견을 물었다. 작성자는 빈 테이블에 대한 사전 검증만을 위해서는 기존 설정이 충분하다고 생각했으나, numberOfGuests의 부재를 검증하는 조건이 추가되면 테스트에 영향을 줄 수 있다고 답하고 Fixture 활용을 예고했다. 실제 수정 여부는 확인되지 않는다.
