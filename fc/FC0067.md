# FC0067 · API 안정성을 DTO 사용 근거로 들면서 요청에만 DTO를 적용한 이유와, 도메인 변경이 응답 형식에도 영향을 줄 가능성을 질문했다.

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0064](FC0064.md) · [다음 FC: FC0060 →](FC0060.md)

- [ ] API 안정성을 DTO 사용 근거로 들면서 요청에만 DTO를 적용한 이유와, 도메인 변경이 응답 형식에도 영향을 줄 가능성을 질문했다. (토론)
  - 조건: 작성자는 현재 조회에서 모든 필드가 필요하므로 응답 DTO의 의미가 적다고 설명했다. 리뷰 참여자가 응답에도 변경 누락 위험이 있지 않느냐고 묻자, 작성자는 내부용·비공개 필드가 생기면 응답 DTO를 도입하고 요청은 이미 입력 데이터와 도메인 필드가 달라 먼저 도입했다고 설명했다. 응답 DTO의 즉시 도입이 확정된 것은 아니다.

- [ ] 응답을 DTO로 포장한 것처럼 요청에도 별도의 DTO를 만들어보도록 제안한다. (개선 제안)
  - 조건: ReservationInfo를 @RequestBody로 직접 받는 예약 추가 API에 대한 제안이다. 후속 답변이나 실제 반영 결과는 제공되지 않았다.

- [ ] 예약 조회 응답에서 도메인 객체를 직접 반환하는 대신 응답 DTO로 변환하자고 제안했다. (개선 제안)
  - 조건: 응답 표현의 변경을 제안했으며, 구체적인 DTO 구조나 실제 반영 여부는 제시되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record TaskReply(long id, String title) {}
return new TaskReply(task.id(), task.title());
```

**적용 설명:** 도메인 전체를 직렬화하지 않아 내부 필드 추가가 API 응답에 자동 노출되는 것을 막는다.
