# FC0364 · 판단을 타입에 위임하는 표현

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0359](FC0359.md) · [다음 FC: FC0367 →](FC0367.md)

## 검토 질문

- [ ] 외부에서 값을 꺼내 비교하는 대신 타입에 의미 있는 판단을 요청하면 의도가 더 잘 드러나는가?

**직접 작성한 예시**

```java
enum RequestMethod {
    GET, POST;
    boolean isGet() { return this == GET; }
}
```

**적용 설명:** 판단을 타입에 보내는 작은 예다. 단순 비교를 감싼 메서드가 실제 가독성을 높이는지 검토한다.

## 구체적인 검토 사례

- [ ] 요청 메서드 값을 외부에서 직접 비교하기보다 RequestMethod 객체에 isGet() 메시지를 보내 판단하도록 제안했다. (개선 제안)
  - 조건: 작성자는 반영했다고 답했으며, 실제 변경 내용은 이 대화에서 확인되지 않는다.

- [ ] getter로 값을 꺼내는 대신 객체에 메시지를 보내는 방식으로 수정하고 차이를 확인해 보도록 제안했다. (개선 제안)
  - 조건: 작성자는 메서드 레퍼런스로 변경하여 가독성이 좋아졌다고 답했다. 이 답변이 리뷰어가 제안한 메시지 전달 방식의 변경을 의미하는지는 확인되지 않아, 제안의 반영 여부는 불명확하다.

- [ ] HttpRequest에서 HTTP 메서드를 getter로 꺼내 비교하는 대신 요청 객체에 판단을 물어보자는 제안이다. (개선 제안)
  - 조건: 작성자는 isGet, isPost 등 메서드가 과도하게 늘 수 있다고 반론했다. HttpRequest의 기존 인터페이스가 내부 구조를 드러내며 톰캣 구현도 절차 지향에 더 어울린다는 개인적 판단을 들어, 요청을 완전히 행위 중심 객체로 만들기보다 자료구조로 취급할 여지를 주장했다. 후속 합의는 없다.
