# FC0376 · API와 화면 문구의 결합

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0368](FC0368.md) · [다음 FC: FC0381 →](FC0381.md)

## 검토 질문

- [ ] API가 화면 문구 자체보다 안정된 상태·행동 의미를 제공해 UI 표현 변경과 분리되는가?

**직접 작성한 예시**

```json
{"action":"PAYMENT_REQUIRED","canRetry":true}
```

**적용 설명:** 화면 문구 대신 의미 있는 상태·행동 코드를 제공하는 예다. 사용자 언어의 문구는 UI가 선택하고 코드 계약은 버전 관리한다.

## 구체적인 검토 사례

- [ ] 화면 안내 문구를 action으로 내려주면 UI 문구 변경 때 백엔드와 API 계약도 함께 변경해야 하는 결합이 생길 수 있다. (위험 지적)
  - 조건: 작성자는 action이 실제 동작 분기에 쓰이면 의미 있는 계약이지만 문구를 이어 보여주는 용도라면 불필요할 수 있다고 설명했다. 리뷰 참여자는 UI 문구와 API 계약의 결합 위험을 덧붙였고, 이후 작성자의 판단 기준도 충분히 좋다고 평가했다. action 자체가 항상 불필요하다는 지적은 아니다.

- [ ] MAX_FIRST_EXTRA_FARE_DISTANCE 상수를 유일한 사용처로 보이는 maximumDistanceStrategy에서 관리하는 것이 맞지 않는지 물었다. (개선 제안)
  - 조건: maximumDistanceStrategy에서만 사용되는 것 같다는 조건에 근거한 상수 소유 위치 제안이다. 전체 사용처나 실제 이동 여부는 이 대화에서 확인되지 않는다.

- [ ] 인스턴스 생성이 유틸리티 클래스로 이동한 상황에서 ControllerScanner에 scan만 남긴 이유를 묻고, 스캔도 유틸리티로 옮기는 방안을 제안했다. (토론)
  - 조건: 리뷰 참여자는 요구사항과 달리 인스턴스 생성이 유틸리티로 옮겨진 것으로 보인다고 전제했다. 작성자는 힌트에 Scanner가 있어 클래스를 만들었고 다른 메서드는 유틸리티로 느꼈다고 설명하면서, scan만 분리한 이유가 모호하다는 데 동의했다. 실제 변경 여부는 확인되지 않는다.
