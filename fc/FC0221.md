# FC0221 · DTO에서 입력을 검증하더라도 도메인 자체의 검증이 필요하며, Reservation 외 다른 도메인도 확인하자고 요청했다.

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0220](FC0220.md) · [다음 FC: FC0222 →](FC0222.md)

- [ ] DTO에서 입력을 검증하더라도 도메인 자체의 검증이 필요하며, Reservation 외 다른 도메인도 확인하자고 요청했다. (토론)
  - 조건: 작성자는 형식·타입·null 검증을 DTO로 옮겼고, 과거 시간 예약 금지는 현재 시간을 알아야 하는 비즈니스 로직이라 서비스에 두었다며 도메인 검증의 필요성에 의문을 제기했다. 리뷰 참여자는 DTO 검증은 빠른 입력 오류 안내에 유용하고, 이후 도메인 값이 바뀔 수 있으며 실제 저장 대상도 도메인이므로 도메인 검증은 반드시 필요하다는 의견을 밝혔다. 다만 미션처럼 로직이 단순하고 처리 시간이 짧으면 DTO 검증은 일부 생략할 수도 있다고 조건을 달았다.

- [ ] 요청 DTO의 유효성 검증에 Spring Validation을 활용하도록 제안했다. (개선 제안)
  - 조건: 작성자는 생성자 내부의 null 검사 대신 DTO에 유효성 제약 애너테이션을 추가하고 컨트롤러에서 @Valid를 사용하는 방향으로 리팩터링하겠다고 답했다. 실제 적용 완료 여부는 확인되지 않는다.

- [ ] 요청 DTO의 유효성 검사가 도메인 검증과 반복된다면 불필요할 수 있다는 의견을 제시했다. (조건부 제안)
  - 조건: 도메인에서 같은 유효성 검사를 반복하고 있다는 조건에 한정된 리뷰어의 의견이다. 실제 요청 검증이 중복인지 확인하거나 제거를 요구한 내용은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record Quantity(int value) {
    Quantity { if (value < 1) throw new IllegalArgumentException("quantity"); }
}
```

**적용 설명:** 요청 검증을 거치지 않는 배치·테스트 생성 경로에서도 불변식을 지킨다.
