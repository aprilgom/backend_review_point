# FC0160 · 서비스를 통한 공통 정책 재사용

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0167](FC0167.md) · [다음 FC: FC0172 →](FC0172.md)

## 검토 질문

- [ ] 다른 기능을 호출할 때 저장소 직접 접근 대신 공통 정책을 제공하는 서비스를 재사용할 이유가 있는가?

**직접 작성한 예시**

```java
Customer customer = customerService.requireActive(customerId);
orderService.place(customer, lines);
```

**적용 설명:** 공통 활성 상태 검증을 서비스 계약으로 재사용하는 예시다. 단순 조회마다 서비스를 겹쳐 만들 필요는 없다.

## 구체적인 검토 사례

- [ ] Repository를 직접 호출하는 대신 도메인별 서비스를 주입해 재사용하고 직접 의존성을 줄이는 방안을 검토하도록 제안했다. (토론)
  - 조건: 최초 제안은 직접 호출할 특별한 이유가 없다면 적용하자는 조건부였다. 작성자는 기존 서비스의 DTO 반환과 필요한 조회 메서드의 부재 때문에 Repository 직접 의존이 더 유연하다고 주장했다. 리뷰 참여자는 LineService가 기본 CRUD를 제공하고 PathService가 추가 로직을 수행하는 역할 분담을 제안하며, 조회 예외 처리의 중복과 변경 지점 증가를 반론으로 들었다. 작성자는 제안 방식으로 수정했다고 보고했지만 구현 결과와 예외 변경 예시의 기술적 타당성은 별도로 확인되지 않는다.

- [ ] 서비스 테스트에서는 Repository에 대한 의존도를 낮추는 방향이 적절하다는 의견을 제시했다. (의견)
  - 조건: Stub을 통한 서비스 로직 집중과 Fake 사용 시 테스트가 자주 깨지는 현상에 관한 작성자 질문에 대한 답변이다. 리뷰 참여자는 코드 변경에 따른 Fake 기반 테스트의 깨짐을 테스트 더블 사용 시 발생할 수 있는 현상으로 설명했으며, 해당 Fake의 설계 결함을 확인한 것은 아니다.

- [ ] 서비스가 여러 Repository에 의존하는 것은 가능하며, 현재 의존 구조에서 구체적으로 어떤 점이 우려되는지 질문했다. (토론)
  - 조건: 참여자는 같은 계층 간 의존은 가능한 지양한다는 관점에서 서비스의 복수 Repository 의존 자체를 크게 문제 삼지 않았다. 작성자는 연관 객체를 함께 조회·생성하는 책임과 단일 책임 원칙에 대한 고민이 이어져 질문했다고 설명했으며, 도메인 특성상 현재 구조가 어느 정도 납득된다고 덧붙였다. 복수 의존을 결함으로 지적한 대화는 아니다.
