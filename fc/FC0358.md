# FC0358 · 조회 모델과 변환 책임의 배치

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0380](FC0380.md) · [다음 FC: FC0373 →](FC0373.md)

## 검토 질문

- [ ] 필요한 값만 가져올지 모델 전체를 거칠지 결정하고 변환 책임·로딩 비용을 적절히 배치했는가?

**직접 작성한 예시**

```java
MemberRow row = members.load(id);
Member member = memberMapper.toDomain(row);
return member.cart();
```

**적용 설명:** 부분 문자열만 반환하는 대신 모델을 거치는 대안이다. 필요한 데이터보다 과도하게 로딩하는 비용도 비교한다.

## 구체적인 검토 사례

- [ ] cart 문자열만 조회하는 대신 Member를 조회해 MemberEntity로 변환하고, 관련 변환 로직을 MemberEntity에 둘 수도 있다고 제안했다. (개선 제안)
  - 조건: 현재 로직을 읽기 쉽게 개선하는 선택지로 제시했으며, 변환 로직을 반드시 MemberEntity에 두어야 한다고 요구하지 않았다.

- [ ] MenuProduct가 Product의 가격을 꺼내 곱셈하지 말고 Product에 계산을 요청해 가격 계산을 캡슐화하도록 제안했다. (개선 제안)
  - 조건: 작성자는 객체에 메시지를 보내는 방식에 강하게 동의했다. 이후 칭찬은 있지만 실제 구현 변경이나 검증 결과는 이 대화에서 확인되지 않는다.

- [ ] ProductMapper에 여러 변환 책임을 집중시키기보다 각 객체가 자신의 변환을 담당하도록 나누는 방안을 고려하면 좋겠다. (개선 제안)
  - 조건: 작성자는 Mapper가 없어도 되는 객체였다고 받아들였다. 리뷰어는 현재처럼 단일 객체 간 변환이 단순할 때 각 객체가 담당해도 충분하다는 의견이며, 변환에 필요한 객체가 많거나 과정이 복잡하다면 별도 Mapper를 고려할 수 있다고 조건을 명확히 했다. Mapper 일반을 불필요하다고 단정한 지적은 아니다.
