# FC0313 · 탐색·필터링 절차의 추출

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0301](FC0301.md) · [다음 FC: FC0299 →](FC0299.md)

## 검토 질문

- [ ] 초기화 메서드의 탐색 조건을 별도 역할로 나누어 등록 범위와 규칙이 드러나게 할 수 있는가?

**직접 작성한 예시**

```java
List<Method> actions = Arrays.stream(type.getDeclaredMethods())
    .filter(method -> method.isAnnotationPresent(Route.class)).toList();
```

**적용 설명:** 자체 Route 애너테이션 기준 탐색을 별도 메서드로 분리할 수 있다. 상속 메서드 포함 여부를 정한다.

## 구체적인 검토 사례

- [ ] initialize 안에서 RequestMapping이 있는 메서드를 추출하는 부분을 별도 메서드로 분리하자는 제안이다. (개선 제안)
  - 조건: 분리할 메서드의 이름이나 구체적인 경계는 제시하지 않았고 작성자 답변도 없다.

- [ ] 검증 로직을 메서드로 한 번 더 분리하기보다 validateUserExist 안에서 직접 처리하는 편이 읽기 좋겠다고 제안했다. (개선 제안)
  - 조건: 현재 validateCredentialUserExist 호출에 대한 가독성 제안이다. 작성자는 수정하겠다고 답했으며, 메서드 분리 전반을 금지한 의견은 아니다.

- [ ] `createValidReservation` 이후 다시 `validateReservation`을 호출하면 혼동될 수 있으므로 각 메서드의 실제 동작을 더 명확히 드러내도록 제안했다. (개선 제안)
  - 조건: 작성자는 처음에 검증 분리와 이름 변경을 보고했으나 해당 보고 문장에 취소선을 표시했고, 후속 답변에서는 서비스 로직을 분리하면서 검증을 `ReservationSchedulerService`로 옮겼다고 설명했다. 작성자 보고의 정정이며 리뷰어의 지적이 철회된 것은 아니다.
