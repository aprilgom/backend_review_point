# FC0279 · DB에서의 조회 범위 제한

## 검토 질문

- [ ] 전체 데이터를 메모리에 올린 뒤 거르지 않고 필요한 조건을 저장소 조회에 반영할 수 있는가?

**직접 작성한 예시**

```sql
SELECT id, starts_at FROM slot WHERE day = :day AND available = TRUE;
```

**적용 설명:** 필요한 범위를 DB에서 제한한다. available이 저장값인지 계산값인지에 따라 실제 조회를 설계한다.

## 구체적인 검토 사례

- [ ] 예약 시간 조회에서 findAll로 모든 예약을 메모리에 올리는 대신 DB에서 필요한 데이터를 필터링하는 방안을 검토하도록 제안했다. (개선 제안)
  - 조건: 작성자는 DB 필터링 쿼리가 익숙하지 않아 기존 함수를 사용했으며 필요한 값만 쿼리로 가져오도록 수정했다고 보고했다. 리뷰 참여자는 후속으로 비즈니스 로직에서 처리할 일과 DB에서 필터링·집계할 일의 경계를 고민하라고 덧붙였다. 모든 처리를 DB로 옮기라는 요구나 성능 측정 결과는 아니다.

- [ ] 예약 데이터가 많아질 때 findAll 전체 조회가 미칠 영향을 고민하고, 향후 페이징을 검토해 보도록 제안한다. (토론)
  - 조건: 처음부터 코드 반영이 아닌 고민 차원의 질문이었다. 작성자는 인덱스와 JOIN 최적화를 제안하고 10만 건 조회 측정 결과를 보고했으나, 리뷰 참여자는 의도가 인덱스보다 풀스캔과 페이징에 있었다고 정정했다. 지나치게 지엽적인 피드백이었다고 완화하면서도 향후 검토할 관심사는 유지했으며, 현재 미션에서 페이징을 적용하라는 요구는 명시적으로 하지 않았다.

- [ ] 예약 전체 조회 쿼리가 무거워지는 점을 짚고, 데이터가 많아질 때 findAll 방식의 조회를 어떻게 처리할지 고민하도록 제안한다. (개선 제안)
  - 조건: 리뷰어는 이번 미션은 전체 조회가 요구사항이므로 현재 변경을 요구하지 않고 이후 미션의 고려사항으로 제시했다. 현업에서 findAll을 활용할 수 없다는 표현은 리뷰어의 견해다. 작성자는 데이터 증가와 여러 서버의 요청에 따른 DB 부담을 예상하고 페이지네이션을 검토하겠다고 답했으며, 측정 결과나 구현 완료 보고는 없다.
