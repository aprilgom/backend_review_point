# FC0367 · 파싱·업무 처리·출력의 분리

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0364](FC0364.md) · [다음 FC: FC0362 →](FC0362.md)

## 검토 질문

- [ ] 요청 객체나 파서가 업무 실행과 응답 생성까지 담당하지 않도록 처리 단계를 구분했는가?

**직접 작성한 예시**

```java
Request request = parser.parse(input);
Reply reply = dispatcher.dispatch(request);
encoder.write(reply, output);
```

**적용 설명:** 파싱·실행·출력을 분리해 프로토콜 값 객체에 부작용이 몰리지 않게 한다.

## 구체적인 검토 사례

- [ ] HttpRequest가 요청 파싱, 로직 처리, 응답 생성까지 담당하므로 책임을 분리하는 것이 좋겠다는 의견을 제시한다. (개선 제안)
  - 조건: 리뷰 참여자는 향후 리팩터링에서 분리할 것으로 기대하며 코멘트로 남겼다. 작성자는 요청, 요청 처리, 응답을 분리했다고 보고했지만 실제 분리 결과는 이 대화에서 검증되지 않았다.

- [ ] HttpRequest의 요청 파싱 구조가 잡힌 만큼, 각 책임을 맡는 객체로 분리해 표현하는 리팩터링을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 현재 변수 명명 덕분에 잦은 split도 이해하기 좋다고 평가한 뒤 책임 분리를 제안했다. 작성자는 다음 미션에서 적용하겠다고 답했고 리뷰 참여자가 동의했다. 현재 단계에서 분리가 완료되었다는 근거는 없다.

- [ ] HttpRequest의 요청 라인 처리 부분을 HttpHeaders로 묶거나 요청 라인을 나타내는 별도 객체로 분리하는 방안을 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 step3에서 진행해도 된다고 시점을 유보했다. 작성자는 요청 라인을 의미하는 requestLine으로 분리했다고 답했으며, 실제 변경 결과는 이 대화만으로 확인하지 않는다.
