# FC0054 · 요청 본문과 미디어 타입의 일치

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0053](FC0053.md) · [다음 FC: FC0057 →](FC0057.md)

## 검토 질문

- [ ] 요청의 인코딩 방식·파싱 방식·Content-Type이 서로 일치하는가?

**직접 작성한 예시**

```http
POST /labels HTTP/1.1
Content-Type: application/x-www-form-urlencoded

name=study&color=blue
```

**적용 설명:** 폼 인코딩 본문에 맞춘 헤더 예시다. JSON 본문을 받는 계약이라면 JSON 헤더와 파서를 함께 사용한다.

## 구체적인 검토 사례

- [ ] JSON 본문을 사용하지 않고 RequestParam으로 입력을 받는다면 application/json 대신 다른 Content-Type을 고려하도록 제안했다. (개선 제안)
  - 조건: 작성자는 게임 이름 하나를 위해 요청 DTO를 만드는 것이 불필요하고 이름에 보안 문제가 없다고 판단해 본문 없이 RequestParam을 사용했다고 설명했다. 리뷰 참여자의 제안은 JSON 본문이 필요 없다는 조건에 따른 것이다. 작성자는 application/x-www-form-urlencoded로 변경하고 본문 없이 RequestParam으로 받도록 수정했다고 보고했으며, 실제 요청 구성은 확인되지 않는다.

- [ ] 서버 처리를 편하게 하려는 목적으로 요청값을 과도하게 받지 말고 꼭 필요한 값만 받도록 제안했다. (개선 제안)
  - 조건: 작성자는 사용하지 않는 값과 구조 변경으로 불필요해진 값을 삭제해 요청 파라미터 수를 줄였다고 보고했다. 어떤 값이 최종적으로 남았는지는 답변에 명시되지 않았다.

- [ ] 요청 본문 생성 여부를 POST 메서드로만 판단하지 말고 Content-Length를 기준으로 판단하는 것이 어떨지 제안했다. (개선 제안)
  - 조건: POST 외에도 본문이 필요한 요청이 있다는 이유로 제안했다. 작성자는 동의했으나 실제 변경이나 다른 본문 전달 방식의 처리 여부는 확인되지 않는다.
