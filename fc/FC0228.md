# FC0228 · 중복 이름 금지를 DB 유니크 제약 오류에만 맡기기보다 서비스 계층에서 검증하고 예외를 발생시키는 방식을 검토하자고 제안한다.

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0226](FC0226.md) · [다음 FC: FC0224 →](FC0224.md)

- [ ] 중복 이름 금지를 DB 유니크 제약 오류에만 맡기기보다 서비스 계층에서 검증하고 예외를 발생시키는 방식을 검토하자고 제안한다. (개선 제안)
  - 조건: 리뷰 참여자는 DB 제약으로 요구사항을 구현하는 것도 가능하지만 자바 코드만으로는 규칙을 알 수 없어 스키마까지 확인해야 한다고 설명했다. 작성자는 커스텀 예외로 변환해도 DB가 유니크 제약 예외를 발생시켜야 한다는 전제가 남는다고 우려했다. 리뷰 참여자의 추가 설명 요청에 작성자가 그 의미를 명확히 했으며, 서비스 사전 검증의 실제 도입 여부는 확인되지 않는다.

- [ ] 이름 중복을 데이터베이스 제약조건으로 검증하는 방식과 비교해 애플리케이션에서 검증할 때의 장단점을 묻는다. (설계 질문)
  - 조건: 작성자는 검사와 저장 사이에 다른 요청이 개입할 수 있다는 동시성 우려와 매번 전체 목록을 조회하는 비용을 설명했고, 스키마에 이미 unique가 있음을 확인했다고 답했다. 리뷰 참여자가 DB 검증만 사용하라고 요구한 것은 아니며, 실제 중복 저장이나 성능 문제 발생도 확인되지 않았다.

- [ ] DB의 유일성 제약이 있더라도 애플리케이션에서 중복 여부를 미리 확인하기 어렵지 않다면 사전 검증하는 편이 좋겠다는 의견이다. (조건부 제안)
  - 조건: 참여자는 상황에 따라 다르다는 전제와 현재처럼 사전 확인이 어렵지 않은 경우라는 조건을 붙였다. 후속 답변에서는 관리 지점이 늘더라도 중요한 검증은 중복해서 수행할 수 있다고 설명했으며, 모든 검증의 무조건적인 중복 수행을 요구하지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
if (labels.existsByName(name)) throw new DuplicateName();
labels.insert(name); // DB UNIQUE 제약도 유지
```

**적용 설명:** 사전 검사는 친절한 오류에 도움을 주지만 동시 삽입을 막지는 못한다. DB 제약 위반도 같은 계약으로 변환한다.
