# FC0277 · 조회 시 캐시 미스로도 캐싱할 수 있는데 생성 시점에도 캐싱하는 전략을 선택한 이유를 질문한다.

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0287](FC0287.md) · [다음 FC: FC0270 →](FC0270.md)

- [ ] 조회 시 캐시 미스로도 캐싱할 수 있는데 생성 시점에도 캐싱하는 전략을 선택한 이유를 질문한다. (설계 질문)
  - 조건: 작성자는 생성보다 조회가 많을 것으로 예상하고, 캐시 미스 시 조회 성능 저하 가능성과 금전 도메인의 데이터 정합성을 고려해 write through를 선택했다고 답했다. 조회량이나 성능 및 정합성 효과가 측정·검증되었다는 근거는 없다.

- [ ] 캐시에서 먼저 조회하고 값이 없으면 원래 작업을 실행해 저장하는 현재 캐시 전략의 명칭을 질문했다. (설계 질문)
  - 조건: 작성자는 On-Demand Cache라고 답하고 요청 시에만 로딩해 이후 요청에 재사용하는 방식이 쿠폰 조회에 적합하다고 설명했다. 리뷰어는 짧게 긍정했으며, 이를 전략 명칭이나 적합성에 대한 별도의 기술 검증으로 보지는 않는다. 요청 시 로딩과 재사용에 관한 관심사로 PERFORMANCE에 분류했다.

- [ ] 쿠폰 생성 직후 조회가 빈번할 때 쓰기 DB로 반복 조회하는 비용을 어떻게 줄일지, 캐시 도입 여부를 복제 지연 길이로 결정하는 이유는 무엇인지 논의했다. (토론)
  - 조건: 작성자는 복제 지연을 측정한 뒤 짧으면 캐시를 도입하고 길면 단일 DB를 쓰겠다고 답했다. 리뷰어는 측정 자체는 긍정했지만 짧을 때만 캐시를 쓰는 이유를 이해하지 못했다고 질문했다. 자신의 대안으로 생성 직후 조회 빈도를 캐시 도입 근거로 삼고, 읽기 DB 반영 전까지 캐시에서 조회하며 평균 복제 지연은 TTL 설정에 활용하겠다고 제안했다. 반대나 필수 변경 요구가 아닌 참고 의견임을 명시했다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Product value = cache.get(id);
if (value == null) { value = products.get(id); cache.put(id, value); }
return value;
```

**적용 설명:** cache-aside 형태의 개념 코드다. 동시 미스·오래된 값·부재 캐싱 정책을 보완해야 한다.
