# FC0253 · 삭제의 멱등성과 부재 정책

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0248](FC0248.md) · [다음 FC: FC0255 →](FC0255.md)

## 검토 질문

- [ ] 이미 없는 대상을 삭제할 때 목표 상태 달성을 성공으로 볼지 오류로 볼지 업무 영향으로 결정했는가?

**직접 작성한 예시**

```sql
DELETE FROM slot WHERE id = :id;
```

**적용 설명:** 이미 없어도 목표 상태가 달성된 것으로 보는 멱등 삭제 예다. 삭제 건수 0을 오류로 볼지는 업무 계약에 따른다.

## 구체적인 검토 사례

- [ ] 존재하지 않는 예약 시간을 삭제할 때 예외를 낼지는 비즈니스 영향에 따라 판단하되, 현재처럼 삭제된 상태 자체가 목적이면 오류를 내지 않아도 된다는 의견을 제시했다. (조건부 제안)
  - 조건: 리뷰 참여자는 없는 ID를 삭제하는 일이 후속 로직에 영향을 주거나 사용자에게 이상하게 느껴질 수 있다면 오류 처리가 적절할 수 있다고 조건을 달았다. 현재 예약 시간 삭제에서는 없는 값을 삭제해도 원하는 상태를 이룬다는 판단을 제시했으며, 인용된 사전 존재 검증 선호를 보편적인 오류로 단정하지 않았다.

- [ ] 삭제하려는 예약 시간을 참조하는 예약이 있을 때 발생하는 예외를 처리하도록 요청했다. (문제 보고)
  - 조건: 작성자는 참조 관계로 인한 DB 예외를 놓쳤다고 답했다. 서비스에서 사전 조회하는 방법은 동시성과 통신 비용 때문에 적절하지 않다고 판단해 DAO에 오류 처리를 추가하겠다고 했으며, 이는 작성자의 판단과 변경 계획이다.

- [ ] 존재하지 않는 예약 시간을 삭제할 때 존재 여부를 검증할지, 어떤 응답을 반환할지 검토한다. (토론)
  - 조건: 처음에는 리뷰어가 부재 검증의 필요성을 질문했다. 작성자는 없는 리소스에 204를 반환하는 것이 혼란을 준다고 판단해 삭제 전 존재 확인을 추가하고 테마 삭제도 수정했다고 보고했다. 이후 리뷰어는 DELETE의 멱등성 관점에서 없는 리소스의 삭제를 실패로 보지 않는 경우도 있고 응답 코드로 구분할 수도 있다고 설명하며 관련 학습을 권했다. 작성자의 구현이 틀렸다는 뜻은 아니라고 명시했으며, 존재 검증이 반드시 필요하다는 확정 지적이나 명시적 철회는 아니다.
