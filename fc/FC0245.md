# FC0245 · 외부 오류 응답의 파싱 실패

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0252](FC0252.md) · [다음 FC: FC0248 →](FC0248.md)

## 검토 질문

- [ ] 오류 응답이 예상 형식이 아니거나 비어 있어도 추가 파싱 예외로 원래 실패를 잃지 않는가?

**직접 작성한 예시**

```java
if (!response.isJson()) throw new UnexpectedRemoteResponse();
try { return decoder.read(response.body()); }
catch (DecodeFailure invalid) { throw new RemoteProtocolFailure(invalid); }
```

**적용 설명:** HTML 오류 페이지·빈 본문·잘못된 JSON도 들어올 수 있다. 본문 크기 제한과 로그 마스킹도 적용한다.

## 구체적인 검토 사례

- [ ] 외부 API에서 예상치 못한 응답이 오면 JSON 파싱이 실패할 수 있으므로 오류 응답 처리에서 이 경우도 방어하도록 제안했다. (개선 제안)
  - 조건: 예상하지 못한 응답 형식이 오는 경우를 조건으로 한 방어 처리 제안이다. 작성자는 반영했다고 답했으나 구체적인 처리 방식이나 검증 결과는 제시하지 않았다.

- [ ] 요청 처리에서 Throwable을 잡으면 Exception뿐 아니라 Error도 포함되므로 어디까지 포착해야 할지 검토해 보자는 제안이다. (개선 제안)
  - 조건: 예외 포착 범위를 생각해 보도록 권유한 것이며, 특정 대체 타입을 지정하거나 현재 처리가 확정적인 결함이라고 단정하지 않았다.

- [ ] 여러 실패를 모두 IllegalArgumentException으로 표현할 때 ControllerAdvice에서 오류별 응답을 어떻게 구분할지, 서버 구현 오류를 클라이언트 요청 오류로 오인하지 않을지 검토하자. (토론)
  - 조건: 리뷰어는 존재하지 않는 ID와 음수 인원 요청이 같은 예외를 발생시키는 점을 들고, 구현 내부의 잘못된 변환도 IllegalArgumentException을 발생시킬 수 있다고 설명했다. 모든 매개변수 오류가 클라이언트 잘못은 아니라는 논의이며, 이번 단계에 ControllerAdvice나 커스텀 예외를 추가하라는 요구는 아니다. 후속 댓글에서도 구현보다 사고 실험으로 충분하다고 재확인했다.
