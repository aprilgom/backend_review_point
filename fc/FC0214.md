# FC0214 · 유형별 유효 필드와 값의 부재

[소속 분야: 도메인 모델·값 표현](../11-domain-model.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0213](FC0213.md)

## 검토 질문

- [ ] 유형에 따라 쓰지 않는 필드를 기본값으로 채워 부재 의미를 숨기지 않고 유효 조합을 보장하는가?

**직접 작성한 예시**

```sql
CHECK (
  (kind = 'FIXED' AND fixed_amount IS NOT NULL AND rate IS NULL) OR
  (kind = 'RATE' AND rate IS NOT NULL AND fixed_amount IS NULL)
)
```

**적용 설명:** 쿠폰 유형별 유효 필드를 제약으로 표현한 조각이다. kind 자체는 NOT NULL과 허용 값 제약을 별도로 둔다.

## 구체적인 검토 사례

- [ ] 타입에 따라 사용하지 않는 값이 생기는 쿠폰 테이블에서, 기본값과 NOT NULL 제약이 값의 부재 가능성을 가려 혼선을 줄 수 있다는 우려다. (토론)
  - 조건: 리뷰 참여자는 테이블 분리 방식과 Type 중심 방식 모두 장단점이 있고 후자가 단순하고 직관적일 수 있음을 인정했다. 핵심은 기본값 저장 여부보다 어떤 값이 비어 있을 수 있는지 드러내는 것이라고 설명했다. 작성자는 혼선을 줄이기 위해 Type + Value 표현으로 변경했다고 보고했지만, 이 대화에 없는 다른 댓글의 상세 요구까지 추정하지 않는다.

- [ ] 할인 금액 계산의 int 다운캐스팅에 1원 미만 절삭 정책이 암묵적으로 포함되어 있으므로 금액 정밀도와 반올림·절삭 정책을 명확히 정할 필요가 있음을 지적한다. (위험 지적)
  - 조건: 작성자는 할인 시 내림을 의도한 다운캐스팅이라고 설명하며 문제의 이유를 물었다. 리뷰 참여자는 토이 프로젝트에서는 중요하지 않을 수 있다고 한정하고, 현업에서는 절삭 방식에 따른 정산금 차이가 법적 문제나 사후 보정 부담으로 이어질 수 있어 경우별 정책을 정한다고 설명했다. 현재 계산이 실제로 잘못되었다고 확정한 것은 아니다.

- [ ] Line의 extraFare 필드를 다음 단계 요구사항을 고려해 미리 추가한 것인지 묻는다. (설계 질문)
  - 조건: 작성자는 2단계 요구사항을 고려해 넣었다고 답했다. 리뷰어가 선행 구현을 문제로 확정하거나 제거를 요구한 것은 아니다.
