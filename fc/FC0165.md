# FC0165 · AppUserService가 UserService 대신 Service 인터페이스를 구현한 것이 의도된 선택인지 물었다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0147](FC0147.md) · [다음 FC: FC0170 →](FC0170.md)

- [ ] AppUserService가 UserService 대신 Service 인터페이스를 구현한 것이 의도된 선택인지 물었다. (설계 질문)
  - 조건: 작성자는 잘못 들어간 부분이라고 답하고 수정하겠다고 했다. 리뷰 참여자는 의도를 확인하는 질문을 했으며, 실제 수정 결과는 제시되지 않았다.

- [ ] TxUserService 생성자가 구체 구현체 대신 트랜잭션 매니저 인터페이스를 주입받도록 변경하면 좋겠다. (개선 제안)
  - 조건: 현재 생성자 매개변수는 DataSourceTransactionManager다. 리뷰 참여자는 JTA나 Hibernate 등을 사용하게 되면 해당 클래스를 변경해야 한다는 교체 가능성 문제를 근거로 제안했다.

- [ ] TxUserService가 AppUserService를 직접 생성하는 결합을 줄이도록 UserService를 주입받자고 제안한다. (개선 제안)
  - 조건: 리뷰 참여자는 구체 클래스의 내부 생성으로 강결합이 발생하는 것으로 보인다고 설명했다. 작성자는 반영했다고 보고했으나 변경된 구현은 이 대화에서 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
interface Users { User find(UserId id); }
final class AppUsers implements Users {
    public User find(UserId id) { return store.get(id); }
}
```

**적용 설명:** 범용 Service보다 실제 제공 기능의 계약을 구현한다. store 필드와 생성자는 생략했다.
