## 검토 질문

- [ ] 같은 부하 조건에서 지연·처리량·DB 사용량을 비교해 커넥션 풀 크기를 결정하는가?

**직접 작성한 예시**

```csv
poolSize,p95_ms,throughput,db_cpu
4,측정값,측정값,측정값
8,측정값,측정값,측정값
```

**적용 설명:** 비교 실험 기록 템플릿이다. 동일 데이터·동시 사용자 수·워밍업 조건에서 측정하고 숫자를 결과로 가장하지 않는다.

## 구체적인 검토 사례

- [ ] 성능 관점의 적절한 커넥션 풀 크기는 직접 측정해 판단해야 한다는 의견을 제시한다. (의견)
  - 조건: 작성자는 테스트로 최대 성능을 내는 풀 크기와 근거를 찾겠다는 생각을 밝혔고, 리뷰 참여자도 성능은 직접 측정해야 알 수 있다고 답했다. 실제 측정 결과나 최적 크기는 제시되지 않았으며 이번 미션에서 필수로 수행하라는 요구도 아니다.

- [ ] 락 문제와 별개로 readOnly 설정에 따른 플러시 작업 차이가 읽기 성능에 영향을 줄 수 있다는 참고 의견을 제시한다. (의견)
  - 조건: 리뷰 참여자는 성능 차이가 있을 것 같지만 미미할 것으로 생각한다고 완화했고, GPT와 나눈 설명을 참고용으로 인용했다. 인용 내용은 Hibernate 사용 여부와 DB 최적화 등에 따라 달라진다는 조건을 포함하며, 실제 코드의 성능 측정이나 기술적 검증 결과는 제시되지 않았다. 읽기 전용 설정으로의 변경을 강제한 것은 아니다.

- [ ] 자동차를 일괄 삽입하지 않고 개별 삽입하더라도 서비스에서 하나의 트랜잭션으로 묶인 현재 방식은 유지해도 괜찮다는 의견을 제시했다. (의견)
  - 조건: 작성자가 자동차 수에 비례하는 삽입 쿼리를 줄이려 했으나 배치 삽입 후 생성 ID를 가져오는 방법을 찾지 못했다고 설명한 데 대한 답변이다. 리뷰 참여자는 ID 없이 다시 조회하기 어렵다는 점을 인정하고, 단일 트랜잭션을 근거로 현재 방식도 큰 문제가 없을 것으로 보았다. JDBC 지원 범위나 성능 효과가 실제로 확인된 것은 아니다.
