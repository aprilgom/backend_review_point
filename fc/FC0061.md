# FC0061 · 본문 없는 성공 응답의 계약

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0059](FC0059.md) · [다음 FC: FC0063 →](FC0063.md)

## 검토 질문

- [ ] 응답 본문이 없는 성공을 어떤 상태 코드로 표현할지 정하고 실제 전송 내용과 일치시키는가?

**직접 작성한 예시**

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
```

**적용 설명:** 본문 없는 성공 응답의 한 예다. 200도 계약에 따라 가능하며 204를 선택했다면 응답 본문을 보내지 않는다.

## 구체적인 검토 사례

- [ ] 본문을 반환하지 않는 성공 응답에 200을 사용한 이유와 이 경우 적절한 응답 상태 코드를 묻는다. (설계 질문)
  - 조건: 작성자는 성공이라는 의미로 200을 사용했으며, 본문이 필요 없는 경우 204를 반환하는 것으로 이해해 수정하겠다고 답했다. 204 사용을 리뷰 참여자가 직접 확정한 것은 아니며, 이후에는 REST API 학습 자료와 GitHub 문서를 추천했다. 외부 자료의 내용은 추출 근거로 보충하지 않았고, 작성자의 후속 URI 복수형 변경 계획은 별도의 리뷰 요구로 추출하지 않았다.

- [ ] 성공했지만 응답 본문이 없는 경우 어떤 HTTP 상태 코드를 반환하는 것이 적절한지 검토하도록 질문한다. (설계 질문)
  - 조건: 작성자는 204 No Content를 알게 되었다고 답했고, 리뷰어는 REST API 학습 자료를 추천했다. 리뷰어가 이 생성 API에 반드시 204를 사용하라고 확정한 것은 아니다.

- [ ] 예약 생성 응답에는 200 OK보다 201 Created가 적절하다고 제안하고, 다른 HTTP 상태 코드도 살펴보도록 질문했다. (개선 제안)
  - 조건: 작성자는 미션 API 명세가 200 OK를 지정해 처음에는 이를 따랐다고 설명했다. 이후 생성 의미를 더 구체적으로 표현한다는 이유로 201이 적절하다는 의견을 밝혔으나, 실제 변경 여부는 이 대화에서 확인되지 않는다.
