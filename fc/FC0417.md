# FC0417 · 서비스 테스트에서 Fake Repository가 중요한 DB 접근 동작을 가려 의미 있는 검증이 부족하다고 지적하고 실제 Repository를 사용하는 통합 테스트를 제안했다.

[소속 분야: 테스트 대상·검증](../21-test-behavior.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0416](FC0416.md) · [다음 FC: FC0418 →](FC0418.md)

- [ ] 서비스 테스트에서 Fake Repository가 중요한 DB 접근 동작을 가려 의미 있는 검증이 부족하다고 지적하고 실제 Repository를 사용하는 통합 테스트를 제안했다. (개선 제안)
  - 조건: 작성자는 독립적인 단위 테스트로 서비스 기능의 명세를 검증한다고 설명했다. 리뷰 참여자는 현재 테스트에서는 DB 접근에 문제가 있어도 통과할 수 있다고 지적했지만, 테스트 더블 자체는 테스트하기 어려운 부분에 유용할 수 있다고 인정했다. 작성자는 테스트 일관성을 위해 대역을 사용했다고 설명하면서도 DB 문제가 가려질 수 있다는 우려에 공감하고 통합 테스트로 바꾸겠다고 답했다. 모든 서비스 테스트를 통합 테스트로 작성해야 한다는 일반 규칙은 아니다.

- [ ] Fake Repository를 사용하는 테스트가 Service 흐름 검증인지 DB 연동 검증인지 목적과 검증 한계를 구분하도록 했다. (개선 제안)
  - 조건: JUnit만으로 단위 테스트를 작성하는 이번 미션에서 Fake 사용은 합리적이라고 평가했다. 다만 실제 SQL, 컬럼명 매핑, FK 제약은 검증하지 못한다고 설명했다. 작성자는 Service 흐름만 검증하겠다고 답했으며, 작성자의 'JUnit만으로 DB 연동 검증은 불가능하다'는 추가 해석을 리뷰 참여자의 주장으로 취급하지 않는다.

- [ ] 서비스 테스트에서 Repository를 모킹하기보다 실제 Repository와 함께 검증하는 통합 테스트를 권장한다. (개선 제안)
  - 조건: 리뷰 참여자는 내부 DB가 동작하지 않으면 서비스도 정상 동작할 수 없다는 이유로, 모킹은 외부 API 등 외부 서비스 의존성에 사용하는 것이 적절하다는 견해를 밝혔다. 이는 참여자의 테스트 전략 제안이지 보편적으로 확인된 규칙은 아니다. 작성자는 취지에 동의하면서 서비스와 Repository를 묶은 테스트 외에 Repository 테스트도 별도로 작성하는지 질문했으며, 그 질문에 대한 답변은 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
users.insert(new User("same"));
assertThrows(DuplicateName.class, () -> users.insert(new User("same")));
```

**적용 설명:** 실제 테스트 DB의 UNIQUE 제약과 예외 변환을 검증한다. 단순 Map fake가 같은 동작을 보장한다고 가정하지 않는다.
