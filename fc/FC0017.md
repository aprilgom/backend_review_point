# FC0017 · 공통 요청 처리 흐름의 재사용

## 검토 질문

- [ ] 요청 유형별 분기와 공통 처리 흐름을 상위 구조로 묶는 것이 중복과 이해 비용을 줄이는가?

**직접 작성한 예시**

```java
HttpReply handle(HttpRequest request) {
    return switch (request.method()) {
        case GET -> get(request);
        case POST -> post(request);
        default -> methodNotAllowed();
    };
}
```

**적용 설명:** 직접 만드는 컨트롤러의 분기 예시다. 공통 분기가 실제로 반복될 때 상위 클래스를 고려하고, 405 응답의 Allow 헤더도 구현한다.

## 구체적인 검토 사례

- [ ] Controller를 직접 구현한 이유를 묻고, AbstractController에서 HTTP 메서드별 처리를 분기하는 구조를 검토하자고 제안했다. (토론)
  - 조건: 참여자는 같은 URL의 다른 HTTP 메서드마다 컨트롤러 클래스를 만들어야 하는 점을 우려하고 Servlet·HttpServlet 구조를 비교 대상으로 설명했다. 원하는 구조를 적용할 자유는 인정하면서 톰캣 구조의 의도를 학습해 보라고 제안했으며, 작성자의 설계 이유나 후속 변경은 없다.

- [ ] 지원하지 않는 HTTP 메서드에 대한 응답을 각 컨트롤러에서 반복 구현하지 말고 추상 클래스로 공통화하자는 제안이다. (개선 제안)
  - 조건: IndexController.post가 methodNotAllowed 응답을 반환하는 코드에 대한 의견이다. 실제 추상화 적용 여부는 제시되지 않았다.

- [ ] 지원하지 않는 HTTP 메서드의 처리를 개별 컨트롤러마다 구현하지 말고 AbstractController로 모으는 방식을 제안한다. (개선 제안)
  - 조건: UserController의 doGet에서 methodNotAllowed를 호출하는 코드가 대상이다.
