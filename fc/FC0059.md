# FC0059 · API와 페이지 URL 경로의 결정 기준을 묻고 RESTful 경로 설계와 자신의 선택 기준을 고민해 볼 것을 제안했다.

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0058](FC0058.md) · [다음 FC: FC0061 →](FC0061.md)

- [ ] API와 페이지 URL 경로의 결정 기준을 묻고 RESTful 경로 설계와 자신의 선택 기준을 고민해 볼 것을 제안했다. (토론)
  - 조건: 작성자는 페이지 경로를 자원과 조건·필터링의 조합으로 정했고 API는 요구사항 명세를 따랐다고 설명했다. 이후 일관성과 가독성을 중요하게 여기지만 확립된 기준은 없어 다음 미션에서 발전시키겠다고 답했다. 리뷰어가 현재 경로를 확정적인 결함으로 지적하거나 특정 대체 경로를 요구한 것은 아니다.

- [ ] 경로 조회 URI를 `/route`로 두고 최단 경로 여부를 쿼리 옵션으로 표현하는 방식을 제안한다. (개선 제안)
  - 조건: 작성자는 `/route`에는 동의했지만 현재 요구사항이 최단 경로 조회뿐이므로 별도 옵션이 필요한지 반문했다. 옵션 도입에 대한 후속 합의는 확인되지 않는다.

- [ ] 경로 조회도 자원을 요청하는 API이므로 URI를 복수형으로 표현하는 것을 제안했다. (개선 제안)
  - 조건: 현재 /path 매핑에 대한 자원 명명 제안이며, 모든 API가 반드시 복수형이어야 한다는 보편 규칙으로 단정하지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```text
GET /api/tasks/17     # 데이터 조회
GET /tasks/17         # HTML 화면
DELETE /api/tasks/17  # 데이터 삭제
```

**적용 설명:** 화면과 데이터 경로를 구분한 한 가지 규약이다. 경로 이름보다 일관된 리소스·메서드 의미가 중요하다.
