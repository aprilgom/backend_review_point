# FC0464 · 식별자의 발급 전후 상태

[소속 분야: 타입·타입 테스트](../24-type-safety.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0456 →](FC0456.md)

## 검토 질문

- [ ] 미발급 식별자와 유효한 식별자를 null·타입 등으로 명확히 표현하고 임의 숫자에 의미를 숨기지 않는가?

**직접 작성한 예시**

```java
record ExistingOrderId(long value) {}
Long unsavedEntityId = null;
```

**적용 설명:** 이미 존재하는 ID와 아직 발급되지 않은 ID의 상태를 구분한다. 0을 무조건 미저장 표식으로 쓰지 않는다.

## 구체적인 검토 사례

- [ ] ID 타입으로 Long 대신 long을 선택한 이유와 null 허용 조건을 확인했다. (토론)
  - 조건: 작성자는 null을 허용하지 않고 더 작은 기본형을 사용하려 했다고 설명했다. 리뷰 참여자는 ID가 null이면 안 된다는 조건이라면 적절한 선택이라고 답했다. Long으로 변경하라는 요구나 기존 지적의 철회는 아니다.

- [ ] id 타입으로 Long을 선택한 이유와 요청 값 바인딩에서 Long과 long이 갖는 차이를 설명해 달라고 요청했다. (설계 질문)
  - 조건: 작성자가 Long 사용은 실수였다며 long으로 바꿨다고 하자, 리뷰어는 long이 더 나은 이유와 JSON 바인딩 차이를 추가로 물었다. 작성자는 누락 값의 기본값 처리, 예외 처리와 효율성 등을 선택 근거로 제시하고 경로 변수의 권장 타입을 되물었다. 해당 근거에 대한 리뷰어의 확인이나 최종 답변은 없다.

- [ ] 예약 id의 타입으로 long 대신 Long을 선택한 이유를 묻는다. (설계 질문)
  - 조건: 작성자는 기본형에서 0이나 별도 상수로 빈 값을 나타내는 대신 Long의 null로 id 부재를 명확하게 표현하려 했다고 답했다. 타입 선택에 대한 결함 지적이나 변경 요구는 아니다.
