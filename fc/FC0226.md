# FC0226 · 변경 경로의 불변식 보장

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0223](FC0223.md) · [다음 FC: FC0228 →](FC0228.md)

## 검토 질문

- [ ] 생성 시 적용한 규칙이 수정 경로에서도 유지되며 시간·외부 상태에 의존하는 조건은 다시 확인하는가?

**직접 작성한 예시**

```java
void reschedule(Slot next) {
    requireAvailable(next);
    this.slot = next;
}
```

**적용 설명:** 생성뿐 아니라 변경 경로에서도 현재 상태에 의존하는 검증을 실행한다. 경쟁 조건은 저장 단계에서도 처리한다.

## 구체적인 검토 사례

- [ ] 예약 생성 시 수행하는 검증을 `updateReservation`에서도 수행해야 하지 않는지 질문했다. (설계 질문)
  - 조건: 인라인 문맥에는 예약 날짜·시간 및 중복 여부 검증이 나타난다. 작성자는 생성에만 있던 과거 시점 및 중복 검증을 수정 대상 정보에도 추가했다고 보고했다. 당일·과거 예약의 수정과 취소를 막는 `validateModifiable`도 적용했다는 내용은 작성자의 추가 설명이며, 별도의 리뷰어 요구나 검증된 구현 결과로 보지 않는다.

- [ ] Reservation에 null 값이 요청되는 경우를 고려해 값 검증을 추가할 것을 제안했다. (개선 제안)
  - 조건: 작성자는 Reservation과 ReservationTime의 도메인 검증, Service의 날짜 시점 검증, RequestDTO의 요청 필드 검증을 추가했다고 보고했다. 이어 DB에서 조회한 ReservationTime을 Service에서 다시 검증할지 Reservation 생성 시 검증으로 포함할지 질문했으나, 이에 대한 리뷰어의 답변은 없다.

- [ ] ReservationTime 생성 시 검증을 가장 먼저 수행하는 것이 좋지 않은지 제안했다. (개선 제안)
  - 조건: 작성자는 BaseEntity 생성자에서 ID를 검증하므로 이미 검증이 먼저 수행된다고 설명했다. 다만 super 호출에서 검증 의도가 드러나지 않는다고 보고 BaseEntity를 제거하겠다고 했으며, 이는 작성자의 판단과 변경 계획이지 리뷰어가 별도로 요구한 추상화 제거는 아니다.
