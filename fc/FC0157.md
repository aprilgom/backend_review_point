# FC0157 · 시간 의존성의 제어

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0170](FC0170.md) · [다음 FC: FC0167 →](FC0167.md)

## 검토 질문

- [ ] 현재 시각처럼 제어하기 어려운 값을 외부에서 공급해 시간대·경계 조건을 재현할 수 있는가?

**직접 작성한 예시**

```java
LocalDate today = LocalDate.now(clock);
boolean expired = deadline.isBefore(today);
```

**적용 설명:** Clock을 생성자로 주입하면 테스트에서 날짜를 고정할 수 있다. 서비스의 기준 시간대도 명시한다.

## 구체적인 검토 사례

- [ ] LocalDateTime.now()처럼 제어하기 어려운 요소를 밖으로 분리해 테스트 가능한 영역을 확보하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 현재 시간 의존성이 추후 테스트 작성을 어렵게 할 수 있다고 우려했다. 작성자는 단순 날짜 데이터를 위해 DateTimeGenerator 의존성과 인터페이스를 추가하면 복잡도가 늘고, 현재 시간을 반환하는 스텁도 기존 테스트와 차이가 불분명하다고 반론했다. 작성자는 납득되지 않아 변경하지 않았다고 밝히고 추가 의견을 요청했으며, 후속 답변은 제공되지 않았다.

- [ ] LocalDateTime.now()를 내부에서 직접 호출하기보다 상위에서 시간을 전달받아 테스트하기 쉽게 만들자는 제안이다. (조건부 제안)
  - 조건: 작성자는 JPA Auditing으로 생성 시간을 자동 생성하고 있다며, 시간을 사용하는 비즈니스 로직이 생길 때 검증을 고려해도 되지 않는지 물었다. 이후 외부에서 주입할 수 없도록 생성자를 바꿨다고 보고했다. 리뷰 참여자는 비즈니스상 시간 검증이 필요 없다면 중요하지 않다고 완화하면서, 시간 생성을 상위 경계로 밀어내는 것은 자신의 평소 습관이라고 설명했다. 현재 구현의 결함이나 필수 변경으로 단정하지 않는다.

- [ ] 제어할 수 없는 시간 때문에 테스트가 어렵다면 시간 의존성을 주입하도록 리팩터링할 수 있으며, Clock뿐 아니라 LocalDate를 직접 주입하는 대안도 검토한다. (개선 제안)
  - 조건: 리뷰 참여자는 테스트의 어려움을 개선하는 리팩터링을 긍정적으로 보되 Clock의 적절성은 활용 방식에 따라 다르다고 설명했다. LocalDate 주입은 고려할 대안이지 필수 요구가 아니다. 작성자는 다양한 Java 시간 API를 일관되게 사용하려고 Clock 주입으로 변경했다고 보고했다.
