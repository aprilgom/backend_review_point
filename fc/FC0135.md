# FC0135 · 구성 요소의 변경 책임

## 검토 질문

- [ ] 집합과 구성 요소 중 누가 생성·추가·삭제를 통제해야 불변식과 수명 관리가 명확한가?

**직접 작성한 예시**

```java
class Menu {
    private final List<MenuItem> items = new ArrayList<>();
    void add(MenuItem item) { items.add(item); }
}
```

**적용 설명:** 구성 요소의 변경을 상위 객체가 통제하는 방향이다. 영속화 연관관계 소유 측과 도메인 탐색 방향은 구분한다.

## 구체적인 검토 사례

- [ ] MenuProduct가 Menu를 다대일로 참조하는 대신 Menu가 MenuProduct를 일대다로 참조하도록 선택한 이유를 물었다. (설계 질문)
  - 조건: 작성자는 객체지향적으로 일대다 단방향 참조가 자연스럽다고 생각했다고 설명했다. 질문 자체는 해당 매핑이 잘못되었다는 확정 지적이 아니다.

- [ ] Menu 생성 시 menuProducts를 함께 전달하지 않고 저장 후 변경하는 이유를 묻고, MenuProduct를 가진 Menu를 저장하는 구성을 제안했다. (설계 질문)
  - 조건: 작성자는 2단계에서는 의존관계 변경을 적용하지 않았으며, 3단계에서 Menu 내부에 MenuProduct를 가지도록 변경했다고 설명했다. 이는 작성자의 변경 보고이다.

- [ ] 메뉴 가격 검증에 상품 가격이 필요한 상황에서 MenuProduct가 Product 대신 productId만 보유하는 관계 설계의 어려움을 논의했다. (토론)
  - 조건: 리뷰 참여자는 Menu에서 검증하려면 MenuProduct를 거쳐 Product를 알아야 한다는 점을 짚고, 자신의 구현에서는 Menu가 임베디드 MenuProduct 컬렉션을 보유하고 MenuProduct가 Product를 참조하도록 했다고 설명했다. 개인적인 사견이며 반드시 반영할 필요는 없다고 명시했다. 후속 승인만으로 해당 설계가 적용되었다고 단정할 수 없다.
