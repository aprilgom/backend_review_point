# FC0300 · 진단용 문자열 표현의 범위

[소속 분야: 가독성·명명](../17-readability.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0309](FC0309.md) · [다음 FC: FC0306 →](FC0306.md)

## 검토 질문

- [ ] 객체 문자열 표현이 진단에 도움이 되면서 민감 정보·순환 참조·과도한 출력은 피하는가?

**직접 작성한 예시**

```java
@Override public String toString() {
    return "Answer[id=" + id + ", state=" + state + "]";
}
```

**적용 설명:** 진단 가치가 있는 안전한 필드만 표현한다. 본문·비밀값·연관 객체의 무한 순환을 피한다.

## 구체적인 검토 사례

- [ ] Answer에서 toString을 제거한 이유를 묻는다. (설계 질문)
  - 조건: 제거 이유에 대한 답변은 없으며, toString을 복구해야 한다는 요구로 확대하지 않는다.

- [ ] 실제로 이름만 수정하는 코드에서 `profile`이라는 개념과 명칭을 사용한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 비밀번호와 이메일을 제외한 사용자 정보를 수정하는 API라는 의미로 profile을 사용했으며, 현재 수정 가능한 해당 정보가 이름뿐이라고 설명했다. 이 대화 안에는 명칭 변경 요구나 설명에 대한 후속 판단이 없다.

- [ ] OrderController의 클래스 시작부에만 공백 한 칸이 없는 이유를 묻는다. (설계 질문)
  - 조건: 클래스 선언 직후 필드 선언이 이어지는 부분에 대한 서식 질문이다. 작성자의 답변이나 수정 보고는 없다.
