# FC0370 · 서비스 계층의 도입 이유

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0378](FC0378.md) · [다음 FC: FC0366 →](FC0366.md)

## 검토 질문

- [ ] 서비스가 실제 유스케이스 조율 책임을 가지는지 단순 전달 계층만 미리 늘리는지 검토했는가?

**직접 작성한 예시**

```java
Receipt placeOrder(CreateOrder command) {
    Order order = Order.create(command.lines());
    orders.save(order);
    return Receipt.from(order);
}
```

**적용 설명:** 유스케이스 조율 책임이 있을 때 서비스 계층의 의미가 생긴다. 도메인 규칙은 Order에 둔다.

## 구체적인 검토 사례

- [ ] Service 계층의 역할을 정리하고, 현재 구현에서 계층 분리가 필요한지와 미리 분리하는 방식의 장단점을 검토하도록 요청했다. (토론)
  - 조건: 작성자가 처음에는 여러 DAO 작업의 트랜잭션 보장을 중심으로 설명하자, 리뷰어는 DAO에서 묶는 것과의 차이 및 서비스의 더 넓은 역할을 다시 물었다. 작성자는 이후 컨트롤러의 HTTP 관심사와 도메인 호출·저장 흐름을 분리하기 위해 게임 진행 로직을 서비스로 위임했다고 보고했다. 리뷰어는 분리 자체를 필수로 요구한 것이 아니라 현재 필요성과 분리 시점의 장단점을 고민하자는 취지이며, 어느 정도 취향의 문제일 수도 있다고 명시했다.

- [ ] Controller·Service·DAO로 계층을 분리한 이유와 장단점을 설명하고, 다른 구조와 비교해 볼 것을 요청했다. (토론)
  - 조건: 작성자는 명시적인 설계 근거 없이 페어의 제안을 따라 자연스럽게 구조가 만들어졌고 DAO 이해가 부족하다고 답했다. 리뷰 참여자는 모든 로직을 한 곳에 두거나 Controller와 DAO만 두는 대안도 생각한 뒤 MVC의 역사 등을 읽어보라고 권했다. 특정 계층 구성을 반드시 사용하거나 제거하라는 요구는 아니다.

- [ ] 컨트롤러와 서비스 계층의 역할을 설명하고 현재 기능에 서비스 계층이 필요한지 검토하도록 요청했다. (토론)
  - 조건: 리뷰어는 이전 체스 미션의 서비스 사용 경험도 물었다. 작성자는 1·2단계는 간단한 CRUD라 서비스를 생략했고, 3단계에서는 복잡한 비즈니스 로직이 필요할 것으로 판단해 추가했다고 설명했다. 리뷰어는 역할 이해를 긍정했지만 서비스가 항상 필수라고 요구하지는 않았다.
