# FC0283 · 첫 매칭과 임의 매칭의 계약

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0275](FC0275.md) · [다음 FC: FC0284 →](FC0284.md)

## 검토 질문

- [ ] 여러 후보가 일치할 때 순서가 의미 있는지 확인하고 탐색 API를 그 계약에 맞게 선택하는가?

**직접 작성한 예시**

```java
HandlerAdapter selected = adapters.stream()
    .filter(a -> a.supports(handler)).findFirst().orElseThrow();
```

**적용 설명:** 여러 어댑터가 지원할 때 순서가 계약이면 findFirst를 유지한다. 아무 매칭이나 허용될 때만 findAny를 고려한다.

## 구체적인 검토 사례

- [ ] 핸들러 어댑터 탐색에서 findFirst와 findAny의 차이를 살펴보고 findAny 사용을 고려하도록 제안한다. (개선 제안)
  - 조건: 리뷰 참여자는 병렬 시퀀스를 사용하지 않는 현재 상황에서 같은 동작을 하면서 성능상 이점이 있을 수 있다고 설명했다. 이는 리뷰 참여자의 주장으로, 성능 측정 결과나 실제 대체 가능성이 확인된 것은 아니다. 외부 링크 내용은 추가 근거로 사용하지 않았다.

- [ ] addController를 호출할 때마다 ControllerScanner.scan을 반복하지 않도록 컨트롤러별 어노테이션 메서드 탐색 방식으로 바꾸자고 제안했다. (개선 제안)
  - 조건: 작성자도 매번 스캐너를 호출할 필요가 없었다고 답했다. 반복 호출에 대한 지적이며 성능 측정이나 개선 효과는 제시되지 않았다.

- [ ] View에서 컴파일한 템플릿을 재사용할 수 있는지 검토하도록 제안한다. (개선 제안)
  - 조건: 작성자는 View 내부의 static Map으로 캐싱해 보았다고 보고했다. 캐시 구현의 적절성이나 성능 개선 효과가 검증된 것은 아니다.
