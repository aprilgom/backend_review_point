# FC0025 · 생성 요청과 수정 요청에 실제 차이가 없다면 미래 확장만을 예상해 DTO를 미리 분리하지 않고 하나로 유지하는 방안을 제안한다.

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0020](FC0020.md) · [다음 FC: FC0027 →](FC0027.md)

- [ ] 생성 요청과 수정 요청에 실제 차이가 없다면 미래 확장만을 예상해 DTO를 미리 분리하지 않고 하나로 유지하는 방안을 제안한다. (조건부 제안)
  - 조건: 리뷰어는 Create와 Update에 차이가 있다면 분리해도 좋지만, 차이가 없으면 관리 지점만 두 곳으로 늘어난다고 설명했다. 작성자는 편의성과 확장성을 위해 미리 분리했으나 생각이 바뀌어 MemberRequest로 합치겠다고 답했다. 실제 통합 완료는 확인되지 않는다.

- [ ] 생성과 수정에 같은 CustomerRequest를 공유하면 요청별 변경이 다른 기능에 영향을 줄 수 있으므로 DTO를 분리하는 편이 좋다는 의견을 제시했다. (의견)
  - 조건: 현재 DTO로 두 요청을 처리할 수 있다는 점은 인정하면서 개인 의견으로 제시했다. 향후 요청 형태가 달라지거나 협업자가 공유 사실을 놓치거나 한 요청에만 맞는 로직을 추가할 때의 위험을 강조했다. 작성자는 취지에 공감했지만 첨부 이미지와 외부 글만으로 구현 변경을 확정하지 않는다.

- [ ] 생성과 수정의 요청 DTO가 동일하고 분리할 필요가 없다면 굳이 나누지 않아도 된다는 의견을 제시한다. (조건부 제안)
  - 조건: 작성자는 현재 두 DTO가 동일하므로 불필요한 복잡성을 피하려고 공용 DTO를 사용했다고 설명했고, 리뷰어는 필요하지 않다면 나누지 않아도 된다고 동의했다. 이후 요구가 달라져도 항상 공유해야 한다는 뜻은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record LabelInput(String name, String color) {}
Label create(LabelInput input) { return labels.create(input); }
void update(long id, LabelInput input) { labels.update(id, input); }
```

**적용 설명:** 생성·수정의 필수값과 검증이 동일할 때의 공유 예시다. 부분 수정 등 계약이 달라지면 분리한다.
