# FC0116 · 조회 컬럼의 명시

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0117 →](FC0117.md)

## 검토 질문

- [ ] 실제로 필요한 컬럼만 조회해 전송량과 스키마 변경 영향을 제한하는가?

**직접 작성한 예시**

```sql
SELECT id, display_name FROM account WHERE id = :id;
```

**적용 설명:** 사용하는 컬럼을 명시하면 불필요한 전송과 스키마 변경의 영향을 줄일 수 있다.

## 구체적인 검토 사례

- [ ] 조회 쿼리에서 컬럼을 명시하지 않고 SELECT *를 그대로 사용할 때의 단점을 검토했는지 질문한다. (설계 질문)
  - 조건: 리뷰 참여자는 구체적인 결함을 단정하지 않고 단점 여부를 물었다. 작성자는 모든 컬럼이 필요해 사용했다고 설명하고, 불필요한 데이터 조회 비용, 컬럼 인덱스 의존 시 순서 변경 영향, JOIN 시 중복 컬럼명 문제를 학습했다고 답했다. 이 설명은 작성자의 학습 보고이며 해당 쿼리에서 그러한 문제가 실제 발생했다는 확인은 아니다. 작성자는 앞으로 컬럼명을 명시하겠다고 밝혔다.

- [ ] SELECT *를 사용하면 필드가 늘어날 때 필요하지 않은 컬럼까지 계속 조회하게 될 수 있다는 점에 대해 의견을 묻는다. (설계 질문)
  - 조건: 리뷰 참여자는 현재 필드 수가 적다는 점을 인정하면서 향후 불필요한 조회 가능성을 제기했다. 작성자는 무의식적으로 사용했다고 답하고 속도와 인덱싱 등도 학습하겠다고 했으나, 실제 성능 저하가 확인된 것은 아니다.

- [ ] 테마 조회 쿼리에서 SELECT *를 사용할 때 발생할 수 있는 문제를 검토해 보라는 질문이다. (설계 질문)
  - 조건: 리뷰어는 현재 구현이 간단하다는 점을 인정하며 참고용으로 질문했다. 작성자는 컬럼 증가 시 불필요한 데이터 조회 비용, 필요한 컬럼의 불명확성, 조인 시 컬럼명 중복 가능성을 학습한 내용으로 답했다. 이 설명을 리뷰어가 직접 제기한 개별 결함으로 확대하거나 현재 쿼리의 성능 문제가 확인된 것으로 해석하지 않는다.
