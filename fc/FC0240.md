# FC0240 · 예상 오류와 예상 밖 예외의 구분

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [다음 FC: FC0241 →](FC0241.md)

## 검토 질문

- [ ] 일부 예외만 처리한 뒤 나머지가 어떻게 전파되는지 알고 서버 결함과 입력 오류를 구분하는가?

**직접 작성한 예시**

```java
try { return endpoint.handle(request); }
catch (InvalidInput invalid) { return error(400, "INVALID_INPUT"); }
catch (Exception unexpected) { recordFailure(unexpected); return error(500, "INTERNAL_ERROR"); }
```

**적용 설명:** 예상 입력 오류와 예상 밖 서버 오류를 구분한다. 가장 바깥 요청 경계에서만 일반 예외를 처리하는 예다.

## 구체적인 검토 사례

- [ ] IllegalArgumentException만 처리하는 예외 처리 클래스에서 다른 예외가 발생하면 어떻게 되는지 검토하도록 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 코드 반영이 필요한 경우 다음 단계에서 진행해 달라고 했다. 다른 예외의 실제 응답이나 필요한 수정 방법은 이 대화에서 확인되지 않았다.

- [ ] 예외별 처리를 구분할 이유가 없다면 여러 예외를 하나의 ExceptionHandler에서 처리하는 방안을 제안했다. (조건부 제안)
  - 조건: 리뷰 참여자는 ExceptionHandler에 여러 예외를 지정할 수 있다는 점을 근거로, 별도 처리가 필요하지 않은 경우에 한해 통합을 제안했다. 작성자는 공통 부모 예외 클래스를 만들어 하나의 핸들러에서 처리하도록 수정했다고 답했다. 부모 클래스 도입 자체가 리뷰 참여자의 요구였던 것은 아니다.

- [ ] 예외 응답 계약을 지키기 위해 ExceptionHandler를 적용하고, 추가한 처리기에서 다른 예외도 처리해보도록 제안했다. (개선 제안)
  - 조건: 작성자는 예외 처리가 다음 사이클 요구사항이라고 이해해 핵심 기능에 우선 집중했다고 설명하면서 공통 예외 처리의 필요성에 동의했다. 리뷰 참여자는 다음 사이클의 내용을 모른다고 밝혔고, 후속 댓글에서 GlobalExceptionHandler가 추가되었다고 언급하며 다른 예외로 처리 범위를 넓히도록 권했다. 모든 예외 처리의 완성 여부는 확인되지 않는다.
