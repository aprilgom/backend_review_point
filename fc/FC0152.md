# FC0152 · 의존 객체를 new로 직접 생성하는 대신 의존성 주입을 사용하는 이유를 설명해 달라고 묻는다.

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0156](FC0156.md) · [다음 FC: FC0154 →](FC0154.md)

**혼합·경계:** 의존성 주입의 일반적인 목적과 컨테이너 사용 사례가 섞임.

- [ ] 의존 객체를 new로 직접 생성하는 대신 의존성 주입을 사용하는 이유를 설명해 달라고 묻는다. (설계 질문)
  - 조건: 스프링을 학습 중인 작성자에게 제시한 학습 질문이다. 작성자는 답변을 외부 문서로 정리했다고 보고했으며 문서 본문은 제공되지 않았다. 리뷰 참여자는 스프링 컨테이너를 통한 객체 생명주기 관리와 관계 연결을 설명하고, 전형적인 내용의 학습에 ChatGPT를 활용해 보라고 제안했다. 이 설명을 모든 의존성 주입의 보편적 정의로 확장하지 않는다.

- [ ] 현재 구현을 통해 의존성 주입으로 구현체를 선택해 사용하는 장점을 이해했는지 질문했다. (설계 질문)
  - 조건: 콘솔 애플리케이션에서 InMemory DAO들을 생성해 서비스와 컨트롤러에 전달하는 구현을 대상으로 한 학습 확인 질문이다. 구현 결함이나 추가 변경 요구로 제시된 것은 아니며 작성자의 답변은 없다.

- [ ] 의존성을 분리하는 이유가 무엇인지 설명을 요청한다. (설계 질문)
  - 조건: 승인 총평에 포함된 설계 이유에 대한 질문이며, 해당 단위에는 작성자의 답변이 없다. 승인을 질문의 해결 근거로 보지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
ReportService service = new ReportService(new FileExporter());
ReportService testService = new ReportService(new InMemoryExporter());
```

**적용 설명:** 생성 결정을 호출자에게 넘겨 환경별 구현을 바꾼다. 프레임워크가 없어도 적용할 수 있다.
