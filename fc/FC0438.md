# FC0438 · 테스트 픽스처의 의도와 가변성

## 검토 질문

- [ ] 반복 객체 생성을 의미 있는 픽스처로 묶되 시나리오 차이와 공유 가변 상태를 숨기지 않는가?

**직접 작성한 예시**

```java
static Order pendingOrder() {
    return Order.create(List.of(new Line("sample", 1)));
}
```

**적용 설명:** 의도가 분명한 기본 fixture다. 테스트별 차이는 인자로 받아 드러내고 공유 가변 객체는 피한다.

## 구체적인 검토 사례

- [ ] 테스트에서 비슷한 객체를 반복 생성하는 대신 Test Fixture를 만들어 재사용하자는 제안이다. (개선 제안)
  - 조건: 작성자는 재사용 가능한 객체를 Fixture 클래스에 정의해 불러오도록 변경했다고 보고했다. 실제 변경의 적절성이나 테스트 결과까지 확인된 것은 아니다.

- [ ] 자주 사용하는 테스트 객체를 Fixture로 분리하여 테스트 준비의 반복 작업을 줄이자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 NORMAL_MEMBER_1과 같은 재사용 객체를 예로 들었다. 작성자는 자주 사용하는 클래스의 객체를 Fixtures 클래스로 분리했다고 보고했으며, 실제 변경 내용은 별도로 확인되지 않았다.

- [ ] 테스트 데이터 생성에 빌더를 적용해 fixture 메서드 수를 줄이고 구성을 간소화하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 자신의 빌더 적용 경험을 공유했고, 작성자는 해당 코드를 참고해 빌더 패턴을 고려하겠다고 답했다. 실제 적용 여부는 제시되지 않았다.
