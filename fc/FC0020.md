# FC0020 · ManualHandlerMapping을 수정하지 않는 방향이라면 HandlerAdapter 도입을 고려해 보라고 제안했다.

[소속 분야: 추상화·중복](../01-abstraction.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0017](FC0017.md) · [다음 FC: FC0025 →](FC0025.md)

- [ ] ManualHandlerMapping을 수정하지 않는 방향이라면 HandlerAdapter 도입을 고려해 보라고 제안했다. (조건부 제안)
  - 조건: 참여자는 현재 execute 메서드를 찾아 HandlerExecution으로 만드는 구현을 칭찬한 뒤 대안을 제시했다. ManualHandlerMapping을 수정하지 않고 HandlerExecution을 하나로 사용하는 경우라는 조건을 붙였으며, 현재 구현을 결함으로 단정하거나 Adapter 도입을 의무화하지 않았다.

- [ ] HandlerAdapter를 인터페이스로 분리하고도 여러 핸들러 타입을 하나의 구현체에서 처리하도록 한 이유를 질문했다. (설계 질문)
  - 조건: 참여자는 타입별 HandlerAdapter 구현체를 둘 수 있다는 대안을 제시했다. 작성자의 적용했다는 답변만으로 구현체 분리 여부나 그 설계 이유까지 확인할 수는 없다.

- [ ] Handler의 타입별 실행 분기를 ManualHandlerMapping과 AnnotationHandlerMapping처럼 구분하는 구조로 리팩터링할 수 있다고 제안했다. (개선 제안)
  - 조건: HandlerExecution과 Controller를 instanceof로 구분하는 코드에 대한 제안이다. 구체적인 클래스 이름이나 인터페이스 설계까지 명시한 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
interface HandlerAdapter {
    boolean supports(Object handler);
    HttpReply invoke(Object handler, HttpRequest request);
}
```

**적용 설명:** 핸들러를 찾는 매핑과 호출 방법을 분리한다. supports가 겹칠 때의 선택 규칙과 미지원 처리도 필요하다.
