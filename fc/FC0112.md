# FC0112 · 식별자의 고유성 검증

[소속 분야: 엔티티 동등성·식별](../06-identity.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0114](FC0114.md) · [다음 FC: FC0115 →](FC0115.md)

## 검토 질문

- [ ] 같은 식별자를 가진 객체가 중복 저장될 수 있는지 생성·저장·DB 제약 경계에서 확인했는가?

**직접 작성한 예시**

```java
bookings.add(new Booking(new BookingId(7)));
assertThrows(DuplicateBooking.class, () -> bookings.add(new Booking(new BookingId(7))));
```

**적용 설명:** 같은 식별자가 두 번 추가되는 경우를 검증한다. 저장소에도 고유 제약을 두어 경쟁 조건을 방어한다.

## 구체적인 검토 사례

- [ ] id를 예약 식별자로 본다면 같은 id의 예약도 추가할 수 있는지 테스트하고, 예약 번호라고 해도 고유해야 하지 않는지 검토하도록 질문했다. (설계 질문)
  - 조건: 작성자는 id를 중복 가능한 예약 번호로 해석하고, 요청 DTO가 id를 받지 않으므로 날짜·시간 중복 검증을 추가했다고 설명했다. 리뷰 참여자는 예약 번호도 고유해야 하지 않는지 재질문했다. id 중복 허용의 타당성과 테스트 결과는 확인되지 않았으며, 날짜·시간 검증 추가는 작성자의 보고다.

- [ ] 이름보다 ID와 같은 식별 가능한 키를 중심으로 설계하는 것이 변경 대응에 유리하며, ID 노출을 피하려고 유사한 값을 대신 만드는 것이 적절한지 검토하자는 논의다. (토론)
  - 조건: 작성자는 클라이언트가 DB 내부 ID를 알면 안 되거나 알 수 없다고 생각해 LineNumber를 사용했다고 설명했고, 문자열 비교 비용도 고려했다며 변경 대응에 유리한 이유를 물었다. 리뷰 참여자는 키가 ID를 뜻한다고 확인하고, 보안 우려는 별도로 해결하되 식별 가능한 값을 사용해야 한다고 주장했다. 요청 필드 변환, HTTPS, 암호화 등은 리뷰 참여자가 제시한 예시이며, 해당 보안 우려에 대한 효과나 기술적 타당성이 이 대화에서 검증된 것은 아니다. 최종 구현 결과도 확인되지 않는다.

- [ ] 자동 생성 식별자를 사용하는 Member 생성자에서 id를 직접 설정할 필요가 있는지 물었다. (설계 질문)
  - 조건: 작성자는 JDBC Template 사용 당시의 코드가 남아 있었으며 JPA 전환 후에는 직접 id를 설정할 필요가 없어졌다고 답했다. 실제 제거 여부는 대화에서 확인되지 않는다.
