# FC0374 · 계층별 DTO의 소유와 변환

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0365](FC0365.md) · [다음 FC: FC0361 →](FC0361.md)

## 검토 질문

- [ ] 입력 모델이 어느 계층의 계약인지 명확하고 계층별 분리의 이점이 변환 비용을 정당화하는가?

**직접 작성한 예시**

```java
package application;
public record RenameTagCommand(long id, String name) {}
```

**적용 설명:** 계층 간 계약을 어느 계층이 소유하는지 명시한다. HTTP 검증 애너테이션과 도메인 규칙을 무심코 혼합하지 않는다.

## 구체적인 검토 사례

- [ ] Request DTO를 Controller 패키지가 아니라 Service 패키지에 둔 이유와 계층별 DTO 분리 방식을 논의했다. (토론)
  - 조건: 작성자는 Service가 Controller 패키지에 의존하지 않도록 배치했으나, Swagger 적용 후 표현 계층 관련 요소가 생겨 요청 DTO를 Controller로 옮기고 별도의 Service DTO를 만들었다고 설명했다. 리뷰어는 이 방식과 Service DTO를 제거하는 방식 모두 가능하며, 연습 단계에서는 두 계층의 DTO를 다르게 사용해 봐도 좋다고 덧붙였다. DTO 분리를 필수 규칙으로 요구하지 않았다.

- [ ] 현재 DTO의 사용 범위를 고려할 때 dto 패키지를 dao 하위에 두는 구조가 적절한지 질문했다. (설계 질문)
  - 조건: 패키지 소유와 배치의 적절성을 묻는 것으로, 구체적인 대체 패키지나 이동 결과는 제시되지 않았다.

- [ ] DTO 패키지의 위치는 컨트롤러와 서비스 중 어느 계층이 DTO를 사용하는지에 맞춰 정하는 것이 적절하다는 의견이다. (조건부 제안)
  - 조건: 두 계층이 모두 사용한다면 어느 쪽에도 속하지 않는 패키지를, 컨트롤러만 사용한다면 컨트롤러 내부 패키지를 제안했다. 작성자는 두 계층이 함께 사용하는 상황이라고 설명하며 DTO를 외부로 옮겼다고 보고했다.
