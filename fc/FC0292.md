# FC0292 · 역과 노선의 변경이 드물다면 그래프를 매번 구성하는 대신 애플리케이션 시작 시나 첫 경로 조회 시 생성해 재사용하는 방안을 고민해 보자고 제안했다.

[소속 분야: 성능·측정](../16-performance.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0274](FC0274.md) · [다음 FC: FC0293 →](FC0293.md)

- [ ] 역과 노선의 변경이 드물다면 그래프를 매번 구성하는 대신 애플리케이션 시작 시나 첫 경로 조회 시 생성해 재사용하는 방안을 고민해 보자고 제안했다. (토론)
  - 조건: 참여자는 개인적인 궁금증이므로 고민만 해 보라고 명시했다. 작성자는 변경이 드물다는 전제에 동의하며 역이나 노선이 변경될 때만 그래프를 다시 그리는 방안을 제시했다. 실제 캐시 도입이나 성능 측정 결과는 보고되지 않았다.

- [ ] 역과 구간이 자주 추가되지 않는다는 전제에서, 경로 조회마다 그래프를 새로 만들지 않는 방안을 검토하고 개선해보자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 현재 방식에 대한 생각을 묻고 가능하다면 개선하자고 제안했다. 성능 문제가 측정되었다는 주장은 없다. 작성자는 애플리케이션 시작 시 DB로 그래프를 만들고 이후 구간 추가 시 갱신하는 방안을 제시했으며, 구현 완료 여부는 이 대화에서 확인되지 않는다.

- [ ] 노선과 구간 변경이 빈번하지 않다는 전제에서, 경로 조회마다 최단 경로 계산 객체를 새로 만들 필요가 있는지 검토하자. (개선 제안)
  - 조건: 작성자는 구간 추가·삭제 시에만 갱신하는 방식을 제안하며 싱글톤과 Bean 활용 방법을 질문했다. 리뷰 참여자는 그래프의 removeEdge 메서드를 이용해 Bean으로 관리할 수 있을 것 같다고 답했다. 작성자는 PathService 생성 시 초기화하고 변경 시에만 refresh하도록 수정했다고 보고했으나, 구현의 적절성은 이 대화에서 확인되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Graph graph = graphCache.get(networkVersion, () -> buildGraph(stations, segments));
```

**적용 설명:** 읽기 많은 그래프의 재사용 예다. 노선 변경 시 버전·무효화·동시 재생성을 처리해야 한다.
