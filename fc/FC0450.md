# FC0450 · 업무 단위의 트랜잭션 경계

## 검토 질문

- [ ] 함께 성공·실패해야 하는 변경을 같은 경계에 묶고 실제 적용·전파·롤백 조건을 확인했는가?

**직접 작성한 예시**

```java
transaction.run(() -> {
    orders.save(order);
    outbox.append(orderPlaced(order));
});
```

**적용 설명:** 가상 트랜잭션 실행기로 원자성 경계를 보인다. 선언형 애너테이션을 쓴다면 실제 적용 경로·전파·롤백 조건도 확인한다.

## 구체적인 검토 사례

**혼합·경계:** @Transactional 적용 사례와 일반적인 트랜잭션 경계 논의가 섞임.

- [ ] @Transactional의 동작과 다른 서비스 메서드에도 트랜잭션을 적용할 필요가 있는지 검토해 달라는 질문이다. (설계 질문)
  - 조건: 작성자는 작업 단위의 원자성과 커밋·롤백으로 이해했다고 답했고, AOP는 아직 깊이 학습하지 않았다고 밝혔다. 기존에는 변경 작업 횟수로 적용 여부를 정했으나 이후 전반적으로 적용하고 조회에는 readOnly 설정을 사용했다고 보고했다. 동시성 문제 완화와 LazyInitializationException 해결도 작성자가 제시한 이유이며, 그 효과나 실제 변경 결과가 별도로 검증된 것은 아니다.

- [ ] 읽기 전용 트랜잭션 설정을 메서드뿐 아니라 클래스 수준에도 적용할 수 있다고 제안했다. (개선 제안)
  - 조건: 작성자는 Repository와 Service의 클래스 수준에 읽기 전용 설정을 두고 필요한 메서드에 별도의 트랜잭션 설정을 명시했다고 보고했다. 적용 범위를 두 계층 모두로 확대한 것은 작성자의 보고이며, 참여자가 직접 요구한 범위나 실제 동작 검증으로 간주하지 않는다.

- [ ] 서비스 클래스 전체에 읽기 전용 트랜잭션을 설정하고 생성·수정·삭제 메서드에 별도 트랜잭션을 지정한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 현재 메서드 구성에서는 클래스에 일반 트랜잭션을 두고 조회 메서드만 읽기 전용으로 지정할 수도 있지만, 향후 메서드 추가 시 DB 변경 메서드만 명시하는 방식이 더 안전하다고 판단했다고 설명했다. 해당 방식의 결함을 지적하거나 답변의 타당성을 확정한 후속 발언은 없다.
