# FC0185 · 데이터 접근 패턴의 일관성

## 검토 질문

- [ ] 기능마다 DAO·Repository를 다르게 쓰는 이유가 책임·도메인 경계로 설명되는가?

**직접 작성한 예시**

```java
interface Products { Product require(ProductId id); }
final class JdbcProducts implements Products { /* 매핑과 조회 */ }
```

**적용 설명:** 같은 역할인데 어떤 곳은 DAO, 어떤 곳은 Repository인 이유를 일관된 기준으로 설명한다. 이름 통일만이 목적은 아니다.

## 구체적인 검토 사례

- [ ] 일부 도메인에는 Repository를 정의하면서 다른 부분에서는 DAO를 직접 사용하는 설계 이유를 설명해 달라고 요청했다. (설계 질문)
  - 조건: 같은 질문이 두 리뷰 본문에 중복되어 하나로 기록했다. Repository 사용을 모든 도메인에 강제한 지적은 아니다. 작성자는 별도 코멘트에 답했다고 했지만 그 설명은 이 단위에 없으며, 이후 승인만으로 설계 변경이나 질문 해결을 확정하지 않는다.

- [ ] 서비스가 반드시 하나의 DAO만 가져야 한다는 전제를 재검토하고 DAO와 Repository를 구별할 필요가 있다는 의견이다. (토론)
  - 조건: 리뷰 참여자는 인용된 작성자의 단일 DAO 원칙에 동의하지 않으며 DAO와 Repository는 다르다고 말했다. 작성자는 이후 하나의 서비스가 여러 DAO를 참조하도록 바꿨다고 보고했다. 두 개념의 구체적인 차이나 변경의 타당성은 이 대화에서 검증되지 않았다.

- [ ] Repository와 DAO의 구분 기준 및 Service가 둘 모두에 의존하는 이유를 묻고, Repository만 의존하는 구조를 제안했다. (토론)
  - 조건: 작성자는 시간 부족으로 모든 DAO를 Repository 안으로 넣지 못했다고 설명하고, Service가 Repository만 의존하도록 리팩터링하겠다고 답했다. 실제 변경 완료는 이 대화에서 확인되지 않는다.
