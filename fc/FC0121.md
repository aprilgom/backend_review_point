# FC0121 · 간단하게 표현할 수 있는 쿼리는 직접 작성하는 대신 Spring Data JPA의 기능을 더 활용해 볼 것을 제안했다.

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0117](FC0117.md) · [다음 FC: FC0119 →](FC0119.md)

**혼합·경계:** Spring Data 기능 외에 JPQL·네이티브 쿼리 선택이 포함됨.

- [ ] 간단하게 표현할 수 있는 쿼리는 직접 작성하는 대신 Spring Data JPA의 기능을 더 활용해 볼 것을 제안했다. (개선 제안)
  - 조건: 리뷰어는 어렵지 않다면 적용해 보라는 조건부 제안으로, 해당 쿼리뿐 아니라 아래의 다른 쿼리들도 대상으로 언급했다. 작성자는 지원 키워드를 학습해 적용했지만, 메서드 이름이 지나치게 길어지는 경우와 연관관계의 주인이 아닌 테이블에서 생성해야 한다고 설명한 쿼리는 JPQL로 남겼다고 보고했다. 이 예외 사유의 기술적 타당성이나 최종 구현은 확인되지 않는다.

- [ ] 네이티브 쿼리를 선택한 이유와 대안, JpaRepository에서 사용할 때의 단점을 검토하고 가능하면 JPQL로도 구현해 보자는 관심사다. (토론)
  - 조건: 작성자는 JPQL을 충분히 학습하지 못해 이전 SQL을 재사용했다고 설명하고, DB 종속성 및 엔티티 변경 대응 등의 장단점과 QueryDSL 대안을 논의했다. 리뷰 참여자는 메서드만으로 제공받기 어려운 쿼리라는 점을 인정하면서 JpaRepository에서 네이티브 쿼리를 쓸 때의 추가 문제를 질문했고, QueryDSL보다 적용이 어렵지 않을 것이라는 이유로 가능한 경우 JPQL 구현을 권했다. 작성자는 이후 JPQL과 Pageable로 변경했다고 보고하면서 단순 조회에는 JPQL이, 복잡한 쿼리에는 네이티브 쿼리가 나을 수 있다는 의견을 밝혔다. 작성자가 설명한 영속성 컨텍스트 관련 주장이나 마지막 칭찬을 기술적 타당성의 검증으로 취급하지 않는다.

- [ ] 자동 생성 메서드나 JPQL로 표현하기 어려운 복잡한 조회에는 @Query를 통한 SQL 활용과 native query를 고려할 수 있다는 의견을 제시했다. (의견)
  - 조건: 작성자가 비교한 두 구현 방식에 대한 답변이다. 복잡한 조건이 많이 붙는 상황을 전제로 한 의견이며, 모든 조회에 native query를 사용하라는 요구는 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
interface BookRepository extends org.springframework.data.repository.Repository<Book, Long> {
    List<Book> findByAuthorId(Long authorId);
}
```

**적용 설명:** 혼합 FC의 첫 항목은 Spring Data 파생 쿼리다. 이 FC는 제외 대상 20개에 속하지 않아 포함했으며 쿼리 복잡도·명시성에 따라 직접 쿼리와 비교한다.
