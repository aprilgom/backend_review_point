# FC0066 · 예약 가능 여부를 포함하는 시간 조회 API의 요청과 응답을 현재 형태로 설계한 이유를 질문했다.

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0055](FC0055.md) · [다음 FC: FC0064 →](FC0064.md)

- [ ] 예약 가능 여부를 포함하는 시간 조회 API의 요청과 응답을 현재 형태로 설계한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 예약 가능 여부를 담기 위해 `/times/available`을 사용하고 필터 조건인 date와 themeId를 쿼리 파라미터로 받으며, 응답에는 `alreadyBooked`를 추가했다고 설명했다. GET 본문, 경로 변수의 용도, 쿼리 파라미터의 null 허용 가능성에 관한 설명은 작성자의 설계 근거이며 리뷰 참여자가 확인한 기술적 결론이나 변경 요구는 아니다.

- [ ] 예약 식별에 name을 경로 변수로 사용하는 이유를 묻고, reservationId를 경로 변수로 받거나 name은 요청 파라미터 또는 본문으로 전달하는 편이 어울린다고 제안했다. (개선 제안)
  - 조건: 작성자는 변경 대상 슬롯에 요청자의 예약이나 대기가 이미 있는지 검증하기 위해 name이 필요했다고 설명했다. 이후 검증 조건과 식별자를 분리하는 편이 낫다고 판단해 reservationId를 경로 변수로 사용하고, requesterName은 로그인 Member 또는 기존 예약에서 얻도록 수정했다고 보고했다. 이름을 외부에서 받지 않는 방식은 작성자가 선택한 대응이며, 리뷰 참여자가 직접 요구한 사항으로 해석하지 않는다.

- [ ] 예약 저장 메서드가 ReservationRequestDto 대신 date, timeId, themeId를 받아 더 유연하게 사용되도록 하자는 제안이다. (개선 제안)
  - 조건: 리뷰 참여자는 AdminReservationRequestDto를 ReservationRequestDto로 변환하는 방식도 어색하다고 보며 인자 변경의 맥락으로 함께 언급했다. 작성자의 답변이나 변경 결과는 없다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
record SlotReply(LocalTime startsAt, boolean available) {}
List<SlotReply> listSlots(LocalDate day, int partySize) {
    return availability.forDate(day, partySize);
}
```

**적용 설명:** 조회에 영향을 주는 조건을 입력으로 드러낸다. 조회 시 가능했던 슬롯도 확정 시 다시 경쟁 조건을 검증해야 한다.
