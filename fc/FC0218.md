# FC0218 · 값이 없는 키 입력의 파싱

[소속 분야: 도메인 검증](../12-validation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0222](FC0222.md) · [다음 FC: FC0219 →](FC0219.md)

## 검토 질문

- [ ] 키만 있거나 빈 값·구분 문자가 포함된 입력을 처리하는 규칙이 명확한가?

**직접 작성한 예시**

```java
String[] pair = part.split("=", 2);
String key = pair[0];
String value = pair.length == 2 ? pair[1] : "";
```

**적용 설명:** 키만 있는 입력을 빈 값으로 취급하는 계약 예시다. 디코딩·중복 키·빈 키 정책은 별도로 정한다.

## 구체적인 검토 사례

- [ ] 쿼리 문자열에 키만 있고 값이 없을 때 파싱이 어떻게 동작하는지 확인을 요청했다. (설계 질문)
  - 조건: 작성자는 값이 없으면 1번 인덱스 접근으로 IndexOutOfBoundsException이 발생한다고 확인했으며, 예외 대신 null을 넣도록 수정했다고 보고했다. 이는 작성자의 설명이며, 제시한 수집 코드의 실제 null 처리 가능 여부나 수정 결과가 검증된 것은 아니다.

- [ ] 문자열로 관리되는 orderStatus에 MAKING처럼 유효하지 않은 값이 들어오면 예외 상황으로 처리해야 하지 않는지 질문했다. (설계 질문)
  - 조건: 테스트 코드에 대한 리뷰에서 제기된 질문이다. 작성자는 존재하지 않는 주문 상태 문자열을 사용하는 테스트를 추가했다고 보고했으며, 실제 예외 처리 동작이나 테스트 결과는 대화에서 확인되지 않는다.

- [ ] userId=처럼 값이 비어 있는 요청을 파싱할 때 문제가 생길 가능성을 묻고 예외적인 입력도 고려하도록 제안했다. (설계 질문)
  - 조건: 작성자는 빈 값을 빈 문자열로 저장하도록 변경했다고 보고하고 name=&value=를 검증하는 테스트 코드를 제시했다. 이는 작성자의 변경 보고이며, 리뷰어가 실제 오류를 재현했거나 변경 후 동작을 확인했다는 근거는 없다.
