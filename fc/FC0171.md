# FC0171 · 직접 작성한 테스트 대역의 비용

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0176](FC0176.md) · [다음 FC: FC0180 →](FC0180.md)

## 검토 질문

- [ ] 직접 만든 fake가 검증하려는 계약을 충분히 표현하며 유지보수·실제 구현과의 차이를 관리하는가?

**직접 작성한 예시**

```java
final class FakeSender implements Sender {
    final List<String> sent = new ArrayList<>();
    public void send(String text) { sent.add(text); }
}
```

**적용 설명:** 단순 관측이 필요한 테스트 대역이다. 실제 전송의 오류·재시도 의미를 이 fake가 검증해 주지는 않는다.

## 구체적인 검토 사례

- [ ] 서비스 테스트에서 mocking 라이브러리나 실제 객체 대신 직접 구현한 Fake 객체를 선택한 이유와 유지관리 부담을 논의한다. (토론)
  - 조건: 작성자는 Mock의 given 설정이 협력 객체 동작을 드러내어 변경에 취약해지고 테스트 이해 비용도 높인다고 설명했다. 리뷰어는 Mock의 리팩터링 내성에 관한 우려에 동의하면서도 Fake를 별도로 관리하는 부담을 지적하고, 실제 객체를 사용하는 방식 대신 Fake를 택한 이유를 다시 물었다. 실제 객체와의 비교에 대한 작성자의 후속 답변은 없다.

- [ ] Mockito와 fake 객체를 사용할 때의 차이를 비교하고 상황에 맞는 테스트 더블을 선택하도록 논의했다. (토론)
  - 조건: 작성자는 fake DAO 메서드를 계속 구현하는 비용에 비해 mock은 준비 시간이 적고 변경과 협업에 유리하게 느꼈다고 답했다. 리뷰 참여자는 fake의 인터페이스·구현체 구조 마련 부담을 언급하면서도 fake의 장점도 있으므로 어느 한 방식만을 요구하지 않았다. 인터페이스 구조가 반드시 필요하다는 설명의 기술적 타당성을 별도로 확인한 것은 아니다.

- [ ] 테스트 대역으로 fake를 선택한 장점과 예상되는 단점을 어떻게 판단했는지 설명을 요청한다. (설계 질문)
  - 조건: 선택의 장단점과 판단 근거를 묻는 질문이며, fake 사용 자체를 결함으로 지적하거나 다른 대역으로 교체하라고 요구한 것은 아니다.
