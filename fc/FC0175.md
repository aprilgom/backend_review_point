# FC0175 · 도메인 중심 저장 계약

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0181](FC0181.md) · [다음 FC: FC0174 →](FC0174.md)

## 검토 질문

- [ ] 저장 구현이 도메인 계약을 따르도록 의존 방향을 정하고 도메인이 데이터 접근 기술을 모르도록 했는가?

**직접 작성한 예시**

```java
// domain: 계약
interface Orders { void save(Order order); }
// persistence: 도메인 계약 구현
final class SqlOrders implements Orders { /* JDBC 구현 */ }
```

**적용 설명:** 도메인이 저장 구현을 import하지 않도록 의존 방향을 역전한다. 구현 본문은 생략했다.

## 구체적인 검토 사례

- [ ] 도메인이 데이터 계층을 모르게 하는 레포지토리 패턴을 적용하려면 도메인 측 인터페이스와 데이터 계층 구현체로 의존 방향을 분리해야 한다고 설명했다. (토론)
  - 조건: 리뷰 참여자는 현재 OrdersRepository가 DAO를 직접 참조하며 엔티티 변환과 데이터 조합을 하는 어댑터 역할이라고 구분했다. 작성자는 레포지토리를 엔티티를 조합해 도메인을 만드는 역할로 이해했다고 답했다. 패턴 적용을 전제로 한 설명이지 즉시 전환하라는 무조건적 요구는 아니다.

- [ ] application 계층이 DataAccessException을 직접 사용하는 것과 infra 계층에서 통일된 예외로 감싸 전달하는 것 사이의 의존성·과설계 절충을 논의했다. (토론)
  - 조건: 작성자는 application·domain을 순수 JVM 코드로 유지하고 외부 라이브러리 예외의 유입을 막자는 기준을 제시했다. 리뷰 참여자는 처음에 질문의 맥락을 놓쳤다고 정정하고 그 기준을 긍정하면서도, DataAccessException은 이미 충분히 추상화되어 있어 추가 래핑이 실무상 과설계일 수 있다는 개인적 견해를 밝혔다. JDBC·JPA의 구체 예외 구현체에 대한 의존에는 반대한다는 구분도 남겼으며, 자신의 근거가 직관적이라고 한정했다.

- [ ] 다른 도메인 객체가 필요할 때 서비스와 저장소 중 무엇에 의존할지는 각 계층의 역할을 기준으로 판단해보자는 논의이다. (토론)
  - 조건: 리뷰 참여자는 두 계층의 역할을 먼저 질문했다. 작성자는 객체 조회에는 저장소를, 비즈니스 처리 결과에는 서비스를 의존하는 기준을 제시하고, 현재 findById의 예외 처리는 기술적 필요이므로 저장소 의존이 적절하다고 설명했다. 리뷰 참여자는 이 사고 과정을 긍정했으나, 이를 모든 경우의 의존 규칙으로 일반화하지는 않았다.
