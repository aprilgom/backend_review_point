# FC0195 · 설명과 반례를 통한 이해 검증

[소속 분야: 문서·개발·학습 과정](../10-workflow.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0192](FC0192.md) · [다음 FC: FC0196 →](FC0196.md)

## 검토 질문

- [ ] 자신의 가정을 다른 사람에게 설명하고 작은 실험·대안 비교로 잘못된 이해를 확인하는가?

**직접 작성한 예시**

```java
// 설명해 볼 질문: 이 호출 후 원본 목록도 달라지는가?
List<String> original = new ArrayList<>(List.of("a"));
List<String> copy = List.copyOf(original);
original.add("b");
assertEquals(List.of("a"), copy);
```

**적용 설명:** 작은 반례를 직접 실행해 서로의 가정을 비교하는 학습 예시다.

## 구체적인 검토 사례

- [ ] 이해가 부족한 지점을 확인하기 위해 동료에게 설명하고 토론하며, 같은 미션의 다른 구현을 함께 비교하는 학습을 권했다. (개선 제안)
  - 조건: 리뷰 참여자 자신의 학습 경험을 바탕으로 한 추천이다. 작성자는 설명과 리뷰 대화에서 놓친 부분을 발견한 경험에 공감하며 활용하겠다고 답했다. 이후 테스트 피드백 요청과 다른 코멘트로 답하겠다는 안내에는 별도의 구체적 테스트 개선점이 제시되지 않았다.

- [ ] 코드는 동작하지만 설계가 적절한지 확신하기 어려운 고민을 동료에게 설명하고 토론하면서 학습 내용을 체화하도록 권했다. (개선 제안)
  - 조건: 상대 참여자는 자신의 학습 경험을 바탕으로 우테코 동료 환경을 활용하라고 권했다. 작성자도 설명 과정에서 논리의 빈틈을 발견한 경험에 동의하고 토론을 계속하겠다고 답했으며, 특정 코드의 타당성을 판정한 대화는 아니다.

- [ ] 우선 동작하는 구현을 찾아가면서 실패한 경우와 성공 이유를 모르는 경우를 기록하고, 여유가 생겼을 때 후속 학습할 것을 제안한다. (개선 제안)
  - 조건: 새로 배울 스프링 내용이 많다는 상황을 고려해 '추후 학습할 키워드'를 분리한 기존 방식을 지지했다. 실패나 원인 미확인 상태를 영구히 방치하라는 뜻은 아니다.
