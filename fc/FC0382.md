# FC0382 · 공통 예외 처리의 책임 분리

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0357](FC0357.md) · [다음 FC: FC0377 →](FC0377.md)

## 검토 질문

- [ ] 컨트롤러마다 반복되는 오류 응답 처리를 적절한 경계로 모아 업무 처리와 분리할 수 있는가?

**직접 작성한 예시**

```java
try { return controller.handle(request); }
catch (AppFailure failure) { return errorMapper.toReply(failure); }
```

**적용 설명:** 예외 응답 매핑을 요청 경계에서 공통 처리한다. ControllerAdvice는 이를 구현하는 한 프레임워크 수단이다.

## 구체적인 검토 사례

**혼합·경계:** ControllerAdvice 외에 컨트롤러의 책임 분리 사례가 포함됨.

- [ ] 컨트롤러가 단일 책임을 지키도록 예외 처리를 분리하고 ControllerAdvice 계열의 활용을 검토하도록 제안한다. (개선 제안)
  - 조건: 리뷰어는 처음에 RestControllerAdvice를 찾아보라고 제안했다. 작성자는 예외 처리를 별도 클래스에 모으고 예외 응답 DTO를 만들었다고 보고하며 ControllerAdvice와 구분해 권한 의도를 질문했다. 리뷰어는 두 어노테이션을 특별히 구분해서 언급한 것은 아니라고 설명했으므로, 별도 응답 DTO가 원래 요구였다고 해석할 수는 없다. 책임 분리 제안 자체를 철회한 것은 아니다.

- [ ] 사용자용 API와 관리자용 API의 관심사가 다르다는 이유로 컨트롤러를 분리하는 방식을 제안했다. (개선 제안)
  - 조건: 작성자는 다음 미션에서 반영하겠다고 답했다. 이 대화에서 컨트롤러 분리의 실제 구현은 확인되지 않는다.

- [ ] ControllerAdvice를 학습하고 예외 처리 로직을 일반 컨트롤러에서 분리하도록 제안한다. (개선 제안)
  - 조건: 기존 ExceptionHandler 적용을 긍정한 뒤 책임 분리를 제안한 것이다. 작성자는 예외 처리 책임을 별도 클래스에 모으면 응집도를 높일 수 있다고 설명하며 수정했다고 보고했으나 실제 변경은 확인되지 않는다.
