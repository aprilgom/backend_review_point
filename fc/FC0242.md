# FC0242 · SQLException을 그대로 던지지 않고 RuntimeException으로 감싸서 던지는 이유를 설명해 달라고 요청했다.

[소속 분야: 예외·실패 계약](../13-errors.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0241](FC0241.md) · [다음 FC: FC0243 →](FC0243.md)

- [ ] SQLException을 그대로 던지지 않고 RuntimeException으로 감싸서 던지는 이유를 설명해 달라고 요청했다. (설계 질문)
  - 조건: 작성자는 체크 예외가 처리를 강제하지만 SQLException의 발생 상황을 예상하여 코드로 처리하기 어렵다고 보아, 예외 처리 강제를 피하려고 언체크 예외로 감쌌다고 설명했다. 이는 작성자의 설명이며 기술적 타당성이 별도로 확인된 것은 아니다.

- [ ] SQLException을 처리하면서 DataAccessException 대신 RuntimeException을 발생시킨 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 실수로 바꾸지 못한 부분이라며 수정했다고 보고했다. 질문을 확정적인 결함 판정으로 바꾸거나 수정 결과를 독립적으로 확인한 것으로 보지 않는다.

- [ ] checked 예외인 SQLException을 잡아 unchecked 예외인 DataAccessException으로 변환해 던지는 이유를 물었다. (설계 질문)
  - 조건: 작성자는 SQLException을 JdbcTemplate 밖으로 전달하는 것을 책임 전가로, 임의 값 반환을 임시방편으로 보았다고 설명했다. 직접 만든 unchecked 예외로 의미를 명확히 하고 자세한 정보를 전달하려는 의도라고 답했으며, 이 설명의 기술적 타당성이 대화에서 검증된 것은 아니다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
catch (SQLException failure) {
    throw new StorageFailure("저장 작업 실패", failure);
}
```

**적용 설명:** 저장 기술 예외를 계약에 맞는 unchecked 예외로 바꾸되 원인은 보존한다. 재시도 가능 여부는 별도 판단한다.
