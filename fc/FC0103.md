# FC0103 · 동시 요청이 애플리케이션의 중복 검사를 함께 통과하면 중복 저장이 가능하므로 데이터베이스에서도 정합성을 보장해야 한다는 우려다.

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0100](FC0100.md) · [다음 FC: FC0098 →](FC0098.md)

- [ ] 동시 요청이 애플리케이션의 중복 검사를 함께 통과하면 중복 저장이 가능하므로 데이터베이스에서도 정합성을 보장해야 한다는 우려다. (위험 지적)
  - 조건: 동시 요청 상황을 가정한 위험 지적이다. 작성자는 역 이름에 UNIQUE 제약조건을 추가해 데이터베이스에서 중복을 검사하도록 변경했다고 보고했으며, 동시성 상황에서의 실제 결과는 확인되지 않았다.

- [ ] 동일한 예약 시간의 중복 저장을 막아야 하며, 저장 전 존재 여부 조회만으로는 동시 요청의 중복 생성을 막기 어렵다는 점을 논의한다. (토론)
  - 조건: 참여자는 처음에 동일 시간으로 여러 번 저장할 수 있는지 질문했다. 작성자는 중복 저장이 가능하다고 답하고 start_at에 유니크 제약조건을 추가했다고 보고하면서, 비즈니스 검증보다 DB 제약조건이 더 좋은 방식인지 물었다. 참여자는 두 요청이 사전 조회를 동시에 통과할 수 있다고 설명하며, 보편적으로 더 좋은 방식이라기보다 현재 구조에서 중복 방지를 해결할 다른 수단이 없다는 취지로 답했다. 이 설명을 모든 구조에서 DB 유니크 제약조건만이 유일한 해법이라는 규칙으로 일반화하지 않는다.

- [ ] 동시 요청이 사전 중복 검사를 함께 통과하면 중복 데이터가 저장될 수 있으므로 데이터베이스에서도 정합성을 보장해야 한다고 지적했다. (위험 지적)
  - 조건: 위험 조건은 여러 요청이 isDuplicated 검사를 통과한 뒤 저장되는 경우다. 작성자는 Line의 title과 Station의 name에 UNIQUE 속성을 부여했다고 보고했으며, 실제 동시 요청 검증 결과는 제시되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
ALTER TABLE subscription
ADD CONSTRAINT unique_subscription UNIQUE (account_id, topic_id);
```

**적용 설명:** 사전 존재 확인만으로 막을 수 없는 동시 중복 삽입을 제약으로 방어한다. 제약 위반을 응답 계약에 맞게 처리한다.
