# FC0008 · 객체 변환을 표현하는 생성 API

## 검토 질문

- [ ] 객체 간 변환을 생성자·빌더·정적 팩토리 중 무엇으로 표현해야 변환 의도와 데이터 보존 규칙이 잘 드러나는가?

**직접 작성한 예시**

```java
static HttpReply from(ReplyData source) {
    return new HttpReply(source.status(), source.headers(), source.body());
}
```

**적용 설명:** ReplyData·HttpReply는 가상 타입이다. 변환 책임을 이름으로 드러내되 헤더·본문 손실 여부를 확인한다.

## 구체적인 검토 사례

- [ ] ResponseEntity에서 HttpResponse를 만드는 빌더 코드를 정적 팩토리 메서드 HttpResponse.from(responseEntity)로 표현하는 대안을 제안했다. (개선 제안)
  - 조건: 작성자의 생각이 궁금해서 묻는 제안이라고 명시했으며, 변경을 필수로 요구하거나 현재 구현을 결함으로 지적한 것은 아니다. 작성자 답변은 제공되지 않았다.

- [ ] 상태 코드가 추가될 때마다 ExceptionHandler를 추가·수정하는 대신, 예외가 httpStatus와 body를 갖도록 추상화하여 하나의 핸들러에서 처리하는 방안을 제안한다. (조건부 제안)
  - 조건: 현재 구조가 의도된 것이 아니거나 매번 핸들러를 관리하는 것이 불편할 경우에 제시한 대안이다. 작성자는 DM 답변대로 진행했다고 했지만, DM의 구체적인 내용과 실제 변경 결과는 제공되지 않았다.

- [ ] HTTP 메서드마다 Request 하위 클래스를 늘리기보다 GET과 POST를 함께 지원하는 HttpRequest 구조를 제안했다. (개선 제안)
  - 조건: 현재 구조에서는 HTTP 메서드가 추가될 때마다 대응하는 Request 클래스도 추가될 것이라는 확장 부담을 근거로 들었다. 기존 요청 추상화 자체는 긍정적으로 평가했다.
