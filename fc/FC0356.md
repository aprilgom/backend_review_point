# FC0356 · 컨트롤러 메서드를 가져오는 단계에서 RequestMapping 어노테이션으로 필터링하지 않고 모든 메서드를 가져온 이유를 질문했다.

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0363](FC0363.md) · [다음 FC: FC0359 →](FC0359.md)

- [ ] 컨트롤러 메서드를 가져오는 단계에서 RequestMapping 어노테이션으로 필터링하지 않고 모든 메서드를 가져온 이유를 질문했다. (설계 질문)
  - 조건: 필터링을 메서드 조회 단계에서 수행할 수 있다는 제안이 포함된 질문이다. 작성자는 스트림으로 필터링하도록 변경했다고 보고했다. 모든 메서드를 조회하는 방식 자체가 실행 결함이라는 지적은 아니다.

- [ ] 로그인 회원 처리와 권한 처리를 ArgumentResolver와 Interceptor로 나눈 기준과 이유를 질문했다. (설계 질문)
  - 조건: 리뷰어는 LoginMemberArgumentResolver의 기능도 Interceptor로 구현할 수 있을 것 같다는 가능성을 제시했다. 작성자는 두 객체를 모두 학습하려고 구현했다고 답하고 인터셉터 구현도 고려하겠다고 했으나, 통합을 결정하거나 변경한 결과는 제시되지 않았다.

- [ ] 기존 ReservationController에 예약 추가·삭제 API가 있는데 페이지용 컨트롤러에도 같은 기능을 별도로 둔 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 JSON API 응답과 타임리프 렌더링·폼 제출 후 리다이렉트의 책임이 다르다고 판단해 분리했다고 설명했다. 다만 현재 프로젝트 규모에서는 기존 API를 호출하는 페이지 구성도 가능했을 것이라고 재고했다. 별도 컨트롤러가 불필요하다는 결론이나 변경 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
List<Method> routes = Arrays.stream(controllerType.getDeclaredMethods())
    .filter(m -> m.isAnnotationPresent(Route.class)).toList();
```

**적용 설명:** 자체 런타임 Route 애너테이션을 표시한 메서드만 등록한다. 일반 public 메서드가 우연히 엔드포인트가 되지 않게 한다.
