# FC0368 · 발급을 돕는 CouponIssuer가 쿠폰 한 건에 종속되는 현재 구조 대신, 미리 생성한 발급기를 활용할 수 있는 협력 관계를 고민하도록 제안했다.

[소속 분야: 책임·계층 경계](../19-responsibility.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0372](FC0372.md) · [다음 FC: FC0376 →](FC0376.md)

- [ ] 발급을 돕는 CouponIssuer가 쿠폰 한 건에 종속되는 현재 구조 대신, 미리 생성한 발급기를 활용할 수 있는 협력 관계를 고민하도록 제안했다. (개선 제안)
  - 조건: 리뷰 참여자는 CouponIssuer라는 이름에서 기대하는 역할과 실제 생성·사용 방식 사이의 책임 문제를 언급했다. 이전 코멘트도 참조하지만 그 구체적인 내용은 이 단위에 없으므로 보충하지 않는다. 특정 구현 방식이 필수라고 단정하지 않으며 작성자의 후속 답변은 없다.

- [ ] InputStream을 전달하며 사용하는 구조에서는 읽기 호출 순서가 보장되지 않을 위험이 있으므로, 한곳에서 의도한 순서대로 처리하도록 구성하자는 의견을 제시했다. (개선 제안)
  - 조건: 리뷰어의 우려는 스트림을 사용하는 메서드의 호출 순서가 확실히 보장되지 않는 경우를 전제로 한다. 작성자는 실제로 전달한 것은 BufferedReader이며 같은 클래스 안에서도 휴먼 에러가 생길 수 있으므로 호출 순서만으로 전달 방식을 배제할 이유는 없다고 반론했다. 현재 방식을 유지하고 리팩터링 단계에서 재검토하겠다고 밝혔다.

- [ ] Game이 보드의 값을 꺼내 차례를 검증하기보다 chessBoard.move에 turn을 전달하여 ChessBoard가 검증하도록 제안한다. (개선 제안)
  - 조건: validateCorrectTurn의 비즈니스 로직 수행 위치에 대한 제안이며, 실제 책임 이동 여부는 확인되지 않는다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
CouponIssuer issuer = new CouponIssuer(policy, clock);
Coupon first = issuer.issue(customerA);
Coupon second = issuer.issue(customerB);
```

**적용 설명:** 발급 정책·시계를 갖는 협력 객체는 여러 쿠폰을 발급할 수 있다. 요청별 가변 상태를 공유하지 않도록 한다.
