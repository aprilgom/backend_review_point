# FC0069 · 생성자 공개 범위 확대의 근거

[소속 분야: API·공개 인터페이스 계약](../03-api-contract.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0060](FC0060.md) · [다음 FC: FC0070 →](FC0070.md)

## 검토 질문

- [ ] 생성자를 더 넓게 공개해야 하는 실제 사용처가 있으며 불완전한 객체 생성 경로가 늘어나지 않는가?

**직접 작성한 예시**

```java
class RecordEntity {
    protected RecordEntity() {}
    public static RecordEntity named(String name) { return new RecordEntity(name); }
}
```

**적용 설명:** 외부 생성 경로를 팩토리로 통제하는 예시다. 이름을 받는 생성자·검증은 생략했으며 public 기본 생성자가 필요한 실제 호출자를 먼저 확인한다.

## 구체적인 검토 사례

- [ ] 별도 사용처가 없는 기본 생성자의 접근 범위를 protected에서 public으로 넓힌 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 다른 패키지의 테스트에서 사용하던 생성자였지만 테스트 변경 후 필요 없어졌으며, 다시 protected로 변경했다고 답했다. 변경 여부는 작성자의 보고로 남긴다.

- [ ] MyReservationResponse 생성자의 접근 제한자를 private에서 public으로 변경한 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 정적 팩토리를 생성자 방식으로 바꾸려다 되돌리는 과정에서 접근 제한자 복원을 누락했다고 설명하고 private으로 돌렸다고 보고했다. 리뷰어는 public 생성자가 항상 부적절하다는 일반 규칙을 제시하지 않았다.

- [ ] PathRequest의 기본 생성자가 public이어야 하는 특별한 이유가 있는지 질문했다. (설계 질문)
  - 조건: 작성자는 @ModelAttribute에서 모든 필드를 초기화하는 생성자 하나만 사용할 수 있도록 수정했다고 보고했다. 질문 자체가 특정 접근 제어자나 생성자 제거를 명시적으로 요구한 것은 아니며, 변경 후 바인딩 동작은 확인되지 않았다.
