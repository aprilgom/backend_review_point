# FC0174 · 서비스 의존 그래프의 순환 방지

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0175](FC0175.md) · [다음 FC: FC0186 →](FC0186.md)

## 검토 질문

- [ ] 서비스 간 협력이 순환하지 않으며 상위 조율자나 분리된 계약으로 흐름을 설명할 수 있는가?

**직접 작성한 예시**

```java
Checkout checkout = new Checkout(inventory, payments);
// Inventory와 Payments는 Checkout을 다시 주입받지 않는다.
```

**적용 설명:** 상위 조율자가 하위 기능을 호출하는 비순환 구조다. 순환을 이벤트로 바꿀 때도 일관성·실패 의미를 정해야 한다.

## 구체적인 검토 사례

- [ ] 서비스가 다른 서비스를 의존하는 구조는 허용할 수 있지만 순환 참조가 생기지 않도록 관리해야 한다는 의견이다. (조건부 제안)
  - 조건: 작성자는 ReservationTime 로직의 중복과 캡슐화 훼손을 피하고 변경을 해당 서비스에 모으기 위해 다른 서비스를 의존했다고 설명했다. 리뷰어는 이 방향과 현재 구조가 괜찮다고 보았으며, 현재 순환 참조가 존재한다고 지적하지는 않았다.

- [ ] 서비스가 다른 서비스를 사용할 때 서비스 수가 늘어나도 순환 참조가 발생하지 않도록 의존성을 관리할 수 있어야 한다고 제안했다. (조건부 제안)
  - 조건: 현재 순환 참조가 발생했다고 지적한 것은 아니다. 오류 경로 추적과 의존성 관리를 자신할 수 있다면 서비스 간 호출을 사용해도 된다고 명시해, 이를 일률적으로 금지하지 않았다.

- [ ] 순환 참조가 없다면 다른 도메인의 저장소를 직접 참조하기보다 해당 서비스를 호출하는 협력이 적절하다는 의견을 제시했다. (조건부 제안)
  - 조건: 작성자는 ID에 해당하는 객체 조회와 검증이 각 도메인 서비스의 책임이라고 판단해 서비스 간 협력을 선택했다고 설명했다. 리뷰 참여자의 동의는 순환 참조 문제가 없다는 조건부이며, 현재 구조에서 순환 참조 유무를 확인한 발언은 아니다.
