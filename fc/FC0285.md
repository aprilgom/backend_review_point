## 검토 질문

- [ ] 인덱스 외에도 불필요한 컬럼·큰 본문을 읽는 비용을 확인하고 필요한 결과만 조회하는가?

**직접 작성한 예시**

```sql
SELECT id, title FROM article
WHERE author_id = :author ORDER BY id LIMIT 20;
```

**적용 설명:** 큰 본문 컬럼을 제외하는 단순 대안이다. 인라인 뷰가 자동으로 빠르다고 가정하지 말고 실행 계획과 읽은 데이터량을 비교한다.

## 구체적인 검토 사례

- [ ] 인덱스 적용 후에도 느리다면 조회 컬럼 수의 영향을 고려해 필요한 컬럼만 가져오는 인라인 뷰로 쿼리를 바꾸는 접근을 제안했다. (개선 제안)
  - 조건: 참여자는 자신의 환경에서 해당 변경 후 눈에 띄는 개선을 경험했다고 했지만, 컬럼 수가 원인인지는 추측으로 제시했다. 작성자는 비슷하게 진행해도 95ms보다 빨라지지 않았다고 답했다.

- [ ] DDL에 인덱스가 없다고 지적하며 조회 성능 개선을 위해 인덱스를 학습하고 적용해 보도록 권했다. (조건부 제안)
  - 조건: 여유가 있다면 진행하라는 조건이 붙은 p3 제안이다. 작성자는 reservation과 holiday 테이블에 인덱스를 추가했다고 보고했지만, 실제 성능 측정 결과나 조회 속도 개선 여부는 제시되지 않았다.

- [ ] covid(programmer_id, hospital_id) 복합 인덱스를 선택한 이유를 묻고, 조인에 사용하는 programmer_id에만 인덱스를 두는 방안을 제안했다. (토론)
  - 조건: 리뷰 참여자는 복합 인덱스의 후행 컬럼이 선행 컬럼에 의존해 정렬되므로 hospital_id 단독으로는 활용되지 않을 것으로 예상했고, 작성자의 실행 계획에서 covid가 전체 테이블 스캔을 한다고 설명했다. 이는 참여자의 해석이며 기술적 타당성을 별도로 확인한 것은 아니다. 작성자는 수정했다고 답했으나 변경 내용과 성능 결과는 이 대화에 제시되지 않았다.
