# FC0117 · 예약과 대기를 상태로만 구분한다면, 예약 존재 여부 조회에서도 RESERVED 상태만 검증해야 하지 않는지 질문했다.

[소속 분야: 쿼리·데이터 조작](../07-data-query.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0116](FC0116.md) · [다음 FC: FC0121 →](FC0121.md)

- [ ] 예약과 대기를 상태로만 구분한다면, 예약 존재 여부 조회에서도 RESERVED 상태만 검증해야 하지 않는지 질문했다. (설계 질문)
  - 조건: 리뷰 참여자는 상태로 예약과 대기를 구분할 경우 관련 쿼리마다 status 조건을 계속 챙겨야 하는 부담도 지적했다. 작성자는 WAITING까지 조회될 위험에 동의하며 메서드명을 existsReservedByDateAndTimeAndThemeAndStore로 변경하고 RESERVED 조건을 추가했다고 보고했다. 실제 변경 결과는 확인되지 않았다.

- [ ] 시간 삭제 가능 여부는 예약 한 건의 존재만 확인하면 되므로 전체 예약을 조회하지 않도록 쿼리 수준에서 제한할 것을 제안했다. (개선 제안)
  - 조건: findAllByTimeId 결과의 비어 있음으로 삭제 가능 여부를 판단하는 코드에 대한 제안이다. 작성자는 LIMIT와 SELECT 1을 사용하는 existsByTimeId를 구현해 수정했다고 보고했다.

- [ ] 예약 ID를 먼저 조회한 뒤 같은 예약의 내용을 다시 조회하기보다, 필요한 예약 정보를 한 번에 가져오자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 조회 분리의 이점이 명확하지 않고, 두 단계 모두 RESERVATION_NOT_FOUND를 사용하면서 메시지만 달라지는 점을 근거로 들었다. 작성자는 중복 예외 처리와 두 번의 쿼리를 인지하고 수정했다고 보고했지만, 변경된 코드나 실행 결과는 제시되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```sql
SELECT EXISTS (
  SELECT 1 FROM booking WHERE slot_id = :slot AND state = 'CONFIRMED'
);
```

**적용 설명:** 대기와 확정을 같은 테이블에 저장한다면 존재 확인에도 필요한 상태 조건을 포함한다.
