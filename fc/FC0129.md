# FC0129 · 상품의 활성 상태를 장바구니에서 반영하려면 상품 객체 자체가 아니라 ID만 저장하고 필요할 때 상품을 조회하도록 바꾸자고 제안했다.

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0130](FC0130.md) · [다음 FC: FC0131 →](FC0131.md)

- [ ] 상품의 활성 상태를 장바구니에서 반영하려면 상품 객체 자체가 아니라 ID만 저장하고 필요할 때 상품을 조회하도록 바꾸자고 제안했다. (개선 제안)
  - 조건: 작성자는 중복 상품 수량 처리 때문에 객체 JSON 저장을 선택했다고 설명했다. 리뷰 참여자는 자신이 제안한 useFlag 기반 처리를 위해서는 ID 저장과 필요 시 조회가 적합하다고 보았다.

- [ ] 변경 감지로 save 호출을 생략할 수 있어 보이는 상황에서 명시적인 저장 호출을 유지하는 이유와 선호를 물었다. (토론)
  - 조건: 작성자는 총 4단계의 리팩터링 중 구조 변경을 놓칠 가능성을 고려해 기존 DB 접근 메서드를 최대한 유지했다고 설명했고, 패키지 구조와 객체 참조가 안정되면 삭제할 생각이라고 답했다. 리뷰 참여자는 이 설명에 긍정적으로 응답했다. save 제거를 강제한 지적이나 명백한 철회는 아니며, 실제 호출 제거 여부도 확인되지 않는다.

- [ ] JPA를 사용하는 상태 변경 로직에서 응답을 만들기 위해 엔티티를 다시 save할 필요가 있는지 재검토하자고 제안했다. (개선 제안)
  - 조건: changeEmpty에서 조회한 객체를 변경한 뒤 다시 저장해 응답으로 변환하는 코드에 대한 제안이다. 작성자는 성공 테스트에서 ID를 제대로 검증하려면 save한 객체를 from에 넘겨야 했다고 설명하고 해당 테스트를 삭제했다고 보고했다. 테스트 삭제는 작성자의 보고이며, save 제거 여부나 테스트 구성의 타당성은 이 대화에서 확인되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
Product product = products.find(line.productId()).orElseThrow();
if (!product.isActive()) throw new InactiveProduct();
```

**적용 설명:** 장바구니 스냅샷 대신 현재 상태를 확인한다. 가격 스냅샷이 필요한 시점과 조회 비용도 구분한다.
