# FC0136 · 집합 사이의 결합도 조절

[소속 분야: 데이터 관계·영속성](../08-persistence.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0135](FC0135.md) · [다음 FC: FC0138 →](FC0138.md)

## 검토 질문

- [ ] 서로 다른 집합을 전체 객체로 연결해야 하는지 ID 참조만으로 충분한지 검토했는가?

**직접 작성한 예시**

```java
record Booking(CustomerId customerId, SlotId slotId) {}
```

**적용 설명:** 예약에 회원 전체가 필요하지 않을 때 ID만 표현한다. 조회·권한 검증은 호출 흐름에서 명시적으로 수행한다.

## 구체적인 검토 사례

- [ ] Reservation의 연관관계를 항상 객체 참조로 표현해야 하는지, Member 객체 대신 회원 ID만 보유하는 약한 연관관계로 설계할 수도 있는지 고민해 보도록 제안했다. (토론)
  - 조건: 작성자는 처음에 fetchType에 관한 지적으로 해석해 지연 로딩으로 변경했다고 답했지만, 리뷰 참여자는 로딩 방식이 아니라 객체 연관관계 자체의 필요성을 묻는 것이라고 정정했다. 처음부터 구현 개선을 요구하지 않았고 현재 단계에서 읽고 넘어가도 된다고 했으며, 관심사를 철회한 것은 아니다.

- [ ] ReservationTime을 참조 ID로 다루는 방식과 객체로 다루는 방식의 차이가 응답 생성용 추가 조회를 어색하게 느끼게 할 수 있음을 논의한다. (토론)
  - 조건: 작성자는 예약 생성 자체가 아니라 응답의 startAt을 채우기 위한 조회가 서비스에 있어도 되는지 고민하며, 컨트롤러에서 여러 서비스를 조합하는 대안도 제시했다. 참여자는 DB 테이블의 참조를 직접 다루는 전략과 객체 및 API 리소스를 다루는 전략의 차이로 설명했고, 서비스가 ResponseDto를 반환해서 발생한 문제는 아니며 현재 구성이 문제라고 보지는 않는다고 밝혔다.

- [ ] Reservation 조회 시 연관된 Payment 목록을 함께 가져오는 방안을 검토하고, 객체 간 관계를 끊어 둔 현재 구조가 객체지향적이라는 판단도 재고해 보자. (토론)
  - 조건: 리뷰 참여자는 Reservation과 List<Payment>를 함께 조회하는 대안을 제시했다. 작성자는 예약 이력은 reservationRepository에, 결제 상태는 paymentRepository에 물어 조합하는 것이 각 저장소의 책임에 맞으며 결제에서 예약을 탐색하는 방식은 책임이 과해질 수 있다고 반론했다. 작성자는 조회를 한 쿼리로 바꿨다고 했지만 최종 연관관계 구조는 이 대화만으로 확인되지 않는다.
