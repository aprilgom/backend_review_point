# FC0099 · 공유 상태의 원자적 갱신

[소속 분야: 비동기·동시성](../05-concurrency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0106](FC0106.md) · [다음 FC: FC0108 →](FC0108.md)

## 검토 질문

- [ ] 읽기-수정-쓰기를 포함한 공유 상태 접근이 하나의 동기화 규약을 따르는가?

**직접 작성한 예시**

```java
synchronized void add(long delta) {
    total = Math.addExact(total, delta);
}
```

**적용 설명:** 같은 모니터를 사용하는 호출 사이에서 읽기-수정-쓰기를 직렬화한다. total 읽기와 다른 쓰기도 같은 동기화 규약을 따라야 한다.

## 구체적인 검토 사례

- [ ] calculate 메서드에 synchronized를 붙이면 테스트가 통과하는 이유를 질문했다. (설계 질문)
  - 조건: 작성자는 한 스레드가 메서드를 수행할 때 다른 스레드의 동시 호출을 막아 스레드 간섭이 발생하지 않기 때문이라고 설명했다. 동기화 원리에 대한 학습 질문이며 테스트나 구현의 결함을 지적한 것은 아니다.

- [ ] calculate 메서드에 synchronized를 붙이도록 한 이유를 설명해 달라고 질문했다. (설계 질문)
  - 조건: 작성자는 1000개 스레드가 sum을 갱신할 때 증가분이 유실될 수 있으며, synchronized로 한 번에 하나의 스레드만 접근하도록 한다고 설명했다. 이 설명에 대한 후속 검증이나 정정은 없다.

- [ ] max-connections를 2로 설정했을 때 성공 요청 count가 2가 되는 이유를 대기열과 타임아웃 시점으로 분석해보자고 질문했다. (토론)
  - 조건: 리뷰 참여자는 처리 지연, 요청 간격, 연결 및 요청 타임아웃을 바탕으로 세 번째 요청이 시간 초과된다는 분석을 제시했다. 작성자는 세 번째 요청의 소요 시간이 0.9초라면 성공하여 count가 3이어야 하지 않느냐고 반문했다. 참여자는 요청이 들어온 시점부터 계산한다는 데 동의하면서 스레드 전환 등의 지연으로 1초를 넘는 것으로 추측한다고 설명했고, 더 알아내지는 못했다고 밝혔다. 결과의 원인은 확정되지 않았다.
