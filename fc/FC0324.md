# FC0324 · 테스트 이름과 실제 범위

## 검토 질문

- [ ] 컨트롤러·서비스·DB 등 실제 포함 범위를 테스트 클래스와 패키지 이름에서 오해하지 않게 하는가?

**직접 작성한 예시**

```java
class TaskApiIntegrationTest {
    // HTTP → 서비스 → 실제 테스트 DB까지 검증
}
```

**적용 설명:** 실제 범위가 통합 테스트라면 클래스·패키지 이름에서 범위를 오해하지 않게 한다.

## 구체적인 검토 사례

- [ ] 컨트롤러만 검증하는 테스트로 오해하지 않도록 테스트 클래스와 패키지 이름이 실제 통합 테스트 범위를 드러내는지 검토하자고 제안했다. (토론)
  - 조건: 처음에는 AdminIntegrationTest처럼 클래스 이름을 바꾸자고 제안하고 integration 패키지를 controller로 변경한 이유를 물었다. 작성자는 서비스 테스트도 DB까지 포함한 통합 테스트여서 기존 구분이 어색했다고 설명하고, 슬라이스 테스트로 오해하지 않도록 integration/controller와 integration/service로 나눴다고 보고했다. 질문자는 통합 테스트의 범위가 여러 가지라는 설명을 받아들이고 해당 패키지 구분을 수용했으며, 관리와 실행이 편리하다면 다른 구조도 괜찮다는 견해를 밝혔다.

- [ ] TossPaymentClientTest 필드의 접근 제어자를 정리하도록 제안한다. (개선 제안)
  - 조건: 구체적으로 어떤 접근 수준을 적용할지는 명시하지 않았다.

- [ ] MissionStepTest의 필드 선언 사이 줄바꿈을 일관되게 적용하자. (개선 제안)
  - 조건: 작성자는 줄바꿈을 일관되게 수정했다고 보고했다.
