# FC0007 · 테스트 추상화의 비용과 가독성

## 검토 질문

- [ ] 테스트 준비를 도우미로 감싸는 이점이 호출을 따라가야 하는 탐색 비용보다 큰가?

**직접 작성한 예시**

```java
// 준비 의도가 짧다면 굳이 여러 fixture를 추적할 필요가 없다.
Account account = new Account("reader", ACTIVE);
assertTrue(account.canRead());
```

**적용 설명:** Fixture가 항상 더 낫다는 규칙은 아니다. 반복량과 준비 코드의 탐색 비용을 함께 비교한다.

## 구체적인 검토 사례

- [ ] 테스트 준비 코드를 Fixture로 감싸는 것이 추가 탐색 깊이에 비해 실제로 가독성과 단순성을 높이는지, 현재 필요한 추상화인지 재검토하자는 의견이다. (토론)
  - 조건: 작성자는 관련 없는 세부 사항을 숨기고 메서드명으로 의도를 전달하기 위한 래핑이라고 설명했다. 리뷰 참여자는 Reservation 반환값을 사용하는 곳도 없고 직접 repository.add를 호출하는 것보다 단순한지 불분명하다고 재질문했다. 작성자는 이후 현재 Fixture 메서드가 불필요하다고 판단하고 수정하겠다고 답했다.

- [ ] ObjectMapper를 감싼 JsonSerializer 추상화가 필요한지, 복잡성과 다른 개발자의 혼동을 줄이기 위해 ObjectMapper를 직접 사용하는 편이 나을지 검토하자. (의견)
  - 조건: 리뷰어는 장기적으로 레거시 코드를 줄이는 데 직접 사용이 도움이 된다는 개인 의견임을 명시했다. 래핑 자체를 보편적으로 금지하거나 현재 구현의 결함을 확정한 발언은 아니다.

- [ ] 결과 크기를 검사하는 if 조건을 별도 메서드로 분리하여 추상화 수준을 높이자고 제안했다. (개선 제안)
  - 조건: isValidSize라는 메서드를 사용하는 예시를 제시했다. 해당 메서드 분리의 실제 반영 여부는 대화에서 별도로 확인되지 않는다.
