# FC0151 · 저장 어댑터의 추가 책임

[소속 분야: 의존성·교체 가능성](../09-dependency.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0155](FC0155.md) · [다음 FC: FC0153 →](FC0153.md)

## 검토 질문

- [ ] 저장 라이브러리를 감싼 구현이 모델 변환·정책·기술 격리 등 분명한 책임을 가지는가?

**직접 작성한 예시**

```java
final class PersistentCustomers implements Customers {
    private final EntityStore entities;
    Customer get(long id) { return toDomain(entities.get(id)); }
}
```

**적용 설명:** 저장 모델 변환을 담당하는 어댑터라면 감싸기의 의미가 있다. 단순 전달만 하는 계층은 비용과 이점을 비교한다.

## 구체적인 검토 사례

**혼합·경계:** 저장소 의존성 감싸기·추상화와 Spring Data 사례가 겹침.

- [ ] JPA 리포지터리를 직접 사용하지 않고 구현체에 주입해서 사용하는 이유를 물었다. (설계 질문)
  - 조건: 리뷰 참여자는 순수한 궁금증이라고 명시했다. 해당 의존 구조가 잘못되었다는 지적은 아니며, 작성자의 설명은 이 단위에 없다.

- [ ] SessionManager를 싱글턴으로 구현한 이유를 질문했다. (설계 질문)
  - 조건: dye0p의 질문에 작성자는 관리 필드가 static이더라도 요청마다 인스턴스를 생성할 필요는 없다고 생각해 싱글턴을 선택했다고 설명했다. 작성자는 서버 실행 시 한 번 생성하는 대안도 가능하며 싱글턴일 필요는 없다고 판단해 두 번째 방식으로 바꿨다고 보고했다. 질문 자체가 싱글턴의 결함을 확정하거나 변경을 요구한 것은 아니다.

- [ ] JWT 비밀키를 @Value로 주입한 이유를 묻는다. (설계 질문)
  - 조건: 작성자는 처음에는 학습 테스트를 참고해 선택했으며, 이후 @ConfigurationProperties와 환경 변수 등의 대안을 비교한 뒤 현재는 추가 설정이 불필요하다고 판단해 @Value를 유지하겠다고 했다. 대안별 타입 안전성·테스트 용이성·보안에 관한 설명은 작성자의 주장으로, 리뷰어의 변경 요구나 검증된 결론이 아니다.
