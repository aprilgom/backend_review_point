# FC0428 · DB 테스트 격리와 초기 데이터 구성 방식들의 장단점을 학습한 뒤 상황에 맞게 선택하자는 제안이다.

[소속 분야: 테스트 준비·격리](../22-test-isolation.md) · [전체 목차](../README.md) · [FC 번호별 목차](../FC_INDEX.md) · [← 이전 FC: FC0422](FC0422.md) · [다음 FC: FC0425 →](FC0425.md)

- [ ] DB 테스트 격리와 초기 데이터 구성 방식들의 장단점을 학습한 뒤 상황에 맞게 선택하자는 제안이다. (개선 제안)
  - 조건: 리뷰어는 팀마다 방식이 다르고 표준이 정해져 있지 않다고 설명했다. JPA 사용 시 truncate 쿼리를 선호한다는 개인적 경험과 함께 @DataJpaTest, @Transactional, @Sql 등을 학습 대상으로 제시했으며, 특정 방식을 필수로 적용하도록 요구하지 않았다.

- [ ] 테스트가 실제 사용 중인 DB에 데이터를 적재하고 삭제하지 않도록 테스트 환경을 분리하고, H2 등의 대체 DB 사용을 고려한다. (개선 제안)
  - 조건: 리뷰어는 현재 테스트가 실제 사용 중인 DB를 변경한다고 지적했다. H2는 운영 데이터에 영향을 주지 않기 위한 여러 대안 중 하나로 제안되었으며, 유일한 해결책으로 요구되지는 않았다.

- [ ] 다른 로컬 환경에서도 테스트가 깨지지 않도록 인메모리 DB 사용을 검토해 보자고 제안했다. (개선 제안)
  - 조건: 테스트의 환경 의존성을 줄이기 위한 제안이며, 실제로 다른 환경에서 테스트가 실패했는지는 제시되지 않았다.

**직접 작성한 예시 · 첫 번째 백엔드 항목**

```java
connection.setAutoCommit(false);
try { exerciseRepository(connection); }
finally { connection.rollback(); }
```

**적용 설명:** 테스트 소유 커넥션 안의 변경을 롤백하는 조각이다. 별도 HTTP 요청·다른 커넥션의 커밋은 이 롤백에 포함되지 않는다.
